# 検索拡張生成とナレッジグラフの併用

検索拡張生成とナレッジグラフは、同じ問題を解く仕組みではない。
得意な問いが違うため、どちらか一方へ統一するより、質問の性質に応じて使い分けた方がよい。

**検索拡張生成（Retrieval-Augmented Generation, RAG）**は、文書から関連する説明や背景を探すことに向く。
**ナレッジグラフ（Knowledge Graph, KG）**は、実体同士の関係を辿り、集合や経路を正確に求めることに向く。

```text
質問
├─ 文書の説明が必要 → 検索拡張生成
├─ 関係や集合が必要 → ナレッジグラフ
└─ 両方が必要       → 両方を取得
                       ↓
                大規模言語モデル
```

## ナレッジグラフが向く問い

元資料は、ナレッジグラフが特に扱いやすい問いを五種類に整理している。

### 条件を満たす集合

複数の条件を同時に満たす対象を、正確な集合として求める問いである。

例として、「重大度がCriticalで、バックエンドチームが担当し、まだ未解決の障害」を探す場合がある。
文書検索の上位数件ではなく、条件を満たす対象をすべて求めたい。

### 二つの対象の差

二つの対象が持つ関係や属性の違いを明示したい場合である。

たとえば、二つのサービスが利用するライブラリの差を調べる問いでは、関係集合を比較する方が正確になる。

### 関係の経路

複数段の依存関係や所属関係を辿る問いである。

たとえば、「認証サービスからデータベースサービスまで、どの依存経路でつながっているか」を調べる場合がある。

### 関係が存在しない対象

「担当者がいない障害」「テストがないコンポーネント」のように、特定の関係が存在しない対象を探す問いである。

### 件数や分布

条件を満たす対象の件数を数えたり、チームごとの件数を集計したりする問いである。

これらは、意味の近い文書を探す問題ではない。
構造化されたデータへ条件を適用する問題である。

## 検索拡張生成が向く問い

文章の背景、理由、手順、設計意図そのものが答えになる場合は、RAGが向く。

たとえば次のような問いがある。

- 認証サービスをこの構成にした理由を知りたい。
- 障害から復旧する手順を確認したい。
- 仕様変更の背景を読みたい。

こうした文章をすべて細かな実体と関係へ分解すると、モデル設計の負担が増える。
元の文章が持つ説明の流れも失われやすい。

## 質問を三種類へ振り分ける

実装では、すべての質問を同じ検索処理へ送らず、質問の種類を判定する。
少なくとも次の三種類へ分けられる。

```text
構造問い合わせ：集合、集計、経路、関係、関係の欠如、正確な事実
文書検索：背景、説明、手順、文章としての文脈
併用：構造化された事実と文章の両方
```

たとえば、「BUG-001の修正方法と関連コンポーネントを教えて」という質問なら、関連コンポーネントはナレッジグラフから取得し、修正手順は文書検索から取得できる。
最後に大規模言語モデル（LLM）が二つの結果を一つの説明へまとめる。

## LLMに事実を作らせない

LLMは、質問の分類、自然言語から問い合わせ文への変換、複数の結果を読みやすい文章へまとめる処理に使える。

ただし、LLMが生成したデータベース問い合わせを、書き込み権限のある本番データベースへそのまま実行するのは危険である。
読み取り専用の権限、許可する問い合わせの制限、実行前の検証などを組み合わせる必要がある。

この構成では、LLMが事実を推測して埋めるのではなく、検索と構造問い合わせで得た結果を説明する位置へ置く。

## GraphRAGという名前より、情報の種類を見る

元資料は、グラフ構造を検索へ取り入れるGraphRAGも扱っている。
ただし、製品名や方式名だけで設計を決める必要はない。

文書の意味的な近さと、実体同士の明示された関係は、別の情報である。
質問へ答えるためにどちらが必要かを先に判断する。
