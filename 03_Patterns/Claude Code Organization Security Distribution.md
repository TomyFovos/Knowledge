# Claude Code Organization Security Distribution

## 概要

Claude Codeを組織に広げるとき、課題は「使わせるか、禁止するか」ではない。

Claude Codeはファイルの検索・読み書き・編集、Web検索、ページ取得、コマンド実行まで行える。つまり便利さの源泉そのものが、ローカルファイルや認証情報の破壊・漏洩につながり得る権限でもある。

一方で、全員に同じ厳格な設定を配れば安全になるとも限らない。コマンドやリスクを理解して自分で調整したいエンジニアと、最初から安全な状態で使いたい非エンジニアでは、必要な自由度が違うからである。

メルカリの事例が示しているのは、**組織全体で一つの設定に統一するのではなく、MDMを使って利用者の特性に応じたセキュリティ設定を分離し、安全性と生産性を両立させる**という考え方である。

## なぜ重要か

AI/LLMの利用がAgentic Workflowへ進むほど、AIが実行できる操作は増える。

チャット型AIであれば、危険な回答を受け取っても最終的に実行するのは人間である。しかしClaude Codeのようなエージェントは、ファイルを編集し、コマンドを実行し、ネットワークへアクセスできる。人間が指示した範囲を超えて、PC上の重要ファイルや認証情報に影響する可能性もある。

特に組織利用では、エンジニアだけが使うとは限らない。資料では、Claude Codeの利用を非エンジニアにも広げながら、活用そのものを止めずに安全性を確保することを課題としている。

ここで重要になるのが、利用者教育だけに依存せず、**設定そのものを組織側から配布すること**である。

## Claude Codeに存在するリスク

Claude Codeの主な能力として、資料では次が挙げられている。

- ファイルの検索、読み書き、編集
- Web検索、ページ取得
- コマンド実行

特にコマンド実行は、`rm -rf` や `curl` のような操作も可能であり、任意の行動につながり得る。

PC上には、業務上重要なファイルや認証情報が存在する。オンラインストレージを基本にしたり、認証情報を短期化したりしても、端末上でClaude Codeが広い権限を持つ限りリスクは残る。

つまり、Claude Codeのセキュリティは「モデルが安全か」だけでは決まらない。**エージェントにどの操作を許可し、どの操作を人間確認にし、どの領域へアクセスさせるか**という実行環境側の設計が重要になる。

## 基本となるセキュリティ設定

資料では、Claude Codeを安全に利用するための設定を5つの観点に整理している。

### 1. 人間による確認を残す

パーミッションモードのbypassを禁止し、AIが確認なしに操作できる状態を避ける。

エージェントの自律性を高めるほど、人間による承認ポイントは減る。しかし安全性が必要な環境では、すべての承認を取り除くのではなく、危険度の高い操作について人間を制御ループに残す必要がある。

### 2. 重要なコマンドは確認を必須にする

Bashのインライン実行や`curl`など、影響範囲が広い操作は確認を必須にする。

重要なのは「Bashを全面禁止する」ことではない。エージェントを実用的に使うための能力を残しつつ、危険な操作の手前に確認を置く。

### 3. 危険な行動は明示的に禁止する

例として、次のような操作が挙げられている。

- 環境変数の管理ファイルの読み込み禁止
- AIによる`sudo`を使ったシステム変更の禁止

認証情報が含まれやすい場所や、端末全体へ影響する権限については、人間確認だけではなく禁止ルールとして扱う。

### 4. Sandboxで実行範囲を狭める

Sandboxを利用し、作業対象ディレクトリの外への操作やネットワークアクセスを制限する。

これは、AIが誤った判断をした場合でも被害範囲を小さくするための境界になる。ネットワークを制限することは、情報漏洩の防止にもつながる。

### 5. 会社のセキュリティポリシーを伝える

システムプロンプトに会社のセキュリティポリシーを追加する。

権限制御だけでは表現しきれない「組織としてどのように行動してほしいか」をエージェントへ伝える役割を持つ。

## 個人設定ではなく、組織設定として配布する

個々の利用者に「この設定をしてください」と依頼するだけでは、設定漏れや差異が生まれる。

そこで資料では、MDM（Mobile Device Management / 端末管理）を使って、Claude Codeの設定とシステムプロンプトを一斉展開する方法を採用している。

Claude Codeには、OSレベルの管理機構から設定を配布できる仕組みがあり、資料ではmacOSやWindowsのManaged Policyと、組織向け`CLAUDE.md`の配布先が示されている。

ここでのポイントは、セキュリティルールをドキュメントとして配るだけではなく、**端末管理の仕組みから実際のClaude Code設定へ反映する**ことである。

## MDMで一律配布すると起きる問題

一斉配布には別の問題がある。

MDMで配布された設定は高い優先度で扱われるため、全員へ同じ設定を配ると、利用者側でのカスタマイズが難しくなる。

しかし組織には、少なくとも二つの異なる利用者像が存在する。

### エンジニア

コマンドやセキュリティリスクについて理解があり、必要に応じてClaude Codeの設定をカスタマイズしたい。

安全性は必要だが、すべてを固定されると生産性が下がる。

### 非エンジニア

細かな設定を自分で調整することを前提にせず、最初から安全な状態で利用したい。

自由度よりも、安全なデフォルトが重要になる。

この二者へ同じ設定を配ると、どちらかに無理が生じる。

厳格にすればエンジニアの自由度を奪い、緩くすれば非エンジニアに必要な安全性を提供できない。

## 配布設定を分離する

そこでメルカリの事例では、MDMに連携した情報を利用して、配布するClaude Code設定を分離している。

考え方は単純である。

**エンジニアには、安全性を確保したうえでカスタマイズ可能な設定を配る。**

**非エンジニアには、実現できる範囲で最も安全な設定を、利用者による追加設定なしで提供する。**

組織のセキュリティポリシーを一つにすることと、全利用者の設定を完全に同一にすることは別である。

守るべき境界は共通化しながら、利用者の能力や役割に応じて自由度を変えることで、利用を止めずに安全性を確保できる。

## このパターンの本質

この事例から得られる中心的な考え方は、Claude Code固有の設定項目そのものよりも、**Agentを組織へ展開するときの権限制御モデル**にある。

一律に強い制限をかけるのではなく、次の層を組み合わせる。

1. 組織として絶対に越えさせない禁止事項
2. 危険な操作の前に置く人間承認
3. Sandboxやネットワーク制限による実行境界
4. システムプロンプトによる組織ポリシー
5. 利用者の能力・役割に応じた設定プロファイル
6. MDMによる強制配布

これによって、「自由に使わせる」か「厳しく固定する」かという二択ではなく、**安全性を共通基盤として維持しながら、必要な人だけに適切な自由度を与える**構成を作れる。

AIエージェントを組織に導入するとき、安全性と生産性は単純なトレードオフではない。権限、承認、Sandbox、ポリシー、利用者区分を分離して設計することで、両方を満たせる余地が生まれる。
