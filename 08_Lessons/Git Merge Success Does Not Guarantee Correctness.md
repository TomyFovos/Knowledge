# Gitのマージ成功は内容の正しさを保証しない

Status: Adopted

#lesson

Gitでマージが衝突なしに終わっても、統合された内容まで正しいとは限らない。

`marcbrooker/git_weirdness` は、現在のGitで再現できる反例を示している。
通常の `git merge` が終了コード0で成功し、衝突も報告しないまま、入力のどちらにも存在しない重複変更を作る場合がある。

ここで区別すべきなのは、「Gitがテキストを統合できたこと」と「変更意図どおりの結果になったこと」である。
前者から後者を導くことはできない。

## 最小反例では一行が余計に増える

出典リポジトリの最小例では、基準となる内容が次の4行である。

```text
a
b
b
b
```

左側の変更は `a` を1行追加する。

```text
a
b
a
b
b
```

右側の変更は、先頭付近へ `b` と `a` を追加する。

```text
b
a
b
a
b
b
```

Gitの標準的なマージ戦略 `ort` で統合すると、衝突なしで次の8行が生成される。

```text
b
a
b
a
b
a
b
b
```

しかし、基準4行に対して左側は1行、右側は2行しか追加していない。
追加だけを一度ずつ適用するなら、結果は最大でも7行になる。

```text
|Left| + |Right| - |Base|
= 5 + 6 - 4
= 7
```

実際の結果は8行である。
つまり、一つの `a` が余分に生成されている。

## 繰り返し行では差分の対応付けが曖昧になる

三方向マージでは、共通の基準から左側と右側の差分を求め、それらを統合する。

```text
        基準
       /   \
   左差分  右差分
      \     /
       マージ
```

問題になるのは、同じ行が繰り返される部分である。

```text
b
b
b
```

同じ内容の行が複数あると、「どの `b` とどの `b` を対応させるか」が一意に決まらない。

Gitの `ort` マージ戦略は、内部の差分計算に `histogram` というアルゴリズムを使う。
このアルゴリズムは処理速度や人間が読みやすい差分を重視した発見的手法を持ち、常に最大の対応付けを求めるわけではない。

その結果、左側と右側の変更が、本来は関連する変更でも別々の位置へ対応付けられ、Gitが独立した変更として両方を適用する場合がある。

## 差分アルゴリズムを変えるとこの反例の結果は変わる

出典リポジトリの最小例では、差分アルゴリズムによって結果が異なる。

| 差分アルゴリズム | この反例での結果 |
| --- | --- |
| `histogram` | 誤った8行を生成する |
| `myers` | 正常な結果になる |
| `minimal` | 正常な結果になる |
| `patience` | 正常な結果になる |

この事実から、「別のアルゴリズムへ変えればすべてのマージが正しくなる」とは言えない。
示されているのは、実装で選ぶ差分アルゴリズムによって、この種の反例の振る舞いが変わることまでである。

## 形式研究では別の失敗も知られている

出典リポジトリは、2007年の論文 *A Formal Investigation of Diff3* も背景としている。

この論文は、直感的には独立して見える離れた変更でも不要な衝突が発生することや、diff3が一定の安定性を持たないことを形式的に示している。

ただし、この論文は差分計算が最大の非交差対応を返すことを前提にしている。
そのため、中心になるのは「本当は統合できるのに衝突と判定する」という安全側の失敗である。

今回のGitの反例は逆向きである。
衝突なしと判定しながら、内容として誤った統合結果を返す。

## 出典リポジトリは反例を自動探索している

`git_weirdness` は、一つの手作り例だけを示しているわけではない。
反例を探し、最小化するためのプログラムも含んでいる。

`fuzz.py` は、基準、左側、右側の内容をランダムに生成し、誤ったマージを探索する。
追加だけを行う場合、結果の行数は次の上限を超えないはずだという性質を検査条件にしている。

```text
マージ後の行数 <= |Left| + |Right| - |Base|
```

この上限を超えるのにGitが「衝突なし」と返した場合、入力にない内容を重複生成した反例として扱える。

`minimize.py` は、見つけた反例をさらに小さくし、問題が起きる最小入力を探す。
出典リポジトリでは、二種類の文字だけを使う場合、基準4行と合計3行の追加が最小反例として示されている。

## 実務ではマージ成功を品質判定にしない

マージが成功したことは、次の検証へ進める条件の一つにはなる。
しかし、それだけで変更を受け入れる根拠にはならない。

```text
Gitでマージする
↓
ビルドする
↓
単体テストを実行する
↓
結合テストを実行する
↓
静的解析を行う
↓
必要なら生成物や振る舞いを確認する
↓
受け入れる
```

どの検証を置くかはプロジェクトによって違う。
共通するのは、マージ処理そのものも誤り得る中間工程として扱うことである。

## AIエージェントの並列開発では変更意図も照合する

複数のAIエージェントが別々のブランチや作業ツリーで変更を作ると、マージ回数は増える。
低い確率の失敗でも、試行回数が増えれば遭遇する可能性は上がる。

テストだけでなく、各AIエージェントへ与えた変更意図と、最終マージ結果を照合する方法も考えられる。

```text
AIエージェントAの変更意図 ─┐
AIエージェントBの変更意図 ─┼→ マージ結果を検証する
AIエージェントCの変更意図 ─┘
```

確認対象には、次のようなものがある。

- 追加したはずの変更が存在するか。
- 同じ変更が重複していないか。
- 誰も変更していない領域へ想定外の差分がないか。
- 最終成果物が要求や設計を満たすか。

このとき、Gitは「安全な統合器」ではなく、「結果を検証する必要がある処理の一つ」になる。

## この知見の範囲

この反例から、「通常のGitマージは頻繁に壊れる」と結論付けることはできない。
示されているのは、衝突なしのマージから内容の正しさを論理的には保証できないという点である。

今回の重複生成は、特定の入力と `histogram` 差分の組み合わせで再現する。
実際の開発でどの程度の頻度で起きるかは、別に測る必要がある。

したがって、実務上の教訓はGitを避けることではない。
Gitが作った統合結果も、他の自動生成物と同じように検証することである。
