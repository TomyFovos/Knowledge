# ナレッジベース

このリポジトリは、人工知能（AI）とソフトウェア開発を中心に、調査結果、設計上の判断、実験、失敗から得た知見を共有するためのナレッジベースである。

完成した文書だけを置く場所ではない。
思いついたことを調べ、試し、判断し、その結果を再利用できる知識へ変えるまでの過程も残す。

```text
思いつく
↓
調べる
↓
試す
↓
判断する
↓
知識として残す
```

## 何を残すか

技術の変化が速い分野では、個人の記憶やチャット履歴だけに知識を置くと、同じ調査や判断を別の人が繰り返すことになる。
このリポジトリでは、後から別の人が判断の根拠まで追える形で情報を残す。

主な対象は次のとおりである。

- 大規模言語モデル（LLM）と生成AI
- AIエージェントと複数エージェント構成
- コンテキスト設計
- AIエージェントの実行基盤設計
- ツール呼び出し
- 評価とベンチマーク
- AIを使った開発方法
- ソフトウェア設計
- テストと品質保証
- 継続的インテグレーションと継続的デリバリー（CI/CD）
- 開発方法論
- 新しいツールやサービス
- 実験結果
- 設計上の判断
- 失敗から得た知見
- 今後試したいアイデア

## 書き始めるときの原則

### まず記録する

内容が整理されていなくても、忘れる前に残す。
分類先に迷う場合は `00_Inbox` に置き、後から整理する。

### 一つのノートに一つの主題を置く

一つのノートで複数の問題を同時に扱うと、後から参照しにくくなる。
題名を見ただけで内容を推測できる単位に分ける。

### 関連するノートを内部リンクで結ぶ

フォルダは大まかな分類に使い、知識同士の関係は Obsidian の内部リンクで残す。

```md
[[関連ノート]]
```

### 未完成であることを隠さない

途中の考察や未検証の案も記録してよい。
ただし、現在の状態が判断できるようにする。

状態を付ける場合は、次のような値を使う。

- `Idea`：まだ検討段階の案
- `Researching`：調査中
- `Experimenting`：実験中
- `Adopted`：採用済み
- `Rejected`：不採用

状態名は機械的に扱う可能性があるため、英語表記を維持する。

## ディレクトリの役割

```text
Knowledge/
├── 00_Inbox/
├── 01_Concepts/
├── 02_Methodologies/
├── 03_Patterns/
├── 04_Systems/
├── 05_Ideas/
├── 06_Experiments/
├── 07_Decisions/
├── 08_Lessons/
├── 09_References/
└── 99_Archive/
```

### `00_Inbox`

分類前のメモを置く。
定期的に内容を見直し、適切なフォルダへ移す。

### `01_Concepts`

概念そのものを説明するノートを置く。
「これは何か」「他の概念と何が違うか」を理解するための場所である。

### `02_Methodologies`

開発や調査をどう進めるかという方法論を置く。
特定の製品より、再利用できる進め方を扱う。

### `03_Patterns`

繰り返し現れる設計上の問題と、その解き方を置く。
採用条件と限界まで書き、名前だけのパターン集にしない。

### `04_Systems`

具体的な製品、サービス、フレームワーク、実装基盤を扱う。
機能一覧ではなく、どの問題をどう解いているかを中心に書く。

### `05_Ideas`

採用するか決めていない案を置く。
案を残すときは、背景、期待する効果、未確認の点も書く。

### `06_Experiments`

実際に試した内容と結果を置く。
成功だけでなく、失敗した実験も残す。

### `07_Decisions`

チームとして行った重要な判断を置く。
採用した案だけでなく、比較した選択肢と当時の判断材料を残す。

### `08_Lessons`

実際の開発、運用、実験から得た教訓を置く。
何が起き、なぜ起き、次回は何を変えるかまで書く。

### `09_References`

外部資料の原本や参照用ファイルを置く。
PDFを保存した場合は、その資料を使ったMarkdownノートの「参考資料」から内部リンクで辿れるようにする。

### `99_Archive`

現在は使っていない情報を保管する。
削除するか迷う内容は、まずここへ移す。

## ノートの基本形

すべての見出しを埋める必要はない。
そのノートで必要な項目だけを使う。

```md
# タイトル

## 概要

対象と、扱う問題を書く。

## 本文

根拠、仕組み、判断条件を書く。

## 関連

- [[関連ノート]]

## 参考資料

- 参照元
```

本文では、一文ごとに改行し、段落ごとに一つの論点を置く。
英語の専門用語を使う場合は、初出で日本語の意味を説明する。
説明なしに英単語だけを混ぜない。

## アイデアの基本形

```md
# アイデア名

Status: Idea

## アイデア

何を試したいかを書く。

## 背景

なぜ必要だと考えたかを書く。

## 期待する効果

何が改善すると考えているかを書く。

## 課題

未確認の点や懸念を書く。

## 次に試すこと

次の確認方法を書く。
```

## 実験記録の基本形

```md
# 実験名

Status: Experimenting

## 目的

何を確かめる実験かを書く。

## 仮説

事前に予想した結果を書く。

## 方法

どう確かめたかを書く。

## 結果

観測した事実を書く。

## 考察

結果をどう解釈するかを書く。

## 次の対応

次に何をするかを書く。
```

## 判断記録の基本形

```md
# 判断内容

Status: Adopted

## 背景

何を決める必要があったかを書く。

## 選択肢

比較した案を書く。

## 判断

採用した案を書く。

## 理由

採用理由を書く。

## 受け入れる不利益

採用によって残る問題を書く。

## 再検討条件

どの条件で判断を見直すかを書く。
```

## タグの使い方

技術分類はフォルダと内部リンクを中心に管理する。
タグは状態や文書種別のように、用途が明確な場合だけ使う。

```text
#idea
#experiment
#decision
#lesson
#draft
```

## ファイル名

内容を推測できる名前を付ける。
日付は、その日付自体が検索や判断に必要な場合だけ含める。

既存ノートには英語名のファイルもあるため、無理に一括改名はしない。
本文の題名と説明は日本語で統一し、内部リンクを壊さないことを優先する。

## 内容が重複したとき

似たノートを見つけても、すぐに片方を消さない。
まず相互にリンクし、両者の役割が重なっていることを確認してから統合する。

他の人が書いた内容を大きく変える場合も、元の意図と根拠を失わないようにする。
異なる見方がある場合は、反対意見を消さず、どの前提で結論が分かれるかを書く。

## 他の管理手段との使い分け

Obsidian、Todoist、GitHub Issues は役割が異なる。

```text
Obsidian
知識、調査結果、設計思想、判断理由

Todoist
個人が忘れないための作業

GitHub Issues
実際に開発する作業、不具合、改善
```

ナレッジから実装作業が生まれた場合は GitHub Issue へ移し、必要に応じてIssue側から元ノートを参照する。

## このリポジトリで守ること

文書を美しく見せることより、後から別の人が再利用できることを優先する。
そのためには、結論だけでなく、判断に使った条件と参照元を残す必要がある。

書いた知識は固定物ではない。
新しい事実が得られたらリンクを足し、必要なら内容を更新する。
