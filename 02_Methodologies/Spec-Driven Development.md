# 仕様駆動開発

AIエージェントへ実装を任せる前に、要求、設計、作業項目を文書として整理する方法がある。
この方法は、**仕様駆動開発（Spec-Driven Development, SDD）**と呼ばれている。

元資料は、2025年7月にAWSが開発環境Kiroを発表した時期から、この呼び方が広まったと整理している。
ただし、「実装前に考える」という行為そのものは新しくない。
Vibe Codingのように先に生成へ進む開発が広がったため、従来からあった「実装前に仕様を作る」進め方へ、後から名前が付いたという見方を示している。

## 仕様には二つの役割がある

元資料は、AI時代の仕様駆動開発に二つの実用上の役割を見ている。

一つは、AIエージェントへ作業の順序を与えることだ。
要求を確認し、設計し、作業項目へ分けてから実装へ進むことで、いきなりコードを変更するのを防ぐ。

もう一つは、決めた内容をエージェントと人間が後から参照できる形で残すことだ。
一回の会話だけに判断を置かず、変更や保守のときにも参照できる長期記録として使う。

## 各ツールの流れは似ている

Kiro、Spec-Kit、OpenSpecは、文書名や細かな手順が異なる。
しかし、元資料は中心となる流れを次のように整理している。

```text
Kiro
要求 → 設計 → 作業項目

Spec-Kit
仕様化 → 計画 → 作業項目

OpenSpec
変更提案 → 仕様 → 設計 → 作業項目
```

共通しているのは、実装前に未決事項を外へ出し、人間が確認できる形へする点である。

## 仕様をいつまで残すかで三つに分かれる

Martin Fowlerの記事は、仕様の扱い方を三つに分類している。

- **仕様を先に作る方式（spec-first）**：実装前に仕様を書き、作業が終わったら仕様を捨てる。
- **仕様を基準として残す方式（spec-anchored）**：作業後も仕様を残し、変更や保守に合わせて更新する。
- **仕様を原本にする方式（spec-as-source）**：仕様を原本とし、コードはそこから生成する。

元資料は、現時点の実務では最初の二つが中心であり、仕様を原本にしてコードを全面生成する方式は一般的な運用には至っていないと整理している。

## 短期の計画だけなら専用の仕様は必須ではなくなった

元資料が「仕様駆動開発の消費期限」と表現する理由の一つは、AIエージェント自体が計画機能を持つようになったことにある。

現在のコーディングエージェントには、調査し、質問し、実装計画を作り、その計画に沿って作業する **計画モード（Plan Mode）**が組み込まれている場合がある。
これは、仕様を先に作る方式が担っていた「考えてから実装する」という役割と重なる。

そのため、一回の作業計画を作るだけなら、専用の仕様ファイルを長く維持する必要は薄くなる。
設計判断を残す目的なら、設計判断記録（ADR）や用語集のような別の文書でもよい。

## チーム開発では仕様の役割が変わる

一人でAIエージェントを使う場合、利用者が変更内容を追えていれば、細かな仕様文書を省けることがある。
しかし、チームで開発すると事情が変わる。

AIエージェントが高速に変更を作れるほど、人間側が変更理由を理解し、レビューする速度が追い付かなくなる。
このずれは、コードの実装と、チームが持つ「なぜそう動くのか」という理解の間に負債を作る。

元資料は、Thoughtworksの **コードベースの認知負債（codebase cognitive debt）**や、生成AI利用時の **理解負債（Comprehension Debt）**の議論と、この問題を結び付けている。

この場面では、仕様はAIエージェントだけのための指示書ではない。
変更の意図を人間が読み、合意し、レビューするための共通形式になる。

## チームへAI駆動開発を導入するときの「型」になる

元資料は、チームへAI駆動開発を導入する方法として、AI-DLC、個別のスキル集、仕様駆動開発を比較している。

AI-DLCは開発全体を扱える一方、既存の開発プロセスや会社標準まで見直す必要があり、導入負担が大きかったと報告している。

反対に、個別のスキルを組み合わせる方法は軽いが、チーム全員が共有する作業手順としては形が弱いと評価している。

その中間として、仕様駆動開発には次の三つがある。

- 実装前に要求と設計を確認する規律。
- 変更理由を人間が理解するための文書形式。
- 仕様と実装を照らし合わせるレビューの流れ。

元資料は、これを最終的な完成形ではなく、AI駆動開発へ慣れるまでの「守る型」として使う考え方を示している。

## OpenSpecを選んだ理由

元資料の事例では、特定のAIエージェントへ固定しない方針から、Kiro固有の仕様機能を候補から外している。
その上で、Spec-KitとOpenSpecを比較した。

Spec-Kitは生成する文書が大きくなりやすく、人間が読む負担が高いと判断した。
そこで、より軽量なOpenSpecを選んでいる。

特に評価しているのは、次の二つの操作である。

- `/opsx:verify`：仕様と実装が対応しているかを一次確認する。
- `/opsx:archive`：作業が終わった仕様を保管し、現在の仕様へ反映する。

ここでの判断軸は機能数ではない。
チームが読み続けられる量に抑えながら、仕様と実装の対応を保てるかを見ている。

## 仕様が新しい負債になったら型を変える

仕様駆動開発を続けること自体が目的になると、仕様ファイルの維持が新しい負担になる。
元資料は、次のような状態を「型を破る」きっかけとして挙げている。

- 実装より人間レビューの待ち時間が支配的になる。
- 仕様ファイル同士や、仕様と実装のずれを直す作業が重くなる。
- 自然言語の仕様では機械的に検査できない部分が問題になる。
- 詳細な仕様が、性能の上がったAIエージェントへの不要な制約になる。

この段階では、残す情報を設計判断記録やコードへ移し、不要な仕様ファイルを減らす選択肢が出てくる。

仕様駆動開発には期限が決まっているわけではない。
チームが変更を理解し、合意するための助けより、仕様を維持する負担の方が大きくなったときが見直し時になる。
