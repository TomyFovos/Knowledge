# RAG Limitations and Knowledge Graph

## 概要

RAGは、LLMに外部文書を検索・提示して知識不足を補う強力な方法である。ただし、RAGが解決するのは主に「関連する文脈を見つけること」であり、関係性の推論や構造的整合性を保証する仕組みではない。

この違いを見誤ると、「検索結果はもっともらしいのに、業務判断としては信用できない」という状態になる。

## LLM単体の限界

LLMは確率的に次のトークンを生成する。文章生成には強いが、同一入力でも回答が揺れる可能性があり、学習後に更新された社内情報も自動では保持しない。

そのため、文章要約やアイデア出しのような誤答コストの低い領域と、金額・契約・権限・コンプライアンスのような誤答コストの高い領域を分けて考える必要がある。

本資料ではこれを **Safe Zone / Unsafe Zone** と呼んでいる。

- Safe Zone: 誤答コストが低く、LLM単体でも扱いやすい
- Unsafe Zone: 誤答コストが高く、構造化された事実や決定論的処理を併用すべき

## RAGが失敗しやすい典型パターン

### 1. Chunk Boundary

文書を一定サイズに分割すると、一つの意味が複数チャンクへ分断される。検索で一部だけ取得できても、条件や前提が別チャンクに残り、意味が欠けることがある。

### 2. Hallucination Amplification

取得文書に必要な情報が不足していると、LLMがその空白を「もっともらしい補完」で埋めることがある。RAGが取得した文書があることで、かえって利用者が回答を信じやすくなる。

### 3. Cross-document Reasoning

答えを出すために複数文書の関係をつなげる必要がある場合、類似検索だけでは必要な文書を一貫して揃えにくい。

例として、現在の契約プラン、製品の制限値、上位プランだけが持つオプションを別文書から組み合わせて判断するケースがある。

### 4. Negative Queries

「担当者がいない」「テストが存在しない」のような、存在しない関係を探す問いは、類似文書検索では扱いにくい。

### 5. Aggregation / Exact Set

「何人いるか」「条件をすべて満たす対象は何か」のような、集合・集計の問いは検索ではなくデータ問い合わせの問題である。

## KGが補う部分

KGでは、エンティティと関係を明示的に保持するため、複数の関係を辿る、関係の欠如を調べる、集合を絞る、件数を数える、といった処理をクエリとして表現できる。

したがって「RAGが弱いからKGに置き換える」のではなく、**文脈検索と構造推論を別問題として扱う**ことが重要になる。

## 95%という数字について

元資料はMIT NANDA Reportを引用し、「生成AIパイロット案件の95%が実質的ROIをもたらしていない」と紹介している。本ノートでは、その数値を一般法則として拡張せず、元資料の問題提起として扱う。

重要な論点は数値そのものより、AIシステムが組織固有の文脈・過去の意思決定・構造化されたルールを継続的に扱えないまま、本番業務へ投入されることにある。
