# ナレッジグラフ

**ナレッジグラフ（Knowledge Graph, KG）**は、知識を「実体」と「実体同士の関係」で表す方法である。
人物、製品、障害、組織などを点として持ち、それらがどう結び付いているかを辺として記録する。

たとえば、「鈴木さんはProject Alphaを担当している」「Project Alphaの予算承認者は山田さんである」といった事実を、文字列ではなく関係として保持できる。

LLMは自然な文章を生成できる一方、事実や関係を確率的な生成だけに任せると、回答が揺れる可能性がある。
ナレッジグラフを併用すると、文章生成と、検査可能な事実関係の管理を分けられる。

## 二つの代表的な表現方法

ナレッジグラフには複数の表現方法がある。
元資料では、RDFとプロパティグラフを代表例として扱っている。

### RDF

**RDF（Resource Description Framework）**は、知識を「主語、述語、目的語」の三つ組で表す標準形式である。

```text
<鈴木一郎> <担当する> <Project Alpha>
<Project Alpha> <予算承認者> <山田部長>
```

一つの事実を一つの三つ組として積み重ねる。
標準形式との相互運用や、外部の公開データと接続したい場合に向く。

### プロパティグラフ

**プロパティグラフ（Property Graph）**は、実体を表すノードと、関係を表す辺の両方に属性を持たせる形式である。
Neo4jは代表的な実装の一つであり、Cypherという問い合わせ言語で関係の経路を辿れる。

元資料では、標準形式との相互運用より、開発のしやすさやモデル変更の柔軟性を優先する場合に、プロパティグラフから始める案を勧めている。

## リレーショナルデータベースとの違い

リレーショナルデータベース（RDB）も、表同士の関係を表現できる。
したがって、「RDBは関係を扱えない」という説明は正しくない。

違いが出やすいのは、何段もの関係を辿る問い合わせである。
RDBでは結合処理が増え、問い合わせとスキーマ変更の負担が大きくなることがある。

ナレッジグラフでは関係そのものをデータとして扱うため、「AからBを経由してCへ到達する」といった経路を直接表現しやすい。

一方、金額計算、集計、トランザクション処理、構造が安定した業務データにはRDBが向く。
実際のシステムでは、請求や顧客情報をRDBに置き、関係構造や権限関係をナレッジグラフに置くような使い分けが考えられる。

## ベクトルデータベースとの違い

**ベクトルデータベース**は、文章や画像を数値表現へ変換し、意味の近さを使って検索する仕組みである。
似た内容の文書を探す用途に向く。

ナレッジグラフは、あらかじめ定義した関係を扱う。
どの経路でつながっているか、特定の関係が存在しない対象は何か、条件を満たす対象が何件あるか、といった問いを扱いやすい。

両者は競合する仕組みではない。
文章の意味的な近さを探す場合はベクトル検索、明示した関係を辿る場合はナレッジグラフ、というように役割を分けられる。

## AIと組み合わせる理由

元資料は、ナレッジグラフをAIと組み合わせる利点を三つに整理している。

- **根拠を追跡しやすい**：どの関係を辿って結論へ到達したかを確認できる。
- **知識を更新しやすい**：モデルを再学習しなくても、外部の知識構造を更新できる。
- **LLMへ任せる責任を減らせる**：金額、契約、権限のように誤りの影響が大きい情報を、構造化されたデータから取得できる。

ナレッジグラフはLLMの代替ではない。
LLMが自然言語を扱い、ナレッジグラフが事実と関係を保持するという分担に意味がある。
