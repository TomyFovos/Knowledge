# 可逆な副作用

動的に読み込んだコンポーネントを安全に外すには、コードを削除するだけでは足りない。
そのコンポーネントが登録したイベント、確保した資源、変更した共有状態、起動した子コンポーネントまで回収する必要がある。

論文 *A Programming Paradigm for Spatiotemporal Composability* は、この問題を **可逆な副作用（Revertible Effects）**として扱う。

通常の副作用は、計算が環境をどう変えるかだけを表す。
可逆な副作用では、変更後の状態と、その変更を戻す **逆操作（inverse）**を同時に返す。

```text
e : Γ → Γ × (Γ → Γ)
```

現在のコンテキスト `Γ` に副作用を適用すると、変更後のコンテキストと逆操作が得られる。
片付け処理を別の場所へ後付けするのではなく、副作用を起こす場所で戻し方も登録する点が特徴である。

## 小さな逆操作から終了処理を組み立てる

一つのコンポーネントは、複数の副作用を順に実行する。
たとえば次のような処理がある。

1. イベントリスナーを登録する。
2. ルートを追加する。
3. タイマーを開始する。
4. 子コンポーネントを登録する。

実行基盤は、それぞれの逆操作を蓄積する。
コンポーネントを外すときは、最後に行った変更から逆順に戻す。

この方式では、コンポーネント全体の終了処理を別に手書きする必要がない。
原子的な操作ごとに逆操作を定義できれば、複合的な片付け処理は実行基盤が組み合わせられる。

一般的な `deactivate()` や片付け用コールバックでは、登録処理と解除処理が離れた場所に置かれ、解除を書き忘れる可能性がある。
可逆な副作用は、作成と撤回を同じ場所で対にすることで、その責任を局所化する。

## 複数コンポーネントの変更が混ざると単純な巻き戻しでは足りない

一つのコンポーネントだけなら、逆操作を逆順に実行すればよい。
しかし、複数のコンポーネントが同じ環境へ変更を加えると、変更の履歴は入り交じる。

コンポーネントAが共有状態を変更し、その後にBが別の変更を加えたとする。
Aだけを外したいとき、Aの逆操作がBの変更まで消してしまえば、コンポーネント単位の回復にはならない。

論文は、この問題を扱うために、副作用同士の **独立性と可換性**を条件として置く。
異なるコンポーネントの副作用が独立していれば、実行順が入り交じっていても、一方の寄与だけを撤回できる。

したがって、[[Spatiotemporal Composability]] が時間方向に求めているのは、単純な取り消し履歴ではない。
「誰が行った変更か」を追跡し、他の変更を残したまま対象の寄与だけを取り除けることが必要になる。

## 非同期処理の途中でも回復経路を保つ

コンポーネントの初期化は、一回の操作で終わるとは限らない。
複数の処理を順に進め、途中で非同期処理を待つ場合もある。

論文は、副作用を反復処理として扱えるようにし、各段階で変更と逆操作を記録する。
途中で必要な構成が変われば、そこまでに記録した逆操作を使って部分的に戻せる。

すでに開始した一回分の非同期処理は途中で切らず、その処理が終わった後に停止へ移る。
論文は、この性質を **慣性（inertia）**と呼んでいる。

## 失敗時も同じ回復経路を使う

初期化の途中で失敗した場合も、それまでに記録した逆操作を使って片付ける。
失敗専用の別経路を用意するのではなく、通常の削除と同じ回復機構へ合流させる。

失敗した実行単位は、他の兄弟コンポーネントまで巻き込まず、その単位だけが失敗状態になる。
これにより、失敗をコンポーネント単位へ閉じ込める設計が可能になる。

## 逆操作の正しさは自動では証明されない

実装例の Cordis では、コンテキストへの変更を `ctx.effect` に通し、返された片付け関数を蓄積する。

ただし、実行基盤が「この逆操作は本当に元の変更を正しく戻すか」を自動で証明するわけではない。
論文の形式モデルは逆操作の正しさを前提にし、Cordisの実装では、その正しさを副作用の作者へ委ねている。

したがって、可逆な副作用は、どんな操作でも自動で元に戻す仕組みではない。
次の規律を組み合わせて、回復可能性を構造として持つ方法である。

- 外界への変更をコンテキスト経由へ集める。
- 原子的な変更と逆操作を対にする。
- 実行基盤が逆操作を所有者ごとに追跡する。
- 別のコンポーネントの変更を壊さない独立性を保つ。
