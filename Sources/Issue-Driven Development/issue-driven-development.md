# Issue駆動開発（Issue-Driven Development）

## 概要

Issue駆動開発は、Issueを単なるタスク管理項目ではなく、開発作業の入口、実行単位、履歴の起点として扱う考え方である。

似た考え方として、日本では以前から**チケット駆動開発（TiDD: Ticket Driven Development）**が知られている。
TiDDでは「No Ticket, No Commit」という考え方が代表的で、コードを変更する前にチケットを作成し、その変更をチケットと対応付ける。

Issue駆動開発は、この考え方をGitHub Issueなどへ持ち込み、さらにAIコーディングエージェントによる開発と組み合わせやすい形へ発展させたものとして捉えられる。

ただし、「Issue-Driven Development」という名称に業界共通の厳密な標準定義が存在するわけではない。
実際の運用では、チケット駆動開発、GitHub Flow、Issue中心のAgent Workflowなど、複数の考え方が重なっている。

## 基本的な流れ

典型的なIssue駆動開発では、作業を次のように進める。

```text
要求 / バグ / 改善案
        ↓
Issueを作成
        ↓
背景・要求・受け入れ条件を記述
        ↓
Issueを作業単位として着手
        ↓
branch / worktree
        ↓
調査
        ↓
設計・計画
        ↓
実装
        ↓
テスト
        ↓
Pull Request
        ↓
レビュー / CI
        ↓
merge
        ↓
Issue close
```

この構造では、Issueが「何をするか」を示すだけでなく、その変更が必要になった理由、完了条件、実装結果までを追跡するための基点になる。

## Issueを作業契約として扱う

AIエージェントを使う場合、Issueの役割はさらに大きくなる。

人間向けのタスク管理では、Issueに「ログイン画面を修正する」とだけ書かれていても、担当者が周辺状況を確認し、不足している情報を補いながら作業できる。

一方、AIエージェントへまとまった作業を任せる場合、Issueには少なくとも次の情報が必要になる。

- なぜ変更するのか
- 何を変更するのか
- どこまでを対象とするのか
- 何を変更してはいけないのか
- どの状態になれば完了なのか
- どのように検証するのか

このため、AIエージェントを前提としたIssueは、単なるToDoよりも**作業契約**に近い。

```text
Issue
├─ Background
├─ Goal
├─ Scope
├─ Constraints
├─ Acceptance Criteria
└─ Verification
```

エージェントは、このIssueを入力としてコードベースを調査し、実装し、テストし、Pull Requestを作成する。

## IssueとPull Requestの対応

Issue駆動開発では、変更単位をできるだけ小さく保ち、IssueとPull Requestの対応関係を明確にする運用と相性がよい。

```text
Issue #101
    ↓
調査・実装
    ↓
PR #201
    ↓
レビュー・CI
    ↓
merge
    ↓
Issue #101 close
```

必ずしも「1 Issue = 1 PR」でなければならないわけではない。
大きなIssueを複数のPRへ分割する場合もある。

ただし、Issueの目的とコード変更の対応関係を追跡できる状態を維持することが重要になる。

## 仕様駆動開発との違い

Issue駆動開発と仕様駆動開発は競合する考え方ではない。

仕様駆動開発は、「システムや機能として何を実現するのか」を定義することに重点を置く。
Issue駆動開発は、その仕様や要求を「どの変更単位で実行するのか」に重点を置く。

| 比較軸 | 仕様駆動開発 | Issue駆動開発 |
|---|---|---|
| 中心 | Spec | Issue |
| 主な役割 | 作るものを定義する | 実行する変更を定義する |
| 粒度 | システム、機能、要求 | 一つの変更、修正、改善 |
| 寿命 | 比較的長い | Issue Closeまで |
| 実装との対応 | 1つの仕様から複数変更へ展開される | PRや実装タスクへ直接対応しやすい |
| AIへの入力 | 仕様書、設計情報 | 実行可能なIssue |
| 完了判断 | 仕様との一致 | Acceptance Criteriaの充足 |

両者を組み合わせると、次のような階層になる。

```text
Goal
  ↓
Spec
  ↓
Issue #101
Issue #102
Issue #103
  ↓
各Issueを実装
  ↓
Pull Request
```

Specが「何を実現したいか」を保持し、Issueが「そのために次に何を変更するか」を保持する。

## AIエージェントとの相性

AIコーディングエージェントでは、Issueを実行単位として扱うと、エージェントへ渡す仕事の境界を明確にしやすい。

```text
Issue取得
   ↓
コードベース調査
   ↓
実装計画
   ↓
実装
   ↓
テスト
   ↓
Pull Request作成
   ↓
レビュー対応
   ↓
CI確認
   ↓
merge
```

この構造にすると、人間が毎回チャットで細かく作業指示を与えるのではなく、Issueを書いた時点で仕事を渡せる。

人間とAIの役割分担も整理しやすい。

```text
人間
  ↓
目的・制約・完了条件をIssueへ記述
  ↓
AI Agent
  ↓
調査・実装・検証
  ↓
Pull Request
  ↓
人間 / CI
  ↓
レビュー・承認
```

Issueが十分に記述されていれば、AIエージェントはIssue単位で比較的独立して作業できる。

反対に、Issueが単なるメモのままであれば、エージェントは不足している前提を推測する必要があり、作業品質が不安定になる。

## チケット駆動開発からの変化

従来のチケット駆動開発では、チケットは主として人間の作業を管理し、変更履歴を追跡するために使われていた。

AIエージェントを組み合わせると、Issueは次のように役割を広げられる。

```text
従来

Issue
  ↓
人間が読む
  ↓
人間が考える
  ↓
人間が実装する
```

```text
AIエージェントを利用する場合

Issue
  ↓
Agentが読む
  ↓
Agentが調査・計画する
  ↓
Agentが実装・検証する
  ↓
人間がレビューする
```

この変化によって、Issueは「人間のタスク管理単位」だけではなく、「AIエージェントへ渡せる実行単位」として扱えるようになる。

## Issue駆動開発を成立させるための条件

Issueを書くだけではIssue駆動開発にはならない。

最低限、次の関係を追跡できる必要がある。

```text
なぜ変更したのか
        ↓
Issue

何を変更したのか
        ↓
Commit / Pull Request

正しく変更できたか
        ↓
Test / CI

誰が確認したか
        ↓
Review

変更は完了したか
        ↓
Merge / Issue Close
```

この一連の情報が結び付いていることで、後から変更理由や判断を確認できる。

## 現時点での整理

Issue駆動開発は、完全に新しい開発方法論というより、既存のチケット駆動開発やGitHub Flowを、AIエージェントによる実行へ適した形で再構成したものとして捉えると理解しやすい。

特にAIエージェントを利用する開発では、次の構造が扱いやすい。

```text
Goal
  ↓
Spec
  ↓
Issue
  ↓
Agent Execution
  ↓
Pull Request
  ↓
CI / Review
  ↓
Merge
```

この構造では、仕様と実装の間にIssueという実行可能な単位が置かれる。

その結果、人間は目的、制約、受け入れ条件を定義し、AIエージェントはIssueを単位として調査、実装、検証を進める、という責務分担を作れる。

今後AIエージェントによる開発方法を整理する場合は、**「Issueをタスク管理から作業契約へ変える」**という視点が一つの軸になる。
