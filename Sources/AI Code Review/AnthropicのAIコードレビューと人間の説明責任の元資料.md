# AnthropicのAIコードレビューと人間の判断・説明責任

- **作成日**：2026年10月21日
- **主な調査対象**：Anthropic「How the Claude Code team does code review」（2026年10月15日）
- **対象領域**：AIエージェントによるソフトウェア開発、コードレビュー、品質保証、ハーネス、説明責任
- **資料の位置付け**：公式情報の調査と、この会話で行った業務開発への考察を統合したナレッジ
- **対象外**：今後の実装計画、作業の優先順位、ToDo、サイト構築のロードマップ

> **読み方**：本文では、Anthropicが公表している内容を「**公式情報**」、そこから推論できることを「**解釈**」、今回の会話で形成した業務開発向けの考え方を「**検討結果**」として区別する。具体例や提案の表は、明記がない限りAnthropicの社内標準ではない。

## 概要

Anthropicは、Claudeが大量のコードを生成する状況に対応するため、人間による逐行レビューへの依存を減らし、PR作成前の実行可能な検証、複数のAIエージェントによるレビュー、セキュリティチェック、CI、リスクに応じた人間の承認、段階的リリース、ロールバックを組み合わせている。[R1]

今回の議論で焦点となったのは、「AIが先に高度なレビューを行うなら、その後の人間はAIより高いコードレビュー能力を持たなければならないのか」と、「AIが大量の実装を担う環境で、担当者は何を根拠に説明責任を果たすのか」という二つの問いである。

**到達した理解**：人間の役割は、AIと同じ観点で全行を再検査することだけではない。変更の必要性、リスク、設計方針、検証の十分性、採用判断を扱う。ただし、人間が対象を理解せず形式的に承認するだけでは品質保証にならない。検証の証拠、判断理由、責任主体を追跡できることと、必要な技術的理解を得られることの両方が必要である。

## 調査のきっかけ・目的

起点はAnthropicのコードレビュー運用に関する記事 [R1]。AIコーディングが完全ではないという前提で、機械的な検証とAIレビューを先行させ、人間の認知的負担を増やさずに品質を確保する方法を検討した。

議論は次の問題へ広がった。

- AIがシニアエンジニア以上にレビューできる場合、ジュニアエンジニアの人間レビューには何が残るのか。
- 業務システムにおける「人間がループに残る」判断を、要件定義、基本設計、レビュー、顧客調整のどこに置くのか。
- AI開発の速度が上がり、コード全体を人間が把握できなくても、変更の説明責任を維持できるのか。
- ハーネスをブラックボックスとして利用させず、利用者がその能力や限界を理解するにはどのような検証の考え方が有効か。
- 実装コストの低下によって、試作後に採否を決める開発方式にどのような価値が生まれるのか。

## 結論・重要ポイント

1. **AnthropicはAI生成コードの完全性を前提にしていない。** 不具合をすべてマージ前に発見するのではなく、複数の検査層と、本番での検知・復旧を組み合わせる。[R1][R2]
2. **すべてのPRに独立した人間のレビュアーが必要なわけではない。** 低リスクでは自動検査のみでマージできる場合があり、中リスクでは信頼された変更指示者自身を承認者に数えられる。[R1]
3. **人間の強みを、AIより優れたバグ検出能力と同一視しない。** 目的、事業上の優先順位、組織固有の情報、リスク受容、設計方針、検証の抜け漏れへの判断を別に考える。[R1] ただし、人間に必要な専門能力の問題は残る。
4. **検査が成功した事実と、検査範囲が十分であることは別である。** Lintやテストは、定義した条件の判定には再現性があるが、仕様の妥当性や未定義の条件まで保証しない。
5. **説明責任は少なくとも三層に分かれる。** 変更と承認を追跡できること、なぜ採用したかを説明できること、問題発生時に調査・是正できること。Anthropicの監査ログは一つ目に強いが、それだけで残りが満たされるわけではない。[R2]
6. **小さな変更と意図の記録には意味がある。** 変更理由、対象、検証証拠をGitやPRに関連付ければ、理解・監査・復旧を支えられる。[R3][R5]
7. **ハーネスの信頼は、内部を完全に理解したかではなく、能力と限界を観測したかでも評価できる。** A/B比較による体験と、正解付き課題での反復評価は区別する必要がある。[R4]
8. **AIによる試作コストの低下は、実物を見て採否を決める余地を広げる。** ただし、予算、データ取扱い、採用権限、評価基準の合意まで不要になるわけではない。[R1][R2]

## 1. Anthropicの取り組みと背景

### コード量増加と人間の時間

**公式情報**：2026年10月15日の記事によれば、Anthropicのモノレポに取り込まれる変更は2026年5月の1日約2,500件から9月の30,000件超へ増加した。Claude Codeはそのモノレポとは別リポジトリであり、Claude Codeのマージ済みPRは6月から9月にかけて2倍超となり、差し戻しが必要になったPRの割合は40%超減少した。[R1]

Anthropicは、コードレビューに二つの役割があると整理している。

1. 問題を出荷前に発見して修正すること。
2. チームでコードベースの理解を共有すること。

前者は機械化が進み、後者の実現方法はまだ十分に制度化されていない。[R1]

人間のコストは「レビューを読む時間」だけではない。誤った変更によって障害が起き、修正に時間を使うことも人間のコストである。そのためAnthropicは、人間の承認数、コメント数、待機時間などを減らしながら、差し戻し率と障害率を悪化させないことを重視している。[R1]

> **数値の注意**：PRの差し戻し減少はAnthropicが報告した結果であり、どの検査がどの程度の改善を直接生んだかを単独で証明するものではない。「実質的な指摘があるPRが16%から54%に増加した」という値も、レビューの精度・再現率そのものではない。[R1]

### 製品としてのCode Reviewと社内運用の違い

**公式情報**：2026年10月15日に、Code Reviewは研究プレビューを終え、Claude TeamとEnterprise向けに一般提供（GA）された。GitHub Appを介したPRレビューが中心で、リポジトリ単位でQuick / Standard / Deepの深度を選べる。多くのレビューは約6〜10分で完了するとされる。[R1][R7]

一方、Anthropic**社内**では、リスクに応じて自動チェックだけでマージ可能な変更も存在する。これは、外部向けCode Review製品が人間の承認を代行するという意味ではない。製品が投稿するのはレビュー結果であり、求められている人間の承認枠をAIの承認で埋めることはできない。[R1]

## 2. 実際のコードレビューの流れ

**公式情報**：原文では「6つの層と、その下支えとなるロールバック」の構造が説明されている。[R1]

| 段階 | 内容 | 主に検出・軽減する問題 |
| --- | --- | --- |
| 1. PR作成前 | テスト、ビルド、スクリーンショット、E2E検証、新しい文脈のサブエージェントレビュー、内部スキル | 基本的な実装ミス、動作・設計との不一致 |
| 2. PRでのAIレビュー | PRの目的とコードベース全体を踏まえた複数エージェントによる検査 | バグ、根本原因の未解決、他領域への影響 |
| 3. セキュリティレビュー | 独立した自動セキュリティレビュー、指摘が残る場合のマージ制限 | セキュリティ上の欠陥 |
| 4. CIの自動チェック | Lint、型チェック、各環境のテスト、ビルド | 定義済みルール違反、回帰、ビルド不成立 |
| 5. リスク別の人間承認 | 変更内容に応じて必要な承認者を変更 | 高リスクな影響、目的・方針に関する判断 |
| 6. マージと段階的リリース | マージキューで再検証、Feature Flag、社内先行利用、段階展開 | 変更間の競合、リリース影響の限定 |
| 補完：検知とロールバック | テレメトリー、オンコール、Feature Flagの無効化、差し戻し | マージ前に見逃された障害への対応 |

**認識が修正された点**：「すべての機械的な検証をCI/CDで終えたものだけがPRになる」という理解は正確ではない。PR作成前にも検証するが、AIレビュー・セキュリティレビュー・CIはPR作成後にも行われ、マージ前のゲートになる。[R1]

### ルールを繰り返し適用する仕組み

**公式情報**：Anthropicは、`CLAUDE.md`にプロジェクトの技術・規約・目的・非目的を置き、`REVIEW.md`にはコードオーナーがその領域特有の障害パターン、確認すべき事項、証拠の出し方などを記述する。繰り返し指摘される問題は、Lintルール、スキル、指示ファイルに反映する。[R1]

ここでの「スキル」は、エージェントが特定の作業を行うための再利用可能な知識や手順であり、静的解析器そのものとは異なる。決定的なルールで検出できる問題は、AIの推論だけに頼るより、Lintや自動テストに落とす方が適する場合がある。

### 複数AIによるレビューにも限界がある

**公式情報**：複数のエージェントが並行してバグを探し、別のエージェント群が指摘の妥当性を検証し、一定の合意に達したものを投稿する。スタイルだけの指摘を削るなど、ノイズを減らす工夫も行う。[R1]

しかしAIが実装し、AIがレビューし、その指摘をAIが修正すると、終わらないループが発生する。Anthropicでは50回超のレビュー・修正が繰り返されたPRがあり、繰り返し指摘されたコードの約59%は初回レビュー時点から存在していた。そこで、3ラウンドを超えたら実装方針を再検討させる、再レビュー範囲を新しい差分へ絞る、既出指摘を繰り返さない、といった方法を採った。[R1]

「多くレビューするほどよい」という単純な評価にはならない。検出できた不具合だけでなく、誤検出、レビューが収束するまでの回数、障害の実績も重要になる。

**公式情報**：実際に障害を引き起こしたPRと修正・差し戻しを評価セット（eval）に追加し、当該コードを知るエンジニアが問題を確認した上で、レビューエージェントを毎日そのセットで再評価している。正常と分かっているPRにもレビューを実行し、無害なコードに対して不適切な修正を促す指摘を数えるなど、誤検出の害も観察する。[R1]

## 3. リスクに応じた人間の承認

**公式情報**：AnthropicのClaude Code開発リポジトリで示された分類は次のとおり。[R1]

| リスク | 例 | 必要な人間の承認 |
| --- | --- | --- |
| 低 | ドキュメント、文言、社内向け機能、Feature Flagで保護された追加変更 | 0人の場合がある。自動レビューとセキュリティチェックの成功が前提 |
| 中 | 通常の製品変更、キャッシュ、アップデーター、システムプロンプトなど | 1人 |
| 高 | 特に重大なコード、あらかじめ指定された高リスクのパス | 2人 |

ただし、この表の人数だけでは運用を説明しきれない。変更内容からリスク階層を選ぶ分類器があり、追加の人間が必要かを別の分類器でも判断する。指定された機密・重要パスやCIワークフローの変更では人間の承認が必要となる。軽い承認経路は信頼された作成者に限定される。エージェントへ指示した人間が必要承認者の1人として数えられる場合があるが、AI自身の承認は人数にカウントされない。承認対象コミットが更新された場合は、再承認が求められる場合がある。[R1]

**解釈**：Anthropicの設計は「AIレビューを人間が毎回必ず上書きする」制度ではない。自動検査でよい変更と人間の判断が必要な変更を分けている。ただし、「リスクが低い」と分類された事実そのものも誤り得るため、分類の精度と変更の影響範囲の管理が重要になる。

**公表された限界**：差し戻し率や障害率が悪化したら承認を自動的に厳格化する「サーキットブレーカー」は、記事時点ではまだ実装していないとAnthropicが認めている。[R1]

## 4. Where humans stay in the loop：人間に残る5つの判断

**公式情報**：Anthropicが明示する役割は、次の5つである。[R1]

| 人間が判断する事項 | 内容 | 業務開発への対応付け（検討結果） |
| --- | --- | --- |
| 1. そもそも作るべきか | 方向性、品質感、スコープ、既存方針との整合性 | 要件定義・基本設計・意思決定が中心。ただし試作後にも採否を見直せる |
| 2. 高リスク変更を許容できるか | 課金、アップデーター、CIなど影響の大きい変更の吟味 | 社内のリスク受容権限に加え、必要に応じて顧客との調整・合意 |
| 3. アーキテクチャは適切か | 後続開発が模倣する設計パターンの妥当性 | 基本設計や技術設計を中心に、実装中の設計変更でも判断 |
| 4. 検証結果を信用できるか | テスト実行内容、ログ、スクリーンショット、レビュー指摘と見逃し得る範囲を理解する | 実装後の受け入れ・レビュー判断の中心 |
| 5. 結果の責任を誰が持つか | 誰が変更の結果を引き受けるか | 担当者の技術的説明、承認権限、チームや組織の障害対応責任を整理 |

**検討結果**：前半3つは基本設計以前の判断と重なる部分が大きい。ただし、AIによって試作が安くなった場合、実際に作って比較した後で「採用しない」「別の方式へ戻す」という判断も合理的になる。原文でも、既存の意思決定やもっと単純な解決策を踏まえて、PRを閉じたり形を変えたりする例が挙げられる。[R1]

### 「AIより優れた人間」でないとレビューできないのか

**最初の疑問**：十分に優秀なAIが実装とレビューを済ませているなら、その後でジュニアエンジニアが同じコードにバグを見つける余地は小さいのではないか。Anthropicの社員が全員AIより優れていることを前提としているのか。

**確認できた事実**：Anthropicは、全社員がAIより高度なコードレビュー能力を持つことを前提にするとは述べていない。人間には目的・リスク・設計・証拠・結果に関する判断を求めている。低リスクでは人間のレビューが不要な場合もある。[R1]

**解釈**：人間とAIがまったく同じ入力を使って同じバグ検出を繰り返すなら、人間の追加価値は小さくなり得る。一方、人間がAIに渡されていない顧客事情、過去の決定、運用上の制約を知っていれば、コード上の誤りとは別の問題を指摘できる。例として、技術的には正常に実装された機能でも、事前の顧客合意で提供しないと決まっているなら採用してはいけない。

その不足情報を`CLAUDE.md`、スキル、組織のナレッジやレビュー条件に組み込めば、次回以降はAIが検出できる範囲が広がる。Anthropicも、見逃しの原因となった欠落情報を指示や検査に反映している。[R1][R2]

**残る限界**：人間がレビューすべき高リスクの技術判断については、その担当者に十分な技術能力が必要となる。形式上の承認人数を満たしても、判断できなければ安全性は増えない。Anthropicの公開記事だけでは、承認者の能力をどのように保証しているかまでは確認できない。

### 検証成功と検証の十分性

**検討結果**：レビューを次の3段階に区別すると、担当者の仕事が明確になる。

1. **検証の実行**：Lint、型チェック、単体・統合・E2Eテスト、AIレビュー、セキュリティ検査などを動かし、結果を得る。
2. **検証の十分性**：そもそも必要な仕様やリスクを検証しているか、見逃し得る条件を説明できるかを判断する。
3. **残余リスクの受容**：未確認部分や復旧手段を踏まえ、その変更を採用してよいか判断する。

プログラマティックな検証は、**書かれたルールやテスト条件を正しく評価する範囲で**再現性が高い。しかし、存在しないテストケース、誤った期待値、仕様の取り違えまでは自動的に解決しない。Anthropic自身も、検査が何を見逃すか説明できないなら安易に承認しないよう求めている。[R1]

## 5. 説明責任をどう捉えるか

### 結論：コードをすべて説明できることと、採用の責任は異なる

**会話での問題意識**：従来は担当者がソースコードに責任を持ち、プロジェクトリーダーがプロジェクト全体を管理することが多い。AIが実装を広く担うと、1人の技術者が担当者とプロジェクトリーダーに近い役割を兼ねる可能性がある。しかし、大量のAI生成コードの各行を理解する従来型の方法だけでは、説明責任を果たすことが難しくなる。

**検討結果**：説明責任を少なくとも次の三層に分ける。

| 層 | 後から答えられるべき問い | 支える証拠 |
| --- | --- | --- |
| **追跡可能性・監査可能性** | 何を変更し、何を検証し、誰がいつ承認したか | コミット、変更要求ID、CIログ、AIレビュー履歴、承認ログ |
| **採用判断の説明可能性** | なぜこの実装を選び、何をリスクとして受容したか | 要件、設計判断、代替案、検査範囲、未確認事項、承認理由 |
| **結果への責任・是正可能性** | 障害時に誰が調査し、是正し、顧客へ説明するか | 担当・権限の定義、運用体制、ロールバック、インシデント記録 |

AIが作成した説明文を人間が読んだだけでは、内容が正しいとは限らない。ログやテストの実行結果、対象コミットなどに照らして確認できる必要がある。他方、すべての変更説明を人間がゼロから手書きすることも必須ではない。**AIが記録の下書きを作り、人間がリスクに応じて検証・修正する**という役割分担が考えられる。

**注意**：個々の担当者が実質的に広い開発領域を管理できることと、契約上・組織上のプロジェクト責任者になることは同一ではない。顧客に対する約束や承認権限は、組織の役割定義に従う。

### Anthropicが実際に残している監査情報

**公式情報**：AnthropicのDeputy CISOが2026年7月21日に公開したセキュリティ記事は、社内のAI-native SDLCに関して、以下の実践を説明している。[R2]

- 自動承認も含め、承認判断の根拠となったシグナルや理由を記録する。
- 自動承認の一部をリスクに応じて人間が抜き取り確認する。
- 新しいAIレビュアーはShadow Modeで人間の確認を受け、信頼性を確かめる。
- 自動承認、ツール呼び出し、エージェント間メッセージなどをSIEMへ記録し、事後の追跡を可能にする。
- ダッシュボードと再検証により、レビューループ自体の品質を監視する。

これは「なぜその自動判断が行われたかを監査できる」ことへの具体策である。一方、「担当者が顧客仕様を理解していること」「障害時に組織が適切に説明できること」を直接保証する仕組みとは異なる。

### 変更理由・証拠の管理方法

**検討結果**：変更の粒度を小さくし、変更理由と検査の証拠を紐づける。必ずしも5W1Hのすべてをコミット本文に記載する必要はない。

| 記録先 | 主な情報 |
| --- | --- |
| チケット・要件／`intent.md` | なぜ変更が必要か、利用者、制約、期待する結果 |
| `spec.md`、`plan.md`など | 要件、設計、変更対象、代替案、検証計画 |
| Gitコミット | この単位で何を変更したか、なぜ変更したか、参照する要求ID |
| PR | 影響範囲、テスト、リスク、未確認事項、復旧方法 |
| CI・AIレビュー | 実際の検査条件、実行ログ、結果、指摘とその処理 |
| 承認履歴 | 対象コミット、承認者、採用根拠、必要な追加判断 |

具体的なコミットメッセージの例（**今回の議論から作った例であり、Anthropicの指定形式ではない**）：

```text
fix: 再送時の注文二重登録を防止

Why:
  API再送時に同一注文が重複作成される可能性がある

Change:
  登録前にリクエストIDによる重複チェックを追加

Scope:
  注文登録処理のみ。決済処理は変更しない

Refs:
  REQ-142
```

**公式情報との接点**：Anthropicの長時間稼働エージェント研究では、小さな機能単位で進め、説明的なGitコミットと進捗ファイルを残すことで、次のエージェントへの引継ぎや変更の巻き戻しをしやすくしている。[R3] また、同社が公開するAI-native SDLCの教材は、`intent.md`、`spec.md`、`plan.md`をGit等で管理し、実装と検証を結び付ける方式を提案している。[R5][R6]

ただし、この教材に登場する文書名や工程は**推奨パターン**であり、Anthropicのすべての社内開発チームが同一形式を採用していると断定できない。

### 変更のリスクと記録・承認の負担

**検討結果**：記録と説明の作成方法も、レビューと同じくリスクに応じて変える考え方が成立する。

| 変更リスク | 記録の作成 | 人間の関与 | 要求する説明の深さ |
| --- | --- | --- | --- |
| 低 | AIが自動作成し証拠を紐づける | 抜き取り監査や例外時の確認 | 変更目的、差分、検査結果を追跡できる |
| 中 | AI下書きを人間が確認・修正 | 検証の十分性と残余リスクを確認 | 主な設計判断、影響、未確認領域を説明できる |
| 高 | AIの補助は使うが明示的な責任者判断を残す | 関係者・専門家・必要に応じ顧客の合意 | 代替案、リスク受容理由、復旧策まで説明できる |

これは**業務開発に関する会話内の提案**であり、Anthropicの正式な承認基準ではない。AIによるリスクの自己申告だけを分類根拠にせず、対象システム、データ、顧客影響、復旧可能性なども考慮する必要がある。

## 6. ハーネスの理解とA/B比較という論点

### ブラックボックス化の問題

**会話で明らかになった状況**：レビューや実装の機能をハーネスとして自動化できても、利用する社員が「どんな手順が実行され、何が改善され、どこまで信頼できるか」を理解しているとは限らない。ハーネスそのものの学習に負担があり、完成物だけを受け取ると、利用者の理解と委任の根拠が失われやすい。

**検討した考え方**：コードレビュー、実装、テスト生成など個々の能力を切り出し、同じ課題に対する通常のAI実行とハーネス適用後の出力を比較できれば、利用者は内部全体を学ばなくても、特定の機能の効果と限界を具体的に確認できる。これを繰り返して得た理解は、ハーネスにタスクを委任する際の判断材料になる。

ただし「数回試して信頼できた」という**主観的な納得**と、検出性能や安全性についての**客観的な評価**は区別する。

### エージェント用ハーネスと評価用ハーネス

**公式情報**：Anthropicの評価方法に関する記事は、二つを分けて定義している。[R4]

- **エージェント用ハーネス（agent harness）**：モデルに指示やツールを与え、実行を調整し、結果を返す実行環境。スキルや検証フローを組み込める。
- **評価用ハーネス（evaluation harness）**：定義した課題を実行し、手順を記録し、結果を採点・集約する評価基盤。

**検討結果**：ハーネスの能力を比較するときは、入力と課題を揃え、変更する条件（たとえばスキルの有無やレビュー手順）を明確にし、モデルとハーネスのバージョン、検出した不具合、誤検出、見逃し、時間、コスト、実行ログを記録する。同じ課題でも出力が変動するため、単一実行より複数試行が適する。[R4]

比較は、利用者が「何が違うか」を学ぶ用途と、既知の不具合・正解付き課題で「どれだけ正しくできるか」を測る用途に分けて考えると混乱しにくい。AIがつくった解説は理解の助けになるが、その説明が正しいことを自動的に保証するわけではない。

この構想は**今回共有した設計上の視点**として記録する。サイトの制作計画、機能の優先順位、実施手順は本書の対象外である。

## 7. AIで試作し、比較してから採否を決める開発方式

**公式情報**：Anthropicは、エージェントによって着手と試作のコストが低下したため、PRを閉じたり別の方針へ変更したりしても、従来ほど損失と感じなくなったと述べている。[R1] またセキュリティ記事では、短い時間で複数の大きな試作を作れるようになり、長い計画工程の前にすべてを精緻化する必要性が変化していると説明する。[R2]

**検討結果**：従来の業務開発では、着手後の作り直しが高価だったため、実装前に方式や範囲を合意しておくことの意味が大きかった。AIで試作コストが下がると、実物を比較した上で、顧客の要望に近い案を選ぶ判断が取りやすくなる。実装してみて初めて明らかになる制約や使い勝手を、採用判断に反映できることは品質面の利点になり得る。

一方、**すべての事前合意が不要になるわけではない**。試作対象、利用データ、期間・予算の上限、品質や採用の判定基準、最終的な決定権限は引き続き重要である。とくに契約上の影響がある変更では、後から「採用しない」で済まない場合もある。

したがって、今回の理解は「上流工程を廃止する」ことではない。詳細な解決手段を最初から固定する必要性が低下し、**実装・比較を意思決定の一部として使える場合が増える**という変化である。

## 8. 事実と解釈を混同しやすい点

| 誤解しやすい理解 | 整理した理解 |
| --- | --- |
| CIを完全に通過したものだけがPRになる | PR前の検証に加え、PR後のAIレビュー・CI・マージ時の再検証がある。[R1] |
| AnthropicではすべてのPRを人間がレビューする | 低リスクでは0人承認の運用がある。必要な人間承認はAIで代替しない。[R1] |
| AIレビュー後の人間にはAI以上のバグ検出能力が必須 | 人間が担う目的・リスク・証拠・責任の判断は別軸。ただし高度な技術判断には相応の専門性が必要。[R1] |
| LintやテストがGreenなら品質を保証できる | 定義した検査は通過したが、仕様の妥当性や未検査領域までは保証しない。 |
| AIが説明を書けば説明責任は解決する | 説明の正確性、実行証拠、採用判断、責任体制が別に必要。 |
| 監査ログがあれば担当者は理解しなくてよい | 追跡できることと、妥当性を説明・判断できることは違う。 |
| 1人でAI開発できればその人が自動的に全責任者となる | 技術的な担当範囲と、組織・契約上の責任や権限は別に定義される。 |
| A/B比較で数回よい結果を見れば品質は証明できる | 主観的な納得と、反復可能な評価セットでの測定は別である。[R4] |
| AIで試作が安くなれば上流の合意は不要 | 実装方式を柔軟にできるが、評価基準、予算、権限、顧客の制約は必要。 |
| `intent.md`等はAnthropic社内の必須ファイル名 | 公式教材の推奨構成であり、全社標準として一律に運用されているとは確認できない。[R5][R6] |

## 9. 未解決事項と公開情報の限界

以下は現時点の**未解決の問い**であり、実施計画ではない。

- **承認者の専門能力**：Anthropicは人間のレビュー能力をどう評価・担保しているのか。公開記事には詳しい説明がない。
- **検証の十分性の判定**：高度なAIのレビュー結果に対して、人間が独立に妥当性を評価できない場合、どの基準で受け入れるのか。第三者的なテストや本番の観測は一部の補完策になるが、完全な答えではない。
- **コード理解の共有**：人間が毎行読まなくなったとき、システム全体の理解、教育、将来の保守能力をどこまで維持できるのか。Anthropicも正式な仕組みは未確立としている。[R1]
- **責任の所在**：AIを指示した担当者の責任、技術的承認者の責任、組織や契約上の責任をどのように結びつけるかは、利用組織ごとに異なる。
- **AI作成の証拠の信頼性**：AIの説明、テスト結果要約、リスク判定をどの程度独立した証拠で検証できるか。
- **リスク分類の誤り**：低リスクとされた変更が実際には大きな影響を持つ場合の検出と回復をどう保証するか。
- **ハーネスへの信頼の一般化**：限られた課題での評価結果が、未知の課題や環境変更後にもどこまで通用するか。[R4]
