# Treg Web AccessとSEO改善AIエージェント：調査・検討ナレッジ

- 作成日：2026年10月19日
- 調査起点：https://treg.to/web-access
- 対象：Treg Web Access、Webデータ取得、SEO改善エージェントの情報源拡張
- 情報区分：**確認事項**＝公式公開資料等に基づく内容、**検討結果**＝本会話での設計判断、**要確認**＝現時点で検証不足

## 概要

Treg Web Accessは、AIエージェント向けにWeb検索・ページ本文抽出・構造化抽出・サイト内URL探索・ニュース検索・SNSやEC等のプラットフォーム別データ取得を提供する統合アクセス手段。複数の外部データプロバイダーを使い分け、取得失敗時には別のプロバイダーへのフォールバックが可能である。

本会話では、通常のWeb検索との違いを整理したうえで、**SEO改善を閉ループで運用するAIエージェントが参照するWebページに偏りがある**という実際の課題に対し、TregやGoogle公式APIをどう組み合わせるかを検討した。

## 調査のきっかけ・目的

1. Tregはスクレイピングなのか、ローカル実行だから無料なのかを確認する。
2. 通常のWebサーチと比べて何が追加でできるのかを把握する。
3. SEO改善エージェントで、参照するページや情報源が偏る問題に有効か検討する。
4. PageSpeed Insights、Search Console、Google Trends等のデータも利用できる構成を考える。

ユーザーはSEO改善の実行環境や閉ループ運用の準備を自分で行う方針であり、今回の焦点は**エージェントの情報取得・調査品質の向上**にある。

## 結論・重要ポイント

- **確認事項：** TregはローカルでWebページをスクレイピングするソフトではなく、外部プロバイダーを呼び分けるWebデータ取得ゲートウェイである。CLIやSkillはローカルのエージェントから利用できるが、実際の取得処理は通常外部サービスで行われる。
- **確認事項：** 無料経路としてTinyFishによる検索・ページ取得が案内されている。ただし取得失敗時の有料プロバイダーへのフォールバック、プラットフォーム別データ取得等は課金の可能性がある。
- **確認事項：** 通常のWeb検索と機能が重複するが、TregはURL本文の抽出、サイトマップ、構造化抽出、プラットフォーム別API、プロバイダー切替を統合する点に特徴がある。
- **検討結果：** SEO用途ではTregを**外部Web・競合情報の取得層**とし、Google Search ConsoleとPageSpeed Insightsなどの**公式APIを実測・診断データ層**として別に接続する構成が有望。
- **検討結果：** 情報源の偏りはツール導入だけでは解消しない。調査対象の多様性、取得成功の検証、出典・証拠の記録、失敗時の停止条件を設計する必要がある。
- **要確認：** Tregの現行カタログにある個々のSEOデータプロバイダー、Google系APIの対応状況、料金、認証方式は実導入前に再確認する。

## 技術・サービスの概要

提供主体はSuperdesign。公式Webページの実装ソースと、GitHub上のWeb Access Skill仕様を調査した。TregのコマンドやAPIを通じて、エージェントがタスクに合うWebデータ取得ジョブを呼び出す。

概念的な処理経路：

```text
AIエージェント（ローカルまたはクラウド）
  ↓ Treg CLI / API
Tregのルーティング
  ├─ TinyFish：無料優先の検索・ページ取得
  ├─ Crawl4AI / AnyAPI等：取得失敗時の候補
  └─ その他の専用プロバイダー：ニュース・SNS・EC・SEO関連等
  ↓
本文・URL一覧・構造化データ・プロバイダー履歴・費用情報
  ↓
AIエージェントによる分析・判断
```

TregはAIの回答生成エンジンではなく、主として**データ取得のためのツール群とルーティング層**である。検索結果の信頼性評価、引用、SEO改善案の妥当性判断は利用側で実装する。

## 主な機能と利用例

| 機能 | 代表的なジョブ | SEO用途での例 |
|---|---|---|
| Web検索 | `treg.web.search` | 競合・関連トピックを探索 |
| URL本文取得 | `treg.web.extract` | 競合記事の本文・見出しを確認 |
| 構造化抽出 | `treg.web.extract.structured` | タイトル、見出し、FAQ等をフィールド化 |
| サイトマップ・URL探索 | `treg.web.map` | 競合サイトの関連ページを発見 |
| ニュース検索 | `treg.web.search.news` | 新しい情報や公開日を伴う話題を確認 |
| プラットフォーム別データ | カタログで検索 | SNS、EC、レビュー、地図、SEO専門データ等 |

公式Skillは、URLが分かっていればURLを読む、対象ページを探すなら検索して複数ページを読む、サイト全体ならマップから必要ページを絞る、最新ニュースならニュース検索を使う、という使い分けを推奨している。

## 通常のWeb検索との違い

| 観点 | 一般的なAIのWeb検索 | Treg Web Access |
|---|---|---|
| 検索 | 可能 | 可能 |
| URL本文の直接取得 | ツールにより可能・不可が異なる | 専用ジョブを提供 |
| サイト内URL探索 | 専用機能がない場合もある | サイトマップ取得ジョブ |
| 指定スキーマでの抽出 | AIが後処理することが多い | 構造化抽出ジョブ |
| SNS・EC等の専用データ | 一般Web検索では制約が多い | 専用プロバイダーを利用可能な場合がある |
| 取得失敗への対応 | ツールの仕様に依存 | ルーティングによるフォールバック |
| 出典評価・推論・回答生成 | AI側の能力 | Treg自体の主機能ではない |

**注意：** 「Web検索ではページ本文を絶対に取得できない」「Tregならどんなサイトも必ず取得できる」といった理解は誤り。既存検索ツールの能力とサイト側の制限によって結果は変わる。

## 料金・実行場所・フォールバック

### ローカルだから無料なのか

**いいえ。** ローカル側で動くのはCLIやエージェントであり、Webデータ取得は通常外部プロバイダーが実施する。無料なのは、Tregが提供する無料優先の利用経路によるもの。

公式Skillに示された例：

```bash
npx skills add superdesigndev/treg --skill web-access

treg call treg.web.search --data '{"q":"example query"}' --header 'X-Treg-Route-Prefer: tinyfish'
treg call treg.web.extract --data '{"url":"https://example.com"}' --header 'X-Treg-Route-Prefer: tinyfish'
```

実際の利用にはTreg CLIのセットアップと認証が必要。最新手順は公式ドキュメントを参照。

### 費用制御

- `X-Treg-Route-Prefer`：優先プロバイダーの指定。
- `X-Treg-Route-Exclude`：除外プロバイダーの指定。
- `X-Treg-Route-Max-Cost`：ルーティング呼び出しの費用上限を設定。
- `X-Treg-Route-Waterfall: 0`：失敗時の連鎖的な切替を抑制。
- 公式Skillには、上限未指定の場合に失敗をたどるフォールバックで最大 **1米ドル** に達し得る旨の注意がある。これは常に1ドルかかるという意味ではない。
- TinyFishの直接ジョブ `tinyfish.web.fetch` には複数URL取得の例があるが、直接プロバイダー呼び出しにはTregの自動フォールバックがない。
- プラットフォーム別ジョブや有料プロバイダーの価格は変動し得る。呼び出し前にカタログで確認する。

## SEO改善エージェントへの適用

### 実際に問題になっていること

ユーザーの観察では、SEO改善をAIに閉ループで任せる際、**AIが参考にしているWebページに偏りがある**。検索ツールを使っていても、同種のページや検索上位の一部だけを参照し、必要な情報を十分に取得していない可能性がある。

この観察はユーザーの実運用上の課題であり、Tregの導入によって改善するかは未検証。

### Tregが効きそうな箇所

1. 検索結果のタイトル・スニペットで止まらず、URL本文の取得を明示的に実施する。
2. 競合サイト内の関連ページを探索し、単一ページ依存を減らす。
3. 特定プロバイダーで取得失敗した場合に別の取得手段を試す。
4. SNS・レビュー・EC・SEO専門API等、通常検索だけでは拾いにくい情報源を追加する。
5. 取得結果を構造化し、競合ページ間の比較に使う。

### Tregだけでは解決しない箇所

- 同じキーワードや同じサイトばかり検索するエージェントの行動パターン。
- 取得したページの品質・権威性・新しさ・独立性の評価。
- Search Consoleの自サイト固有データ取得に必要な認証と権限。
- PageSpeed Insights等の公式診断値を正しく扱うこと。
- 改善施策の実装、検証、効果測定、ロールバック。

## Google系データソースとの組み合わせ

「GoogleInsights」は文脈上、PageSpeed Insights等を指す可能性があるが、正式な対象サービスは未確定。Googleの各データソースは用途が異なる。

| データソース | 主な情報 | 推奨取得経路 |
|---|---|---|
| Google Search Console | 自サイトの検索クエリ、表示回数、クリック数、CTR、平均掲載順位など | Search Console公式API（認証が必要） |
| Google PageSpeed Insights | Lighthouseによるページ性能診断、Core Web Vitals関連情報など | PageSpeed Insights公式API |
| Google Trends | キーワードの検索関心度の推移 | 利用可能な公式手段・規約・提供状況を別途確認 |
| Google検索上の競合ページ | 公開記事の本文、見出し、リンク等 | Treg等の公開Webデータ取得手段 |
| SEO専門サービス | バックリンク、競合分析など | 各社API、またはTregカタログに対応ジョブがあれば利用 |

**確認事項：** Tregの公式リポジトリには、SEO関連データ取得プロバイダーをカタログから探す例や、外部APIをTreg経由で利用する構成に関する記述がある。ただし、**Treg Web AccessをインストールしただけでGoogleのすべてのAPIを自動利用できるわけではない**。

**要確認：** 現在のTregカタログでSearch Console、PageSpeed Insights、各SEO専門APIがどの形式で利用可能か。Google Trendsについては、利用可能な取得手段の正当性・規約・安定性を個別に確認する。

## 推奨アーキテクチャ（会話での検討結果）

```text
[Search Console公式API] ─┐
                         ├─> [SEOエージェントの調査・分析層]
[PageSpeed Insights API] ┤       │
                         │       ├─ 情報源の分散を確認
[Treg Web Access] ───────┘       ├─ URL・取得日時・根拠を保存
   ├─ 競合検索                   ├─ 取得失敗を検出
   ├─ 本文取得                   └─ 仮説・施策を立案
   ├─ サイト内URL探索                    │
   └─ SEO関連データ                      ▼
                               [CMS / GitHub等で変更]
                                        │
                                        ▼
                                [一定期間後に再計測]
                                        │
                                        └─> 次の改善サイクル
```

ユーザーはSEO改善実行側の環境を準備する前提なので、Tregの導入目的を**外部情報の取得品質と情報源の多様化**に限定すると、効果を評価しやすい。

### 推奨する調査ガードレール

- 調査前に情報源カテゴリを決める：Google公式資料、競合一次ページ、実測データ、SEO専門データ等。
- 検索結果のURLを集めるだけでなく、対象ページの本文取得成功を確認する。
- 同一ドメインや類似コンテンツへの過度な依存を検知する。
- 根拠ごとにURL、取得日時、取得方法、対象の指標、失敗・欠落を記録する。
- Google公式の実測値と競合記事からの推測を混同しない。
- 必須データが欠ける場合は、AIが断定的な改善判断に進まない。
- 改善前後の比較には期間、対象URL、クエリ、計測条件を揃える。

## 導入検証の進め方（提案）

1. 現行エージェントの調査ログから、実際に本文まで読めたURL、参照ドメイン、検索クエリ、取得失敗率を集計する。
2. 同じSEOタスクを、現行Web検索のみと、Tregの本文取得・サイト探索を追加した構成で比較する。
3. 「ユニークな参照ドメイン数」「実際に取得できた本文数」「根拠の再現性」「取得失敗率」「APIコスト」を評価する。
4. Search ConsoleとPageSpeed Insightsの公式APIを別系統で接続し、公開Web情報との照合を行う。
5. 取得品質が改善してもSEO成果が上がるとは限らないため、最終的には検索パフォーマンスの変化を追う。

これは検証計画の提案であり、Tregの性能優位を実証したものではない。

## セキュリティ・Business / Enterprise利用

- 公開Webデータの取得を主目的とする。ログインセッション、Cookie、本人になりすましたアクセスを前提にしない。
- Tregのホスト型サービスは公式規約でEarly Accessとして説明され、可用性やSLAの保証には注意が必要。
- Tregの説明では、プロキシ側でリクエスト・レスポンス本文を保存しない旨がある一方、呼び出しメタデータ等は記録され得る。また、外部プロバイダーには処理に必要な情報が送信される。
- チーム管理機能やメンバー別の利用制限に関する記載があるが、Enterprise向けの契約、DPA、データ所在地、監査要件への適合は個別確認が必要。
- **ライセンス注意：** GitHubのLICENSEは単純なApache-2.0ではなく、追加条項により第三者向けのホスト型・マネージド型・組み込みサービス提供に制限がある。内部での商用セルフホスト利用と、第三者にサービスとして提供することは区別する。

## 質疑応答から判明したこと

### 1. 「スクレイピングなのか。ローカルだから無料なのか」

Webスクレイピングやデータ抽出を利用する仕組みだが、取得処理をローカル実行することが無料の理由ではない。Tregは外部プロバイダーの無料経路を優先する。

### 2. 「通常のWebサーチと何が違うのか」

検索機能自体は重複する。Tregの追加価値は、URL本文・サイトマップ・構造化情報・専用プラットフォームデータの取得と、プロバイダー間のルーティング。単純な質問回答には通常検索で十分なことが多い。

### 3. 「通常検索で取得できなかった箇所で役立つのか」

取得失敗やスニペット依存の改善には役立つ可能性がある。ただし、エージェントがツールを適切に呼ぶ設計や、取得成功を確認する仕組みが不可欠。

### 4. 「SEOの閉ループで参照Webページが偏る」

本件の中心課題。Tregを追加するだけで偏りがなくなるわけではない。取得先の多様化、情報源の種類ごとの最低要件、証拠ログを組み合わせるべき。

### 5. 「Google Insightsなどからも取得したい」

PageSpeed Insights、Search Console、Trendsはデータの性質が異なる。公開Web取得と公式APIを組み合わせる構成が適切。特にSearch Consoleの自サイトデータは認証が必要。

## 誤解しやすいポイント

- **無料＝ローカル実行ではない。** 外部プロバイダーの無料経路を利用している。
- **無料優先＝必ず無料ではない。** フォールバックや専門ジョブで課金され得る。
- **Treg＝ブラウザー自動操作ではない。** ログイン済みブラウザーの操作やPlaywright/CDPの代替ではない。
- **Treg＝通常検索の完全上位互換ではない。** 検索・読解・引用・判断の品質はエージェントの設計にも依存する。
- **取得先を増やす＝偏りが解消する、ではない。** サンプリング・重複排除・根拠の評価が必要。
- **TregでGoogleの内部SEO指標がすべて取得できるわけではない。** Google公式APIの認証・権限が必要な情報がある。
- **「オープンソース」表記＝無条件のApache 2.0ではない。** 追加ライセンス条項を確認する。

## 未解決事項・今後確認したいこと

1. ユーザーが「GoogleInsights」と呼んでいる対象はPageSpeed Insights、Search Console Insights、あるいは別サービスか。
2. 既存SEOエージェントの検索・URL取得ログで、偏りの主因が検索クエリ、検索エンジン、取得失敗、ページ選定、重複排除のどこにあるか。
3. Tregの現行カタログで利用できるSEO関連ジョブ、プロバイダー別料金、品質、レート制限。
4. Search ConsoleとPageSpeed InsightsをTreg経由にまとめる価値があるか、公式API直接接続のほうが運用しやすいか。
5. Google Trendsの正式なデータ取得経路と利用条件。
6. TregのEnterprise利用要件、SLA、データ処理契約、ライセンス上の許諾範囲。
7. 実際にSEO調査の情報源多様性・取得成功率が改善するかの比較検証。
