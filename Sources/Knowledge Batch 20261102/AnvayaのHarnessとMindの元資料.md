# Anvaya ナレッジ

調べた日：2026-11-02　／　主な情報源：Anvaya公式サイト（https://www.anvayahq.com/）

## 1. 概要

Anvayaは、AIがコードを読み書きして作業を進めるツール（エージェント型コーディングツール）に、プロジェクトでの経験を覚える仕組みを組み合わせたものです。2026年第4四半期に公開ベータを予定しています。

要点は次の3つです。

- 作業するAI本体（Harness）と、経験を保存する記憶（Mind）の2部品でできている
- 記憶は自分のPC内に保存され、ローカルのAIモデルを使えば外部に何も送られない
- 公式サイトは実測値と設計上の見積もりを分けて書いている。中心の主張である「使うほど賢くなる」は、サイト自身が未検証の仮説としている

## 2. 理解に必要な前提

| 用語 | 意味 |
|---|---|
| セッション | AIに作業を頼む1回分のやり取り。終わると、通常は内容を忘れる |
| 読み込む量（トークン） | AIが1回の処理で読む文章の量。多いほど時間と費用がかかる |
| ハーネス（Harness） | AIモデルを包んで、ファイルの読み書きやコマンド実行をさせるプログラム |
| MCP | AIツールが外部の機能を呼び出すための共通規格。Claude Codeなどが対応している |
| Ollama | AIモデルを自分のPCで動かすためのソフト |
| ベータ・ベルヌーイ事後分布 | 「役に立った回数」と「立たなかった回数」から、次に役に立つ確率を見積める統計の方法 |

AIコーディングツールには、セッションが終わると学んだことを忘れる、という弱点があります。公式サイトによると、実際に観測したあるClaude Codeのセッションでは、処理した約859万トークンのうち約9割がファイルの読み直しで、考えることに使われたのは約1割でした。

## 3. 解説

### 3.1 全体の構成

```
あなたの指示
    ↓
[Harness] 作業するAI本体（コードを読み、書き、実行する）
    ↑↓  必要な記憶を受け取り、作業の結果を渡す
[Mind] 経験の保管庫（決定、失敗、修正、パターンなどを保存）
    ↓
プロジェクト内の .anvaya/mind/ に保存（自分のPCの中）
```

HarnessとMindのつなぎ方は3通りで、速さが違います。

| 方式 | 所要時間 | 使う場面 |
|---|---|---|
| 同じプログラム内で直接呼ぶ | 0.5ミリ秒未満 | Anvayaの Harness を使うとき |
| ソケット経由（IPC） | 約2ミリ秒 | 複数のツールで1つの記憶を共有するとき |
| MCP経由 | 約10ミリ秒 | Claude Codeなど、他のツールから使うとき |

MCP経由があるため、Harnessを使わずに、Mindだけを他のツールから借りられます。

### 3.2 Mind：経験の保管庫

Mindは、作業から得た記録を6種類のノードとして保存します。各ノードには「重み」があり、次の作業でどれを渡すかを決める優先度になります。

| 種類 | 内容 | 重みが半分になる日数 |
|---|---|---|
| まとめ | 複数の記録から導いた結論 | 693日 |
| 決定 | なぜその設計にしたか | 347日 |
| パターン | 繰り返し出る書き方や落とし穴 | 139日 |
| 概念 | そのプロジェクト特有の用語や知識 | 87日 |
| 修正 | バグの原因と、効いた直し方 | 46日 |
| 試したやり方 | うまくいかなかったやり方など | 23日 |

この日数は、あらかじめ決めた設定値です。実績から求めたものではありません。

重みは2つの要因で変わります。

- 時間：種類ごとの日数で、重みが減っていく
- 結果：その記録を渡した作業で、実際に使われたかを数えて、ベータ・ベルヌーイ事後分布で更新する

さらに、記録の内容が今のコードと合っているかを、gitの履歴と照らして確かめます（記録ごとに行う、コードとのずれの検出）。合わなくなった記録には印が付きます。

```
作業が終わる → 記録として保存（6種類のどれか）
      ↓
次の作業 → 重みの高い記録だけを、予算内（既定4,096）で渡す
      ↓
使われたか確認 → 重みを更新
      ↓
gitと照合 → 古くなった記録に印
```

保存先は、SQLiteのデータベース、検索用の索引（HNSW）、追記専用の記録ファイルです。どれも自分で開いて読め、削除もできます。

### 3.3 Harness：作業するAI本体

- Rust製で、1つのファイルだけで動く。ほかのソフトは不要
- 道具が21個、画面が8種類。人が操作しない自動実行（CI向け）にも対応
- AIモデルは、Ollama、OpenAI互換、Anthropicの3つから選べる

公式サイトが示す軽さの数字は、次のとおりです（すべてAnvaya自身の計測）。

| 項目 | 値 |
|---|---|
| 待機中のメモリ | 約5MB |
| 起動から最初の画面まで | 約12ミリ秒 |
| 作業中のメモリ（中央値） | 25.6MB（238回の計測） |
| 比較したClaude Codeの待機中メモリ | 432MB（約17倍の差） |
| 同時に動かすAIの数 | 既定24個、上限256個 |
| 32個を動かしたときの合計メモリ | 103MB |

軽さの狙いは、クラウドに頼らず、自分のPC1台で多くのAIに作業を分担させることです。

### 3.4 読み込む量を縮める3段階

AIが読み込む量を縮める方法を3段階に分けて試し、測った結果で採用を決めています。

| 段階 | 方法 | 結果 | 現在の扱い |
|---|---|---|---|
| 小（micro-fold） | 大きな出力の全文はディスクに保存し、AIには冒頭の抜粋と再取得できる場所の情報だけを渡す | キャッシュされない読み込み量が中央値で11.0%減（5回の試行、検証19/19） | 初期設定ではオフ。確認が済むまで昇格させない |
| 中（meso-fold） | 古い出力を、数ラウンドにわたって縮める | 2方式を試し、7.8%増と24.5%増。縮めた内容をAIが読み直したがり、かえって増えた | 採用せず、失敗の記録として保管 |
| 大（macro-fold） | 履歴が上限の80%で、古い部分を要約。95%で、直近5ターン以外の古い本文を捨てる | 確実に動くが、要約で細部が失われる | 初期設定でオン。他の多くのツールも同じ方法 |

出力が極端に大きくならないための歯止めも別にあります。

- 1回のツールの出力は、上限の30%まで
- 超えたときは、先頭だけを残し、再取得の目印を付ける。内容は作り足さない

```
出力が大きい → 先頭だけ残して目印を付ける
履歴が80%   → 古い部分を要約
履歴が95%   → 古い本文を捨てる（直近5ターンは残す）
```

公式サイトには「約2千〜4千（Mind経由）対 約5万（生の読み込み）」という比較（中央で約16倍）もあります。これは記録1件あたりの設計上の見積もりで、実測ではありません。実測で確認できた効果は、上の11.0%減です。

## 4. 似たものとの違い

公式サイトの比較表は次のとおりです。いずれもAnvaya側の主張で、第三者の検証ではありません。

| 観点 | 手書きの指示ファイル（CLAUDE.md、.cursorrulesなど） | Anvaya |
|---|---|---|
| 知識の置き場 | 人が書いて保守するマークダウンのファイル | 6種類のノードをつなぐ、重みと減衰のあるグラフ |
| コードが変わったとき | 人が気づいて直すまで、古いまま残る | gitと照合し、合わなくなった記録に印を付ける |
| 毎回AIに渡すもの | 指示ファイル全体と、読み直したファイル | 予算に収めて選んだ記録 |
| 役に立ったかの反映 | ない | 記録ごとに結果で更新 |
| 縮め方 | 要約や切り捨てが中心 | 3段階を測って、採用を判断 |
| 費用と鍵 | 提供元のAPI課金とAPIキーが必要 | Ollamaなら鍵も課金もなし |

メモリ機能を提供する他のサービスは、事実を貯めるだけで、役に立ったかを反映しない、というのが公式サイトの整理です。

## 5. 会話でわかったこと

### 5.1 何を覚えるのか

- 対象は、コードの意図（なぜそう作ったか）だけではない。決定のほかに、修正、失敗したやり方、パターン、概念、まとめも残る
- 人が書くのではなく、作業のセッションから自動で記録される
- 人間向けの設計書の代わりではない。AIが次の作業で参照するための記憶として作られている

### 5.2 縮め方の3段階をどう読むか

- 3つを試したことで、それぞれの長所と短所が数字で分かった。ここがこの機能の価値
- 小：記憶を失わずに縮められる（全文はディスクに残る）。大：確実だが細部が失われる。中：縮めた分を読み直して、かえって増えた
- 中の失敗は、縮めたあとに読み直した量まで数えないと、節約に見えて損をする、という教訓になる
- 記憶を失わずに節約もする「両取り」を目指す方向は筋がよい。今回の結果は、その判断材料になる

### 5.3 組み合わせの仮説（検討中の考え）

次の2点は、公式サイトに書かれていない、会話での検討です。

- 小さな縮め方を行ったうえで、関連するものだけを大きな縮め方に乗せる組み合わせで、効果が出るのではないか。ただし、大きな縮め方は、上限の80%で古い履歴を要約するだけで、関連するものを選ぶ仕組みではない。関連するものを選ぶのはMindの役割。2つを組み合わせた効果は測られていない
- 長時間のセッションほど効果が出やすいのではないか。出力が積み重なるほど縮める余地は増える。一方で、実験は5回の試行のみで、セッションの長さによる違いは示されていない。中の失敗を見ると、長いセッションでは読み直しが増えて逆効果になる可能性もある

### 5.4 使うときの条件（確認できた事実）

- 対応はLinuxとmacOSで、Windowsは未対応
- Rustのビルド環境を用意し、ソースから作る必要がある
- バージョンは1.0未満の公開ベータ。価格は未定
- 記憶はプロジェクト内のフォルダにだけ残る。テレメトリはない。AnthropicやOpenAIを使うときは自分のAPIキーを設定し、そのときも記憶の保存先は自分のPCのまま

向いている場面（推測）：同じプロジェクトで作業を重ね、過去の失敗や判断を思い出す価値が高い場合。短い使い切りの作業では、記憶が溜まる前に終わるため、得るものは少ない。

## 6. 未解決事項

- 長く使ったときに、作業が安くなり、記憶が役立つようになるか。公式サイトは測定計画（Phase 6）を挙げているが、結果はまだない
- 小さな縮め方を、中心の機能として初期設定でオンにできるか。昇格の条件が満たされるのを待っている状態
- 小さな縮め方と、関連する記録の選択を組み合わせた効果
- セッションの長さと、縮め方の効果の関係
- チームで1つの記憶を共有する仕組みがあるか。公式サイトには記載がない（記憶は1台、1プロジェクトごとに溜まる作りに見える）
- 軽さや縮め方の数字を、第三者が再現できるか
