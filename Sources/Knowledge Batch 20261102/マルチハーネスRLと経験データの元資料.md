# マルチハーネスRL ナレッジ

作成日：2026-11-02

## 1. 概要

Hugging Face が公開した「The ultimate guide to multi-harness RL」は、Claude Code や Codex のような既存のコーディングエージェント（ハーネス）を改造せずに、その中で動くオープンウェイトモデルを強化学習（RL）する方法を解説している。

要点は次の3つ。

- ハーネスとモデルの間に**キャプチャプロキシ**を置き、モデルが実際に出したトークンと確率を記録して学習に使う。
- 同じ重みのモデルでも、ハーネスが違うと正解率が大きく変わる。エージェントの成績は「モデル × ハーネス」で決まる。
- 複数のハーネスでまとめて学習すると、どのハーネスでも学習前より成績が上がった。

## 2. 理解に必要な前提

**ハーネス**
モデルを呼び出し、ツールを実行し、いつ終了するかを決める実行環境。Claude Code、Codex、OpenCode などが該当する。システムプロンプト、使えるツール、リトライ、終了条件はハーネスごとに異なる。

**重みの更新**
ここでいう「モデルを強化する」は、ハーネスを改良することではない。モデルの重み（weights）を学習で更新して、モデル自体を賢くすることを指す。

**オープンウェイトモデル**
重みを取得できるモデル（LFM、Qwen など）。重みを自分たちで更新できるため、RL の対象にできる。

**RL と SFT の違い**
- SFT（教師あり微調整）：成功した手本の軌跡をまねて学ぶ。
- RL：自分で試した結果と、成功したかどうかの判定（報酬）から学ぶ。

**トークンと確率**
モデルは文章を、トークンと呼ばれる単位に分けて1つずつ出力する。RL では、実際に出したトークンと、そのときの各トークンの確率が必要になる。

## 3. 解説

### 3.1 なぜプロキシが要るのか

通常の RL では、学習側が「モデルに答えさせる → 結果を見る」のループを回すので、モデルの出力をそのまま持っている。

Claude Code のようなハーネスは、ハーネス自身がモデルを呼び、ツールを動かし、終了を決める。学習側からは中身が見えない。

```
通常のRL     学習側 ⇄ モデル
ハーネス型   ハーネス ⇄ モデル            ← 学習側からは見えない
プロキシ型   ハーネス ⇄ プロキシ ⇄ vLLM
                         └→ 記録して学習へ
```

ハーネスのモデル呼び出し先をプロキシに向けるだけなので、ハーネス本体の改造は要らない。

### 3.2 何を記録するか

プロキシは、モデルが処理したプロンプトのトークン ID、実際に出力したトークン ID、各トークンの確率を保存する。

文章に直したあとで、トークンに分け直すことはしない。同じ文字列でもトークンの区切り方は複数あり、分け直すと、モデルが実際には出していない並びを学習するおそれがある。元記事は、これを on-policy RL を成り立たせる条件として扱っている。

プロキシは4種類の API 形式を受け付ける。

- OpenAI Chat Completions
- OpenAI Responses
- Anthropic Messages
- Gemini generateContent

### 3.3 実装の役割分担

| 部品 | 役割 |
|---|---|
| OpenEnv | 環境のインターフェースとキャプチャプロキシ |
| Harbor | タスク、サンドボックス、ハーネスのアダプタ、成功判定 |
| TRL（AsyncGRPOTrainer） | rollout を受け取って学習 |
| vLLM | モデルの実行（トークンと確率を返す） |

この分離により、新しいハーネスに対応するたびに、学習側でエージェントのループを作り直す必要がなくなる。

### 3.4 学習に使えるモデルの条件

学習用のエンドポイントは、実際に出したトークン ID と各トークンの確率を返す必要がある。vLLM や SGLang は返せる。OpenAI、Anthropic、Hugging Face Inference Providers のようなホスト型のエンドポイントは、評価には使えるが、この仕組みでの学習には使えない。

したがって、「Claude Code を使って Claude を学習する」仕組みではない。Claude Code の呼び出し先を自前の vLLM に向け、その中のオープンウェイトモデルを学習する仕組みである。

### 3.5 結果の読み方

条件：LFM2.5-2.6B を、OpenCode、Claude Code、Codex、Mini-SWE-Agent の4つのハーネスで Async GRPO により学習した。

**確認できたこと**

- 同じ重みで、Mini-SWE-Agent は約62%、Claude Code は約33%だった。
- 4つのハーネスの平均は42%から54%に上がり、どのハーネスでも学習前を上回った。
- OpenCode だけで学習すると、OpenCode では34%から58%に上がった。ほかのハーネスでの伸びは小さかった。
- 個別に見ると、OpenCode では OpenCode のみの学習が58%、複数ハーネスの学習が50%だった。Claude Code では42%対49%、Codex では43%対54%だった。

**言い切れないこと**

- 平均で見た54%（複数ハーネス）と約52%（OpenCode のみ）の差は、著者自身が誤差の範囲としている。学習は1回のみで、学習したタスク数やトークン数も揃っていない。
- SFT と RL の比較は、条件が揃っていない。SFT は最大47.5%、RL は約52〜54%だった。SFT の手本は、Qwen3.8-27B が4つのハーネスで解いた成功例（888タスクから3,189件）である。学習タスク数、トークン数、目的関数、計算量が異なるため、元記事も順位づけではなく観察として扱っている。
- ツール呼び出しが31%減ったことの原因を、効率ボーナスだけに帰すことはできない。報酬には、正解時のみ `1 + 1.5 / (15 + tool_calls)`（最大0.1）の効率ボーナスが付いている。しかし、ボーナスなしの実験はなく、タスクの難易度や出力上限も変わっている。

効率ボーナスは、GRPO と相性がよい。同じタスクの8回の試行がすべて正解のとき、正解の報酬だけでは全試行が同じ報酬になり、学習の手がかりが消える。ボーナスがあれば、少ない呼び出しで解いた試行と多くかかった試行に差がつく。

### 3.6 ベンチマークの読み方への影響

エージェントの成績を比べるときは、モデル名だけでなく、ハーネスの名前とバージョンも実験条件に含める必要がある。

### 3.7 新しいモデルが出たとき

重みは、別のモデルにそのまま移せない。LoRA アダプタも、原則として、対応するベースモデル専用である。一方、タスク、成功判定、成功・失敗の履歴は、別のモデルでも使い回せる。

新しいモデルが出たときの進め方の例（会話での検討）は次のとおり。

1. 蓄積した成功例で SFT をして、v1 を作る。
2. そのモデルを実際に動かし、RL で改善する。
3. その過程で、新しい経験データをさらに蓄積する。

過去の RL で使った勾配や生成確率は、新しいモデルには適用できない。

## 4. 似たものとの違い

| | 通常の RL 環境 | マルチハーネス RL |
|---|---|---|
| ループを回す主体 | 学習側 | ハーネス |
| トークンと確率 | 学習側が最初から持つ | プロキシが記録する |
| 新しい環境への対応 | 環境ごとにループを作る | ハーネスの呼び出し先を差し替える |
| 改造の要否 | 環境側を作り込む | ハーネスの改造は不要 |

SFT との違いは、「2. 理解に必要な前提」を参照。

## 5. 会話でわかったこと

**「モデルを強化する」の意味**
ハーネスを改良するのではなく、ハーネスの上で試した結果をもとに、モデルの重みを更新する。ハーネス上でモデルを動かすだけでは賢くならず、評価と学習の処理を別に実行する必要がある。

**自作のハーネスへの適用（検討）**
自作のエージェントハーネスがあれば、同じ構成の学習環境にできる可能性がある。条件は次の3つ。

1. モデルの呼び出し先を、プロキシ経由の vLLM に差し替えられる。
2. タスクに自動の成功判定がある。コード生成ならテストの合否で判定できるが、ゲームエンジンのようにテストで判定しにくい作業では、判定方法の設計が最大の課題になる。
3. 経験データを、モデルやハーネスから独立した形で蓄積できる。

学習の対象は接続したモデルであり、ハーネス自体が賢くなるわけではない。

**経験データの蓄積（検討）**
ハーネスごとに学習データが散らばらないよう、共通の経験データベースに集める構成が考えられる。

```
ハーネスA ─┐
ハーネスB ─┼→ 共通の経験データベース → 評価・選別・変換 → SFT / RL → 新モデル
チャット  ─┘
```

蓄積する情報は、会話ログではなく、タスク、実行履歴、評価、人間による修正である。チャットの履歴は、そのまま RL に使えない。SFT 向けのデータへの変換と、評価の設計が必要になる。

**サブスクリプション経由の構成でのプロキシの位置**
自作のハーネスが、Claude Code を経由してサブスクリプション上のモデルを使っている構成を例に整理した。なお、この構成の前提は利用者の説明に基づくもので、公式の資料では確認していない。

- ハーネスと Claude Code の間にプロキシを置くと、やり取りされる文章は見える。しかし、ホスト型モデルが実際に出したトークンと確率は見えない。
- ホスト型モデルは重みを更新できないため、そもそも学習の対象にならない。
- 学習するときは、呼び出し先を自前の vLLM に切り替える。普段使いはサブスクリプションのモデル、学習時は vLLM という使い分けになる。

```
普段使い   ハーネス → Claude Code → ホスト型モデル
学習用A    ハーネス → Claude Code → プロキシ → vLLM
学習用B    ハーネス ────────────→ プロキシ → vLLM
```

元記事の構成は学習用Aに当たる。

## 6. 未解決事項

- 自作のハーネスが、元記事のプロキシが受け付ける4種類の API 形式のどれに対応できるか。
- ゲームエンジンの作業のように、テストで判定しにくいタスクの成功判定をどう設計するか。
- 同じ伸びが、自作のハーネスでも出るか。元記事は小型モデルと単一のシードでの結果であり、試して確かめる必要がある。
- ホスト型モデルの出力を、ほかのモデルの学習データに使うことが、各社の利用規約で認められるか。使う前の確認が必要。
- 複数ハーネスの学習が、単一ハーネスの学習より優れているか。元記事は、誤差の範囲としている。
