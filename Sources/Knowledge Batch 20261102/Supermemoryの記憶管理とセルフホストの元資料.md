# Supermemory ナレッジ

調べた日：2026-11-02

## 1. 概要

Supermemory は、AIエージェントに記憶を持たせるサービスです。会話やファイルから事実を取り出し、モデルの外にあるデータベースに保存します。質問が来るたびに、関係する記憶を探してプロンプトに差し込みます。モデルは変わらず、プロンプトの中身だけが変わります。サイトでは、この考え方を「コンテキスト内での継続学習」と呼んでいます。

要点は次の4つです。

- 記憶はモデルの外にあるため、モデルやツールを替えても引き継げる
- 記憶は文章のまま溜めず、事実に分け、事実どうしをつないだグラフとして持つ
- 新旧の入れ替えや、期限切れの記憶の削除まで、仕組みの側が行う
- 接続は API、MCP、プラグインの3通りで、ホスト版のほかに自分で動かす版もある

## 2. 理解に必要な前提

**プロンプトと文脈。** AIモデルは、毎回届く文章（プロンプト）だけを手がかりに答えます。会話が終わると、そこで学んだことは残りません。モデルを追加で学習させれば覚えさせられますが、時間と費用がかかります。そこで、必要なことをプロンプトに入れ直す方法が使われます。これが「文脈に入れる」という意味です。

**RAG と記憶の違い。** RAG は、文書を細かく切って検索し、近いものを返す方法です。誰が聞いても同じ結果になります。記憶は、特定のユーザーや案件について、事実を時間の流れの中で追跡します。

**MCP。** AIアシスタントに外部の道具をつなぐための共通の規格です。設定にURLを書くだけで、対応するクライアントが道具を呼べるようになります。

**フック。** 特定のタイミング（質問を送る時点、返答が終わった時点など）で、自動的に動く小さな処理です。

**ベンチマークの指標。** 記憶の性能は、公開の試験で測られます。測るものが「検索で正解の根拠が上位k件に入ったか」（Recall@k）なのか、「最終的な答えが合っていたか」なのかで、意味が違います。

## 3. 解説

### 3.1 全体の流れ

```
ファイル / チャット / URL
        ↓
  記憶用モデル（learner-1） ⇄ 記憶DB（時間を扱うベクトル＋グラフ）
        ↓
エージェントの文脈に差し込む
```

### 3.2 記憶ができるまで

記憶ができるまでには2段階あります。1段階目は、文書を検索できる形に索引化する作業です。2段階目は「ドリーミング」と呼ばれ、記憶用のモデルが内容から事実を取り出し、既存の記憶と統合して整理します。

記憶の置き場は、ベクトル検索、全文検索、グラフを備えた、時間を扱える事実中心のデータベースです。サイトによると、記憶用のモデルは自社で開発した専用のものです。

### 3.3 記憶どうしの3つの関係

新しい事実は、既存の記憶と次の3つの関係で結ばれます。

| 関係 | 内容 | 例 |
|---|---|---|
| 更新 | 後の情報が前の情報を置き換える。最新のものに目印が付き、検索では現在の情報が返る。過去の記憶は履歴として残る | 「Google で働いている」→「Stripe で働き始めた」 |
| 拡張 | 置き換えずに詳しくする。両方が有効なまま残る | 「Stripe の PM」に「決済基盤を担当し、5人のチームを率いている」が加わる |
| 導出 | 発言の傾向などから、直接は言われていない事実を推測して作る | 決済APIの話が多いことから「中核の決済製品に関わっていそう」 |

一時的な予定（「今日の15時に打ち合わせ」など）は、日を過ぎると自動で忘れられます。好みの記憶は、繰り返し出てくるほど強まります。

従来の知識グラフは「主語・関係・目的語」の三つ組を並べる形で、規模が大きくなると検索が遅くなりやすいとされます。Supermemory は、1つの事実を1つの完結した単位として持つ形を採っていると説明しています。

### 3.4 なぜどのモデルでも使えるのか

Supermemory は、モデルの中身には触れません。関わるのは、プロンプトの前後だけです。質問が送られる前に関係する記憶を探してプロンプトに足し、返答が終わったあとに、その会話から覚えるべきことを保存します。

```
質問 → [フック：記憶を探す] → プロンプトに足す → どのモデルでも
返答 ← [フック：内容を保存] ←
          ↑↓
   Supermemory（コンテナタグごとの記憶）
```

接続の方法は3つです。

- **API**：ユーザーの好みや最近の活動をまとめたプロファイルを、1回の呼び出しで取得できる。公式は約50ミリ秒としている。これをシステムプロンプトに入れる
- **MCP**：設定にサーバーのURLを書くと、MCP対応のクライアントから使える。記憶を保存する道具や、思い出す道具が提供される。エージェントが必要だと判断したときに呼ぶ使い方になる
- **プラグイン**：Claude Code、Cursor、OpenAI Codex、OpenCode などに用意されている。フックで自動的に動き、使う側は何も頼まなくても記憶が働く。通信が遅くなっても作業を止めないように作られているものがある

**共通の記憶になる条件。** 記憶は「コンテナタグ」という区画の名前で分かれます。同じ名前を使うツールどうしが、同じ記憶を読み書きします。たとえば Cursor は、Claude Code、Codex、OpenCode のプラグインと、同じリポジトリ用の名前を共有しています。つないでいないツールには、記憶は共有されません。

## 4. 似たものとの違い

### 4.1 プロジェクト内のメモファイルにモデルが書く方法との比較

考え方は同じです。どちらも「書いたあとに整理し、必要なときに取り出しやすくしておく」ことを目的とします。規模が小さいうちは、大きな差は出ません。小さなファイル操作だけで、ある記憶ベンチマークで高度な記憶システムと同程度の正解率が出た、という報告もあります（ConvoMem の論文）。

違いは、整理を誰が、いつ、どんな形で行うかです。

| 観点 | メモファイル方式 | Supermemory |
|---|---|---|
| 整理の担当 | 作業中のモデル（または人間） | 専用の記憶用モデル。作業とは別のタイミングで実行 |
| 新旧の扱い | 両方が残り、読んだ側が矛盾を解消する | 更新関係を記録し、検索では最新を返す |
| 期限切れの記憶 | 自分で消す | 一時的な記憶は自動で忘れる |
| 検索 | ツールや索引を自作する | 意味検索、全文検索、関係をたどる検索を1回の呼び出しで返す |
| 人が読めるか | 読める。Git で履歴も管理できる | データベースの中にあり、直接は読みにくい |
| 仕組みの単純さ | 単純 | 複雑 |

注意点が1つあります。Supermemory の整理も、実際にはモデルが行っています。違いは、作業用のモデルとは別の専用モデルが、別のタイミングで担当することです。メモファイル方式でも、作業用モデルに整理を毎回担当させれば、同じ内容は実現できます。その場合は、整理のためのトークンと手間が、作業の途中に混ざります。

自社の実験では、ファイルが5個から約1万個に増える間、Markdown のメモはトークン消費が約7倍に増え、Supermemory は約4倍でした。これは自社の報告で、条件も限られているため、そのまま一般化はできません。

### 4.2 RAG との違い

RAG は文書の断片を検索する方法です。Supermemory は、事実を時間の流れで追跡する記憶と、文書検索を同じエンジンで扱えるとしています。

## 5. 会話でわかったこと

### 5.1 性能の数字の読み方

- LongMemEval は、ノイズの多い11万トークン以上の会話履歴から、保存した情報を取り出せるかを500問で試す試験です。Supermemory は、2026年5月の報告で Recall@20 が97%だったとしています。以前の版では、Recall@15 が95%で、取り出した記憶は平均約720トークンでした
- Recall@k は、正解の根拠が上位k件に入ったかどうかです。最終的な答えが合っていたかどうかとは別の指標です。この2つを並べて比べると、見かけの差が大きくなります。他社の宣伝で、この混同が起きたという検証記事があります
- 数字を読むときは、次の3つを確かめます

  1. 何を測っているか（検索の当たり具合か、最終的な回答の正しさか）
  2. 誰が測ったか（自社の報告か、第三者の検証か）
  3. テストの規模と条件（質問数、データの作り方、設定）

- サイトの「1位」は自社の報告です。第三者の論文 SWE-ContextBench は、比較した中で Supermemory が総合で最も良いと報告しています
- Salesforce の研究者らは、既存のベンチマークは質問数が少なく、LoCoMo は10の会話しかないと指摘しています
- 記事によっては、約99%という値が、本番のエンジンではない実験的な構成の結果だと書かれています。公式サイトの値と、実験構成の値は区別して読みます
- SMFS（記憶をファイルシステムとして扱う形）の研究では、110問の課題で、累積トークン数が Claude で3分の1、Codex で1.75分の1になり、正確さも上がったと報告されています。モデルの賢さではなく、記憶の出し方で費用を減らす話です

### 5.2 API 利用への懸念がある場合

API を使うサービスは、価格や安定性への心配が出やすい選択肢です。Supermemory には、自分で動かす版があります（次節）。ただし、ホスト版との間に機能の差があります。

### 5.3 自前で作るときの設計の要点

これまでの内容から、次の7つに整理できます。1と2が「整理」の中心で、3から7は、整理した結果を安全に使うための部分です。

1. 書き込み時に、モデルで会話を小さな事実に分ける
2. 後から来た事実が古い事実を置き換えたと記録し、最新を示す目印を付け、履歴は残す
3. 期限のある記憶は、日付で失効させる
4. ユーザーや案件ごとに、記憶の区画を分ける
5. 意味での検索、単語での検索、関係をたどる検索を、まとめて返す
6. 重い整理は、返答のあとに非同期で行う
7. 記憶の取得や保存が失敗しても、作業は止めない

## 6. セルフホスト版

確認できた事実は次のとおりです。

- 1つのバイナリを起動するだけで動く。Docker、データベース、設定ファイルは要らない
- グラフエンジンとベクトル化の機能は、中に入っている
- 記憶の取り出しと整理に使うモデルは、OpenAI、Anthropic、Gemini などのほか、Ollama などの局所モデルを指定できる。完全にオフラインでも動かせる
- APIはホスト版と同じで、接続先の1行を変えるだけで切り替えられる。Claude Code、Codex、OpenCode のプラグインも、手元のサーバーを向けられる
- 公式の比較表では、Google Drive などとのコネクタ、PDF や画像の取り込みの一部、MCP は、ホスト版にあってセルフホスト版にない項目として挙がっている
- 記憶の抽出は、自分で用意したモデルが担当する。本番の環境では、長期の記憶向けに調整された専用モデルが使われる

ホスト版と自分で動かす版は、次のように使い分けられます。

| | セルフホスト版 | ホスト版 |
|---|---|---|
| 動かす場所 | 自分の環境 | 提供側の環境 |
| 記憶抽出のモデル | 持ち込んだモデル | 専用モデル |
| コネクタ、MCP | 一部なし | あり |
| 向く用途 | 手元での開発、閉じた環境、プライバシーを重視する作業 | 規模が大きい運用 |

## 7. 未解決事項

- **セルフホスト版のライセンス。** 公式ドキュメントは、無料でオープンソースだと説明している。一方、競合の EverMind が書いた比較記事は、ローカル版のサーバーはオープンソースではなく、軽量版のライセンス上限があるとしている。どちらが正確かは、確かめられていない。利用や改変を考えるなら、ライセンス文書を直接確認する必要がある
- **記憶用モデル（learner-1）の詳細。** 公開されている情報は、サイトの説明にとどまる。内部の仕組みや学習データは確かめられていない
- **第三者による再現。** 自社の性能の報告のうち、第三者が再現した結果は、SWE-ContextBench の論文以外では確認していない
- **セルフホスト版の品質。** 持ち込んだモデルの質に左右される。モデルごとの差は調べていない
- **料金の体系と、長期の運用での安定性。** 料金のページと運用実績は、調べていない
