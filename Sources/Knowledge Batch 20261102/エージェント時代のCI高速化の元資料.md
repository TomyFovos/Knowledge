# エージェント時代のCI高速化：ナレッジ

## 概要

コーディングエージェントがコードを書く速さが上がると、PRごとの確認（CI）の遅さが開発全体の上限になります。参照した記事は、CIを製品のように扱って改善した事例です。最大40分かかっていた待ちが2分になりました。

要点は次のとおりです。

- 時間の大半は、テストの実行ではなく「待ち」と「準備」にあった
- 効いた施策は、実行用マシンの変更、並列化、lint・型検査ツールの置き換え、テストの分割と準備の見直し、変更範囲だけの実行、push前の手元検査の6つ
- 費用は月230ドルから4,300ドルに増えた。筆者は、エージェントを速くする手段としては最も安いと評価している
- CIが速くなると、次に遅い部分は人がマージを押す作業になる

| 項目 | 改善前 | 改善後 |
|---|---|---|
| 実行用マシンの待ち | 最大11分 | 8秒 |
| lint | 2分 | 5秒 |
| 型検査（サーバー、初回） | 70秒 | 5秒未満 |
| テスト（1シャード） | 100秒 | 35秒 |
| 依存キャッシュの外れ（PR） | 半数 | 1% |
| サーバーのテストジョブ | 168秒 | 74秒 |

## 理解に必要な前提

- **CI**：PRを出すたびに自動で動く、lint・型検査・ビルド・テストなどの確認
- **アムダールの法則**：全体のうち速くできない部分が、全体の速さの上限になるという考え方。書く作業だけを10倍にしても、CIが遅いままなら全体はほとんど速くならない
- **シャード**：1つのテスト群を複数のマシンに分けて同時に走らせるときの、分けた1つ分
- **PR用キャッシュの範囲**：GitHub Actionsでは、PRのキャッシュはそのPRのブランチ内に限られる。mainで作ったキャッシュを別のPRが自動では使えず、mainから引き継ぐ仕組みが別に必要
- **ブロブなしクローン**：`filter: blob:none`で、ファイルの中身を後から必要なときに取得する方式。浅いクローン（履歴を切る方式）と違い、git履歴を読む処理が壊れない
- **エージェントの再試行**：CIが失敗してもエージェントは原因を直さずに再実行しがちで、遅さや不具合が表に出にくい

## 解説

### 全体の流れ

```
エージェントが push → CI を待つ → 赤なら修正 → また push
                      ↑ ここが長いと、1周ごとに全体が止まる
```

CIの時間は、待ち（マシン確保）、準備（取得・インストール・キャッシュ復元）、実行（検査やテスト本体）に分けて考えます。記事の筆者は、直近150回の実行をエージェントに集計させ、ジョブごとにこの3つへ分解しました。そこから、準備に隠れていた不具合が見つかっています。

### 1. 待ち時間を削る

- **実行用マシンの変更**：標準のマシンはジョブ開始前に最大11分待つことがあった。外部のランナーサービス（記事ではBlacksmith）に替えて8秒になった。変更はジョブごとの`runs-on`の1行
- **小さいジョブも移す**：数秒で終わるジョブを標準のマシンに残すと、そのジョブが最も遅い部分になる。5秒の仕事でも、マシンを10分待てば10分かかる
- **並列化**：lint、型検査、ビルド、テストを同時に走らせると、PRの所要時間は最も遅いジョブで決まる
- **最も遅いジョブの中身を見る**：最初のテストシャードが、マイグレーション確認や他アプリのテストも抱えて最後に終わっていた。別ジョブに切り出して2分短縮
- **並列数をコア数に合わせる**：4コアで8タスクを動かしていたのを半分にしても速さは同じで、不安定なテストが1つ直った

ここまでで、40分が約10分になりました。

### 2. lintと型検査を速いツールに替える

- **lint**：ESLintからOxlintへ。2分が5秒になった。エージェントは厳しいルールを嫌がらないので、使えるルールはすべて有効にする
- **型検査**：1か月で3回替えた。サーバーの初回は、tscで70秒、TypeScript 7で13秒、bun checkで5秒未満（CIで採用）。手元ではtsrsで0.6秒
- 速い新ツールの情報をSlack上の社内エージェントに貼り、6分後に計測結果、20分後にマージという流れで、替える作業自体も人手をほとんどかけずに回している

### 3. テストを速くする

- **大きいマシンに分ける**：8分のテストを、8コアのマシン6台（各シャードが専用のDBを持つ）に分けた。各シャードはCPUの大半をモジュール読み込みに使っていたので、台数よりコア数が効いた
- **ファイルごとの再読み込みをやめる**：Vitestはテストファイルごとに新しい作業用プロセスを作り、そのたびにNestJSアプリ全体を読み込んでいた。`isolate: false`で1シャード100秒が35秒になった
  - 副作用として、テスト同士が状態を引きずる。ファイルごとに状態を戻すフックを入れ、片付けるべきものをエージェントに伝える
- **準備の見直し**：半数のテストジョブで依存キャッシュが使われていなかった。原因は、PR用キャッシュがブランチ内に限られ、mainから引き継ぐ仕組みがなかったこと。これを直してキャッシュの外れは1%になった
- **小さな改善**
  - `node_modules`のキャッシュ：インストール33秒が復元13秒
  - ブロブなしクローン：チェックアウト36秒が12秒
- **試して効かなかった案**：2万件のテストを調べても削るべきものはほとんどなく、時間もテストにはなかった

### 4. 変更した範囲だけ実行する

- `nx affected`で、PRが変更したプロジェクトのテストだけを走らせる。フルテストは毎晩mainで実行する
- 省く判定そのものを試す。サーバーの変更をわざとNxから見えなくしたところ、6つのシャードがすべてテストを省いて緑のまま通った。今はその状態を失敗として扱う
- 省く仕組みは、誤ると「何も確認していないのに成功」と出る

### 5. push前に手元で止める

- pre-pushフックで、変更したファイルだけ整形・lint・型検査を走らせる（9秒未満）。型エラーはCIを待たずに手元で直せる
- AGENTS.mdなどの指示文書ではなく、フックにする。エージェントは手順を飛ばすことがあり、長いセッションでは指示文書がほとんど読まれないという報告もある
- 「お願い」は読み飛ばされることがあり、「強制」は必ず通る

### 費用と次の課題

- 月額は230ドルから4,300ドルに増えた。大きいマシン、シャード分割、並列実行で速さを買った部分が大きい
- 費用を抑える施策もある。変更範囲だけのテスト、キャッシュ、コア数に合わせた並列数
- 待ちや重複を削る施策は時間と費用の両方に効き、マシンを大きくする施策は時間に効いて費用は上がる
- CIが2分になると、次に遅いのは人がマージを押す作業になる

## 似たものとの違い

| 観点 | 標準のランナー | 外部のランナーサービス | 自前のCI用VM |
|---|---|---|---|
| マシン待ち | 最大11分の例あり | 8秒の例あり | 自分で台数と起動を管理 |
| 切り替えの手間 | なし | `runs-on`の1行 | VMの構築と保守 |
| ディスクIO | 共有環境 | NVMeを売りにする（後述） | 構成次第 |

| 観点 | 指示文書に書く | フックで強制する |
|---|---|---|
| エージェントの遵守 | 読み飛ばされることがある | 必ず通る |

| 観点 | 全テストを毎回実行 | 変更範囲のみ実行 |
|---|---|---|
| 時間と費用 | 大きい | 小さい |
| リスク | 低い | 省く判定が誤ると素通りする |

## 会話でわかったこと

### 時間と費用の関係

- CIの遅さと費用は、どちらも開発のボトルネックになる。ただし、全部の施策がトレードオフではない
- 記事は、施策ごとの費用の内訳を出していない。どの施策がどれだけ費用に響いたかは、このままでは分からない

### フルテスト以外の実行

- 記事では`nx affected`で実現している。ただし、何割のPRでテストが減ったかは書かれていない
- 省く判定のテスト（変更をわざと隠す）が不可欠

### 自前のCI用VMとランナーサービスの比較（ディスクIOが詰まる場合）

- 公式ドキュメントによると、Blacksmithはベアメタルのゲーミング向けCPUでジョブを動かし、キャッシュ用のsticky diskはローカルのNVMe上のCephクラスタに保存される。ジョブ開始時にマウントされ、マウントは約3秒（一部の利用例の記載）
- 性能の数字（キャッシュ取得4倍、Docker 40倍など）は、ほとんどBlacksmith自身のブログ由来で、自環境の実測とは別物
- IOが詰まる原因（`node_modules`の展開、DBの初期化、ビルドの書き込み）で効き方が変わる
- 切り分けの手順
  1. CIの実行中に`iostat -x 1`でディスク使用率を見る。張り付いていればディスクが原因
  2. 自前VMのディスクをNVMeや高IOPSのものに替えるだけでも改善することがある
  3. 最も重いジョブ1つの`runs-on`を書き換え、実行時間を並べて比べる

## 未解決事項

- 各施策が費用に与えた影響の内訳（記事に記載なし）
- 変更範囲だけのテストで、何割のPRが対象になったか（記事に記載なし）
- 新しい型検査ツール（bun check、tsrsなど）が、tscと同じ指摘を返すか。Bunの計測は64コアのマシンでの数字で、自環境での結果は別に確かめる必要がある
- 自前のCI用VMとランナーサービスで、実際にどれだけ差が出るか（自環境で計測が必要）
