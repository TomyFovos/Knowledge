### 投稿でやっていることを、かなり単純化するとこうです

たとえば企業から、

> 顧客から来た問い合わせを読んで  
> 「緊急」「通常」「営業」「クレーム」「セキュリティ事故」  
> のどれかに分類したい。

と言われたとします。

普通ならDeepSeekやClaudeなどの巨大LLMに毎回、

```text
この問い合わせを分類してください
```

と聞きます。

でも毎回巨大モデルを使う必要はありません。

まず巨大モデルに大量の例題を解かせます。

```text
問い合わせA → セキュリティ事故 0.98
問い合わせB → 通常 0.87
問い合わせC → クレーム 0.91
...
```

数万～数十万件くらい教師データを作ります。

そして、小さいQwen 4Bのようなモデルに、

```text
入力：
この文章

正解：
security_incident = 0.98
```

というペアを大量に学習させます。

すると最終的には、

```text
DeepSeek 300B級
        ↓
   教師データ作成
        ↓
   Qwen 4Bなど
        ↓
  企業専用判断モデル
        ↓
   4bit量子化
        ↓
  RTX / Mac / CPU
```

という構成になります。

これが投稿で言われている「巨大モデルの判断能力を小型モデルへ移す」という発想です。

ただし、かなり重要な注意点があります。

**これはJevそのものを作っているわけではありません。**

TypeSafeが公開している説明では、Jevは単なる小型LLMではなく、文字列を自己回帰生成する普通のLLMとは異なるアーキテクチャ、並列サンプリング、さらに「RLCD（Reinforcement Learning for Calibrated Decisions）」という学習方式を使う専用モデルだと説明されています。出力も文章ではなく、型付きの判断と確率です。([TypeSafe AI](https://typesafe.ai/blog/introducing-system-one-models-and-jev))

ですから、企業向けサービスとして表現するなら、

**「専用Jevを作ります」ではなく、  
「Jev的な用途を狙った企業専用ローカル判断モデルを構築します」**

のほうが技術的には正確です。

## 実は「4B LLMを蒸留」が常に正解ではありません

ここが企業案件ではかなり重要です。

仮に顧客から、

> メールに機密情報が含まれているか判定したい

と言われたとします。

選択肢はかなりあります。

```text
プログラム
   ↓ 無理なら

正規表現・ルール
   ↓ 無理なら

Embedding / 小型Classifier
   ↓ 無理なら

100M～1B級モデル
   ↓ 無理なら

3B～8B LLM
   ↓ 無理なら

大型LLM
```

という順番で考えたほうがいいです。

たとえば、

> 「電話番号が含まれているか」

ならPythonの正規表現です。

> 「これはクレームか？」

ならBERT系Classifierで十分な可能性があります。

> 「顧客の文章全体を読んで、規程上のセキュリティインシデントに該当するか？」

くらいになると、LLMを蒸留した1B～4Bモデルが有力になります。

> 「法律、契約書、社内規程を横断して理由付きで判断しろ」

になると、大型LLMやRAGが必要になる場合があります。

つまり企業向けの価値は、

**「なんでも4Bモデルを作る能力」ではありません。**

むしろ、

**「この業務ならルールで十分、この業務ならClassifier、この業務だけ蒸留LLM」**

と設計できる能力です。

これは、今まであなたがJevについて考えていた「プログラムで解けるものはプログラムに寄せ、曖昧な判断だけAIに渡す」という考え方とかなり相性がいいです。

## 「蒸留」という言葉にも少し注意が必要です

ここは今後他社に説明するときに知っておいたほうがいいです。

世の中ではかなり広く、

> 大モデルに答えを作らせて、小モデルに学習させた

ことを「蒸留」と呼びます。

ただ、機械学習的には少し種類があります。

教師モデルが、

```text
A = 0.72
B = 0.18
C = 0.10
```

のような**確率分布そのもの**をStudentに教えるKnowledge Distillationもあれば、

```text
正解 = A
```

だけ大量生成して学習する方法もあります。

後者は厳密には「synthetic dataを使ったSFT」や「pseudo-labeling」に近い場合があります。

さらに、

```text
理由:
○○だからA
最終回答:
A
```

のような推論例まで移す方法もあります。

なので、この投稿だけから

> 「DeepSeekの内部logitsを使った本格的Knowledge Distillationをやった」

とまでは判断できません。

実際に何をしたのかは、学習コードやデータ形式を見ないと分かりません。

# 企業専用モデルを作るなら、実際の工程はこうなります

あなたが将来、

> 「御社専用のローカルAIを作れますか？」

と聞かれたとき、実際には次の工程になります。

1. **業務を決める。** 「何でも答える社内LLM」ではなく、「何を入力して何を判断させるのか」を定義します。出力も `YES/NO`、5分類、0～1スコアなどに固定します。

2. **正解データを作る。** 実データから専門家が正解を付けたGold Datasetを作ります。境界事例や失敗例もかなり重要です。

3. **巨大Teacherを使う。** DeepSeek、Claude、GPT系、あるいは複数モデルで大量の教師ラベルを生成します。機密データを外に出せない企業なら、このTeacher自体をオンプレミスにすることもあります。

4. **Studentを学習する。** Qwen 1.5B/3B/4BなどへQLoRAやLoRAで学習させます。ここが、あなたがまだ触っていない領域です。

5. **未知データで評価する。** Accuracyだけではなく、Precision / Recall / F1、誤検出、見逃し、Brier ScoreやCalibration Errorなどを測ります。学習データをテストに混ぜないことが非常に重要です。

6. **confidence境界を決める。** たとえば `0.95以上=自動処理`、`0.70～0.95=確認`、`0.70未満=拒否/大型モデルへ送る` のようにします。

7. **量子化する。** ここで初めて、今までBonsaiで触っていた世界に戻ってきます。GGUFやAWQ/GPTQなどで軽量化します。

8. **ローカル配備する。** llama.cpp、vLLM、SGLang、Ollama等で社内API化し、既存システムにつなぎます。

この一連をできれば、かなり正当に

> **企業専用ローカルAIの設計・学習・評価・配備ができます**

と言えるようになります。

# Phase 4
## 「学習すれば良くなる」わけではないことを学ぶ

ここはかなり面白いところです。

同じDatasetを使って、

```text
epoch = 1
epoch = 3
epoch = 10
```

を比較します。

すると、

```text
Train accuracy

1 epoch  → 85%
3 epoch  → 96%
10 epoch → 99%

Test accuracy

1 epoch  → 81%
3 epoch  → 91%
10 epoch → 78%
```

みたいなことが起きます。

これが**Overfitting**です。

さらに、

```text
Learning rate
Batch size
Gradient accumulation
Sequence length
Epoch
Warmup
Weight decay
```

を少しずつ触ります。

ここでようやく、

> 「Fine-tuningする」

という言葉の意味がかなり具体的になります。

期間は2～4日。

# Phase 7
## 「Accuracy 95%だから安全」を卒業する

商品化するならここが必須です。

例えば、

```text
正常メール 9,500件
事故メール   500件
```

の場合、

全部「正常」と回答するモデルでも、

```text
Accuracy = 95%
```

です。

役に立ちません。

そこで、

```text
Precision
Recall
F1
False Positive
False Negative
```

を見るようになります。

さらに重要なのが、

```text
Confidence
Calibration
```

です。

モデルが、

```text
0.99
```

と言ったものが本当に99%正しいのかを見る。

さらに、

```text
confidence >= 0.95
→ 自動処理

0.70～0.95
→ 人間確認

< 0.70
→ 拒否
```

という**Abstention設計**もやります。

ここまで来れば企業案件として相当まともになります。

期間は3～5日。

```text
↓

8bit

↓

4bit

↓
```

|---|---:|---:|---:|

## まず、RAG・Fine-tuning・MCPの役割を分けましょう

たとえば架空企業に「AX-17」「赤伝」「P3申請」「Nexus案件」のような社内用語があるとします。

| やりたいこと | 主に使うもの | 理由 |
|---|---|---|
| 「AX-17とは何？」に答える | **RAG** | 社内資料から定義を探せる |
| 最新の社内規程に基づいて答える | **RAG** | モデル再学習なしで資料更新可能 |
| 「赤伝」という言葉を自然に使わせる | Fine-tuning | 話し方・使い方をモデル側へ寄せられる |
| 社内独自の回答形式を守らせる | Fine-tuning | 振る舞いを定着させやすい |
| SharePointから最新資料を取る | MCP等のTool接続 | 外部システムへアクセスするため |
| チケットを検索する | MCP等 | 動的データ取得 |
| チケットを登録する | MCP等 | 実際の操作 |
| 社内文書だけを根拠に回答させる | RAG + Guardrail | 根拠を制限できる |

MCPは「専門知識を学習させる技術」ではありません。公式仕様でもMCP Serverは、モデルへResources・Tools・Promptsを提供するための仕組みとして定義されています。つまり、モデルと社内システムの接続規格です。([Model Context Protocol](https://modelcontextprotocol.io/specification/2025-06-18/server?utm_source=chatgpt.com))

一方RAGは、質問されたときに関連文書を検索し、その内容をLLMへ渡して回答させます。Hugging Faceも、RAGを「回答前に文書コーパスを検索し、モデルの知識を補う」仕組みとして説明しています。([Hugging Face](https://huggingface.co/docs/transformers/main/chat_template_tools_and_documents?utm_source=chatgpt.com))

したがって今回の商品では、**RAGはほぼ必須、MCPは後から追加、Fine-tuningは必要性を測って追加**という順番がよいです。

# 「専門用語を覚えさせる」＝Fine-tuningではありません

```text

↓

```

> **事実・規程・製品情報・社内用語の定義 → RAG**

> 「この会社ではこの質問にはこういう考え方で答える」

```text

「何を知っているか」
        ↓
       RAG

Behavior
「どう答えるか」
        ↓

```

です。

# LLMのParameterは何を表しているのか

ここからがLLMにつながる部分です。

LLMのParameter一個一個が、

```text

= Pythonについて答えるWeight

Parameter 5678
= 猫について答えるWeight
```

という対応になっているわけではありません。

知識や言語能力は、**大量のParameterの組み合わせとして分散して保存されています。**

そのため、

> 「このParameterは何を覚えているのか」

と一個だけ取り出しても、人間が意味を読み取れることは通常ありません。

先ほどの単純な例では、

```text

```

というWeightを見れば、「振動を強く重視している」と比較的簡単に解釈できました。

LLMでは何十億個というParameterが何層もの計算に関与するため、その対応関係はそこまで単純ではありません。

## Parameterが決めているもの

それでも役割自体は、先ほどのWeightとつながっています。

LLMのParameterは、

**「入力された数値を、次の計算結果へどう変換するか」**

を決めています。

たとえば、

```text
「猫は」
```

という入力を受け取ったとします。

LLMは文字そのものを計算できないので、まずTokenという単位へ分け、それぞれを数値に変換します。

かなり単純化すると、

```text
「猫」
↓
[0.14, -0.37, 0.81, 0.22, ...]

「は」
↓
[-0.08, 0.41, 0.13, -0.52, ...]
```

という大量の数値になります。

そこから、学習済みのParameterを使って何度も計算します。

```text
入力されたTokenの数値
        ↓
Parameterを使った計算
        ↓
別の数値表現
        ↓
Parameterを使った計算
        ↓
別の数値表現
        ↓
……
        ↓
次に来そうなTokenのスコア
```

最後には、たとえば、

```text

動物        3.2
犬          1.4
飛行機     -2.7
```

のようなスコアができます。

これを確率へ変換すると、

```text
かわいい   55%
動物       25%
犬          8%
……
```

のようになります。

その結果を使って次のTokenを一つ選びます。

```text
回答B

回答C
技術用語を残しながら丁寧に説明する
```

のように、複数の妥当な回答があり得ます。

そのため、LLMでは「唯一の正解値に完全一致させる」というより、**学習データで望ましいとされるToken列へ高い確率を割り当てる方向にParameterを調整する**と考えるほうが正確です。

たとえば正解データが、

```text
日本の首都はどこですか？
→ 東京です。
```

だった場合、モデルが最初に、

```text
京都です。
```

へ高い確率を出していたとします。

学習では、その確率分布を少しずつ変えて、

```text
学習前

東京   0.20
京都   0.45
大阪   0.15
その他 0.20
```

だったものを、

```text
学習後

東京   0.85
京都   0.04
大阪   0.02
その他 0.09
```

のように、「東京」を出しやすい状態へ寄せていきます。

ここでLossが表しているのは、単純な数値差ではなく、**モデルが望ましいTokenへどれだけ低い確率しか与えていないか**です。

したがって、LLMではLossが下がるほど、

```text
望ましいToken列に
より高い確率を与えられる
```

ようになります。

ただし、Lossが下がったからといって、

```text
すべての質問に対して
完璧な回答ができる
```

ことを意味するわけではありません。

学習データに含まれていない表現や、似ているが少し違う質問にも適切に答えられるかという**汎化**も必要になります。

今回の実験で確認したかったのは、まさにその前段です。

```text
ランダムなParameter
        ↓
現在の出力
        ↓
望ましい出力との差を測る
        ↓
Loss
        ↓
Parameterを少し修正
        ↓
より望ましい出力へ近づく
```

この仕組み自体は、先ほどの4 Parameter程度のモデルでも、数十億Parameterを持つLLMでも共通しています。

したがって、今回学んだ内容を一文にすると、**機械学習は、望ましい出力とのずれをLossとして測り、そのLossが小さくなる方向へParameterを繰り返し調整する処理**です。

LLMでは「唯一の答えに一致する」よりも、「望ましい回答を構成するTokenへ高い確率を割り当てられるようになる」という形で、その学習が現れます。

先ほどまでの話では、モデルへ入るものは最初から `[1.0, 2.0, 3.0]` のような数値でした。
しかしLLMへ入るのは文章なので、そのままではWeightとの計算ができません。

そこで、文章をいったん **Token ID** に変え、そのIDをさらに「計算に使える数値のまとまり」へ変換します。
この後半を担当するのがEmbeddingです。

## Token IDとEmbeddingは別物

たとえば、説明用に次のような対応表があるとします。

```text
ID 0 = <pad>
ID 1 = 猫
ID 2 = 犬
ID 3 = りんご
ID 4 = みかん
```

文章が、

```text
猫 犬 猫
```

なら、Tokenizerがまず、

```text
[1, 2, 1]
```

へ変換します。

ただし、この `1` や `2` は単なる識別番号です。

```text
猫 = 1
犬 = 2
```

だからといって、

```text
犬は猫の2倍
```

という意味ではありません。

同様に、

```text
猫 = 1
りんご = 3
```

だから「りんごは猫より3倍何かが強い」という意味にもなりません。

そのため、Token IDそのものをニューラルネットワークの数値として扱うのは都合が悪いのです。

## EmbeddingはIDごとの数値表を持つ

そこで、各Token IDに対して複数の数値を割り当てます。

たとえば4次元Embeddingなら、概念的には次のような表になります。

```text
ID 0 <pad>   → [ 0.12, -0.31,  0.05,  0.82]
ID 1 猫      → [ 0.73,  0.21, -0.42,  0.15]
ID 2 犬      → [ 0.68,  0.18, -0.37,  0.24]
ID 3 りんご  → [-0.13,  0.92,  0.61, -0.20]
ID 4 みかん  → [-0.08,  0.87,  0.55, -0.15]
```

すると、

```text
猫 犬 猫
```

は、

```text
[1, 2, 1]
```

を経由して、

```text
[
  [ 0.73, 0.21, -0.42, 0.15],
  [ 0.68, 0.18, -0.37, 0.24],
  [ 0.73, 0.21, -0.42, 0.15]
]
```

へ変わります。

この数値なら、先ほど扱ったWeightとの行列計算に使えます。

## この数値にも、最初は意味がありません

ここはWeightの話と同じです。

最初から、

```text
猫      → 動物っぽい数字
りんご  → 果物っぽい数字
```

が設定されているわけではありません。

Embeddingも最初はランダムなParameterです。

学習を繰り返すうちに、

```text
猫と犬は似た文脈に出やすい
りんごとみかんも似た文脈に出やすい
猫とりんごでは使われ方がかなり違う
```

という情報がLossを通して反映され、Embeddingの値も少しずつ変更されます。

その結果として、学習後には「似た使われ方をするTokenのベクトルが似た特徴を持つ」という現象が現れます。

ただし、4つの数値それぞれに、

```text
1個目 = 動物度
2個目 = 果物度
```

のような、人間が読める意味が必ず割り当てられるわけではありません。
意味は多数の次元に分散して表現されます。

## 実際にPyTorchでEmbeddingを作る

今回はまだTokenizerを使わず、Token IDを手で用意します。

プロジェクトで、

```bash
nano embedding_demo.py
```

を作って、次を入れてください。

```python
import torch

torch.manual_seed(42)

device = "cuda"

# Token数は5個、各Tokenを4個の数値で表現する
embedding = torch.nn.Embedding(
    num_embeddings=5,
    embedding_dim=4
).to(device)

print("=== Embedding全体 ===")
print(embedding.weight)

print("\nShape:")
print(embedding.weight.shape)

# 「猫 犬 猫」に相当するToken ID
token_ids = torch.tensor(
    [1, 2, 1],
    device=device
)

print("\n=== Token IDs ===")
print(token_ids)

vectors = embedding(token_ids)

print("\n=== Embedding後 ===")
print(vectors)

print("\nShape:")
print(vectors.shape)

print("\n=== 1個目と3個目は同じTokenか ===")
print(torch.equal(vectors[0], vectors[2]))
```

実行は、

```bash
uv run python embedding_demo.py
```

です。

## コードの意味

今回の、

```python
torch.nn.Embedding(
    num_embeddings=5,
    embedding_dim=4
)
```

では、5種類のTokenについて、それぞれ4個の数値を持たせています。

したがって内部には、

```text
5行 × 4列
```

のParameterがあります。

つまり、学習可能な値は20個です。

```text
Token 0 → 4 Parameter
Token 1 → 4 Parameter
Token 2 → 4 Parameter
Token 3 → 4 Parameter
Token 4 → 4 Parameter
```

そのため、

```python
print(embedding.weight.shape)
```

は、

```text
torch.Size([5, 4])
```

になります。

## `embedding(token_ids)` は何をしているのか

今回、

```python
token_ids = torch.tensor([1, 2, 1])
```

を渡しています。

するとEmbeddingは、自分が持っている表から、

```text
1行目
2行目
1行目
```

を取り出します。

つまり、計算というより最初の段階では **検索表から該当する行を取ってくる** と考えると分かりやすいです。

```text
Embedding Table

ID 0 → [...]
ID 1 → [A, B, C, D]  ← 猫
ID 2 → [E, F, G, H]  ← 犬
ID 3 → [...]
ID 4 → [...]

入力
[1, 2, 1]

        ↓

出力

[
 [A, B, C, D],
 [E, F, G, H],
 [A, B, C, D]
]
```

そのため、最初と3番目は同じToken ID `1` なので、

```python
torch.equal(vectors[0], vectors[2])
```

は、

```text
True
```

になります。

## LLMではこれが巨大になる

今回のEmbeddingは、

```text
Token数   = 5
次元数    = 4

5 × 4 = 20 Parameter
```

しかありません。

実際のLLMでは、たとえば概念的に、

```text

100,000 Token

Embedding dimension
4,096
```

なら、

```text
100,000 × 4,096
= 409,600,000 Parameter
```

となります。

Embeddingだけで数億Parameterになることもあります。

文章が、

```text
「日本の首都はどこですか？」
```

なら、まずTokenizerが、

```text
文章
 ↓
Token
 ↓
Token ID
```

へ変換し、その後Embeddingによって、

```text
Token ID
 ↓
大量の数値を持つベクトル
```

へ変換します。

そこから先で、Transformerがそのベクトル同士の関係を計算します。

現時点では、

**Tokenizerは文字列をIDへ変え、EmbeddingはIDを学習可能な数値ベクトルへ変える**
