# Azure SRE Agent / AWS DevOps Agent 記事ナレッジ

## 1. このナレッジの目的

Azure SRE Agent と AWS DevOps Agent について、社内向けニュース記事として整理した内容を残す。

今回の記事は「使ってみた感想」ではなく、2026年に Microsoft と AWS が相次いでクラウド運用向け AI エージェントを一般提供したことをニュースとして紹介する。

読者はエンジニアリング初学者を想定する。
そのため、CI/CD、テレメトリ、Runbook などの専門用語を前面に出さず、「監視情報だけでなく、ソースコードの変更履歴なども見ながら原因を調べられる」といった粒度で説明する。

文章量は少なめにし、処理の流れ、役割分担、比較などは画像で理解できる構成とする。

---

## 2. 記事で伝えたいこと

Azure SRE Agent と AWS DevOps Agent は、単なるログ要約 AI ではない。

障害が起きたあとに、システムの状態、エラーログ、ソースコードの変更履歴、過去の障害情報などを確認し、原因候補を整理して対応案を人間へ提示するところまでを担う。

保守では毎回同じ障害が発生するとは限らないため、従来の「決められた条件で決められた処理を実行する自動化」だけでは対応しにくかった。
今回のサービスが興味深いのは、異常検知の後にある「何が起きたのかを調べる」仕事まで AI の対象になったことである。

## 4. Azure SRE Agent

Azure SRE Agent は、Azure 上で動くシステムについて、状態、ログ、ソースコードなどを確認しながら障害原因を調査する AI エージェント。

単一のエラーログを見るだけではなく、「直前にどのような変更があったか」なども合わせて確認し、原因候補や対応方法を提示できる。
設定した権限の範囲では、復旧操作まで実行させる構成も可能。

Microsoft は自社サービスでも Azure SRE Agent を利用しており、2026年3月の一般提供時点で、1,300以上のエージェントを展開し、35,000件以上のインシデントを軽減したと公表している。

### 初学者向けの説明

> Azure 上で問題が起きたときに、ログだけでなくシステムの状態や最近のソースコード変更などを確認し、原因候補と対応方法を整理してくれる AI エージェント。

---

## 5. AWS DevOps Agent

AWS DevOps Agent も、システムの状態やソースコードの変更履歴などを確認しながら、障害原因を調査する AI エージェント。

AWS 環境だけではなく、Azure やオンプレミス環境も調査対象にできる点が特徴。
障害発生時の原因調査だけではなく、システム運用上の改善点を調べる用途にも利用できる。

### 初学者向けの説明

> AWS や Azure、社内サーバーなどで問題が起きたときに、システムの状態や変更履歴を調べ、原因候補と対応方法を整理してくれる AI エージェント。

---

## 6. Azure と AWS の違い

| 項目 | Azure SRE Agent | AWS DevOps Agent |
| --- | --- | --- |
| 主な用途 | Azure 環境を中心とした SRE・運用支援 | 複数環境をまたいだ DevOps・運用支援 |
| 原因調査 | 可能 | 可能 |
| ソースコード変更履歴を含めた調査 | 可能 | 可能 |
| 対応案の提示 | 可能 | 可能 |
| 復旧操作 | 権限設定に応じて可能 | 承認を含む変更操作を実行可能 |
| 対応環境 | Azure 中心 | AWS、Azure、オンプレミス |

記事では、詳細な機能一覧よりも「どちらも障害調査まで AI が入る」という共通点を主題にする。

---

## 7. AI と人間の役割分担

すべての処理を AI へ任せる必要はない。

AI は異常検知後の情報収集、原因候補の整理、対応案の作成を担当し、人間は提案内容を確認したうえで、本番環境へ変更を加えるか判断する構成にできる。

導入初期は、調査と提案だけ AI に任せ、復旧操作は人間が行う構成が現実的。

---

## 8. 自社製品の外販との組み合わせ

自社で開発したツールを外部へ販売すると、販売先が増えるほど保守負担も増えやすい。
ソフトウェア自体は複数社へ展開できても、障害を調査するエンジニアの時間は同じようには増やせない。

そこで、販売したシステムの状態、ログ、ソースコード変更履歴などを AI エージェントが確認できるようにしておけば、一次保守を AI に任せる構成が考えられる。

```text
お客様環境
    ↓
障害発生
    ↓
AIエージェントが一次調査
    ↓
原因候補 + 対応案
    ↓
自社の保守担当者
    ↓
人間が判断・対応
```

この構成であれば、保守担当者が毎回ゼロから情報収集を始める必要を減らせる。
「製品へ AI 機能を追加する」というより、「販売後の保守サービスに AI エージェントを組み込む」という捉え方が近い。

## 9. 導入時の考え方

Microsoft や AWS が提供元であることは、企業導入を検討するうえで材料になる。
ただし、提供元への信頼と、AI が個別障害の原因を正しく判断できることは別の問題。

お客様環境へすぐに導入するのではなく、まず検証環境や社内システムで、原因候補の精度、必要な情報の取得可否、誤提案への気付きやすさ、権限範囲、費用を確認する。

最初は読み取りと原因調査を中心に使い、実績を見ながら任せる範囲を広げる方針が適している。

## 10. 料金

### AWS DevOps Agent

AWS DevOps Agent は、AI エージェントが実際に処理した時間に応じた秒単位の従量課金。

2026年時点の AWS 公式例では、月10件のインシデントを1件あたり平均8分調査した場合、月額 39.84 ドル。
周辺の AWS サービス利用料は別途発生する。

### Azure SRE Agent

Azure SRE Agent は Azure Agent Units（AAU）を使用する。
料金は、エージェントを利用できる状態にしておく分と、実際に AI が処理した分から構成される。

AWS と Azure では課金方式が異なるため、障害件数だけで単純比較するのではなく、実際の利用方法を想定して評価する必要がある。

## 11. SharePoint記事用の短縮本文

# AzureとAWS、AIエージェントをクラウド運用へ

MicrosoftとAmazon Web Services（AWS）が、AIエージェントをクラウド運用へ本格的に投入しています。

Microsoftは2026年3月に**Azure SRE Agent**、AWSも同月に**AWS DevOps Agent**の一般提供を開始しました。
どちらも単にログを要約するAIではなく、障害が起きたときにシステムの状態やソースコードの変更履歴まで調べ、原因候補と対応案を人間へ提示できます。

## 障害対応の「調査」までAIが担当する

これまでの自動化は、異常を検知して人間へ知らせるところが中心でした。
今回の2サービスでは、その後の情報収集と原因調査までAIが進め、人間は整理された原因候補と対応案を受け取れます。

## 監視情報だけを見ているわけではない

例えばエラーが増えた場合、現在のシステム状態だけでなく、「直前にソースコードが変更されていないか」といった情報も合わせて原因を探します。

## Azure SRE Agent

Azure上のシステム状態、ログ、ソースコードなどを調査し、原因候補と対応方法を提示します。
設定した権限の範囲では、復旧操作まで任せることもできます。

## AWS DevOps Agent

システム状態やソースコードの変更履歴などから障害原因を調査します。
AWSだけでなくAzureやオンプレミスも調査対象にできるため、複数環境を利用するシステムにも対応できます。

## 人間の判断は残せる

原因調査をAIへ任せても、本番環境を変更する最終判断まで自動化する必要はありません。
まずは調査と提案をAIへ任せ、人間が承認して対応する構成から始められます。

## 自社製品の保守にも使える可能性

販売先で障害が起きたとき、AIが一次調査を行い、原因候補と対応案を整理して保守担当者へ通知できれば、人間が毎回ゼロから調査を始める負担を減らせます。

## 料金の考え方

AWS DevOps Agentは、AIが実際に処理した時間に応じた従量課金です。
AWSの公式例では、月10件の障害を1件平均8分調査した場合に39.84ドルとされています。

Azure SRE Agentは、エージェントを利用できる状態にしておく料金と、実際のAI処理量に応じた料金を組み合わせる方式です。

## クラウド保守にもAIエージェントが入ってきた

変わり始めているのは、監視の自動化だけではありません。
障害が起きてから原因を調べ、対応案を作って人間へ知らせるところまでが、AIエージェントの担当になり始めています。

## 12. 作成した画像

記事用として9枚作成した。

### 01. Azure SRE Agent と AWS DevOps Agent の登場

記事冒頭で今回のニュース全体を理解させる画像。
Azure SRE Agent、AWS DevOps Agent、2026年3月の一般提供、クラウド運用へ AI エージェントが入ってきたことを表現する。

推奨比率：16:9

### 02. 従来の障害対応と AI エージェント導入後

従来は「異常発生 → 人間が調査 → 原因特定 → 対応」、AI 導入後は「異常発生 → AI が調査 → 原因候補・対応案 → 人間が判断 → 対応」という Before / After を示す。

### 03. AI が原因を調べるために見る情報

「システムの状態」「エラーログ」「ソースコードの変更履歴」「過去の障害情報」を中央の AI エージェントへ集約し、監視結果だけを見ているわけではないことを示す。

### 04. Azure SRE Agent の役割

「Azure上のシステム → Azure SRE Agent → 原因候補 → 対応案 → 必要に応じて復旧」という流れを示す。

### 05. AWS DevOps Agent の役割

AWS、Azure、オンプレミスから AWS DevOps Agent へ情報が入り、システム状態の確認、変更履歴の調査、原因候補の提示を行うことを示す。

### 06. AI と人間の役割分担

「異常検知 → 原因調査 → 対応案作成 → 人間が承認 → 復旧対応」という流れで、AI にすべてを任せる必要はないことを示す。

### 07. 自社製品の一次保守

複数のお客様環境から AI エージェントへ情報が集まり、原因候補と対応案が自社の保守担当者へ届く構成を示す。

### 08. AWS と Azure の料金体系

AWS は「AI が実際に動いた時間に応じて課金」、Azure は「利用できる状態の料金 + AI が処理した量」という考え方の違いを示す。

### 09. 記事のまとめ

「異常発生 → AI が調査 → 原因候補 → 人間へ通知」という最小フローで、記事全体の結論を再確認する。
