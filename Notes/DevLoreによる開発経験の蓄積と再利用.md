# DevLoreによる開発経験の蓄積と再利用

**DevLore** は、筆者が設計している、過去の開発資料や仕事の経験を根拠付きの知識へ変え、人間やAIが次の仕事で再利用できるようにする仕組みである。
名前はDevelopment（開発）とLore（蓄積された知識・伝承）を組み合わせたものである。
二つの記事で扱われており、このノートはその内容をDevLore中心にまとめ直したものである。
一つは組織の経験蓄積を論じた [[AIを使う会社から、経験を蓄積できる会社へ|AIを使う会社から、経験を蓄積できる会社へ]]、もう一つはAI開発プロジェクト群を紹介した [[AIに仕事を任せるために作っているプロジェクト|AIに仕事を任せるために作っているプロジェクト]] である。

記事時点の状態は「検索・Ranking実験を継続中」であり、以下の多くは設計方針として読む必要がある。

## 解こうとしている問題は「見つかる」と「使える」の差である

会社には設計書、仕様書、レビュー記録、障害票、議事録などが大量に残っている。
しかし、文書が保存されていることと、経験として再利用できることは違う。

一つ目の問題は、判断の経緯が残らないことである。
最初の設計書、障害票、修正版の設計書が残っていても、なぜ最初の設計を採用したのか、どの条件で失敗したのか、なぜ変更したのか、今回にも当てはまるのかは残りにくい。
単純な全文検索や類似度検索では、最初の設計書だけを見つけて「過去もこの構成だった」と誤る可能性がある。

二つ目の問題は、検索結果に性質の違う情報が混ざることである。
現在の社内規程は従う規範、過去案件の設計書は参考事例、障害票は問題が起きた根拠、修正版設計書は変更後の結果、別案件の成功事例は再利用候補、担当者の振り返りは判断材料である。
同じ「関連文書」として並べると、この違いが失われる。

三つ目の問題は、仕様書にきれいに残っていない知識である。

- この顧客では以前この表現を指摘された。
- この種類の変更では、いつもここを確認している。
- 設計上は問題なさそうでも、この会社ではこの作り方を避けている。

長く担当している人は覚えていても、新しく参加した人やAIエージェントは知らない。

DevLoreの目標は、「この資料が見つかった」状態から「この資料は今回どのような立場で利用できるのか」が分かる状態へ進めることである。
筆者は、過去の情報をたくさん集めることより、過去の情報を誤った意味で使わないことの方が重要だとしている。

## 知識と一緒に保持する属性

DevLoreは、知識を次の属性と一緒に扱う。

- 出所（どの文書のどの記録か）
- 版情報
- 今回の仕事との関係
- 規範か参考事例か
- 根拠（Evidence）
- 他の情報との矛盾
- 人間判断が必要か
- 適用条件

## 検索から根拠付きの知識候補を返す流れ

プロジェクト紹介記事の機能図は、DevLoreの処理を次のように描いている。

![[Assets/Images/AI Projects Overview/04-DevLoreによる開発経験の再利用.webp]]

```text
過去の開発資料・記録（社内に蓄積された情報）
  設計書、仕様書、レビュー記録、過去の指摘（課題・コメント）、
  対応記録（対応履歴）、開発ドキュメント（手順・運用など）、過去の判断や作業履歴
↓ 取り込み（Import）
DevLore
  Discover：利用可能な文書や情報源を見つける
  ↓
  Search：現在の作業に関係する過去情報を検索する
  ↓
  Candidate Selection：関連性のある候補を絞り込む
  ↓
  Ranking：現在の作業との関連性やEvidenceとの近さで順位付けする
  ↓
  Duplicate整理：似た内容の重複・近い候補を整理する
  ↓
  Evidence / Provenance：どの文書のどの記録を根拠にしているかを保持する
  ↓
  Resolve / Read：候補から元文書や詳細情報を参照できる
  （土台：過去の開発資料のナレッジベース＝文書・記録・メタデータ・Evidence情報）
↓
検索結果（Knowledge候補＋Evidence）
↓
利用する人／AI
↓
確認・判断（利用側）
↓
必要に応じて採用（別のAuthority）
```

検索結果は種類ごとにEvidenceを伴って返される。
図中の例は説明用である。

| 返る知識候補 | 内容 | Evidenceの例 |
|---|---|---|
| 関連Knowledge候補 | 今回の作業に関係しそうな過去の知識 | 設計書A のp.12「〜と判断した」 |
| 過去のレビュー観点 | 過去に議論された観点 | レビュー記録B のコメント「〜を確認すべき」 |
| 過去の指摘 | 類似の指摘・注意点 | 課題管理C の指摘「〜に問題があった」 |
| 類似した設計上の注意点 | 似た設計パターンでの注意点 | 設計書D のp.8「〜に注意する」 |

利用者として図に挙がっているのは次の四者である。

- **AIエージェント**：開発作業の調査・検討に使う。
- **開発者**：設計・実装・レビュー時の参考にする。
- **Arthur**：開発支援で使う。
- **AI-DE**：開発プロセスで使う。

## 見つけることと採用することを分ける

DevLoreの中心的な設計判断は、知識を見つけることと、それを現在のプロジェクトで採用することを分けることである。

過去に何度も同じ指摘があっても、それが今も有効な会社ルールなのか、特定案件だけの判断だったのかは別の話である。
過去に採用された方法が現在も正しいとは限らない。
顧客、システム、技術、制約が変われば、過去の成功例が今回も成功する保証はない。

そのためDevLoreは、過去事例から抽出した手順（Playbook）や判断を、そのまま現在の規範へ自動昇格させない。
渡すのは判断材料である。

- 過去にはこの方法を採用した。
- この条件では問題が発生した。
- この根拠で別の方法へ変更した。
- この条件なら再利用できる可能性がある。
- この点は今回あらためて人間が判断する必要がある。

利用側は内容を確認し、現在のコンテキストに合うかを判断し、必要なら元文書も参照する。
現在の要求や設計へ採用する、または正式なルールや要求として決定するのは、DevLoreとは **別の権限（Authority）**である。
プロジェクト群の中では、現在有効な要求と判断を保持するのはArthurの役割になっている。

熟練者の頭の中だけにあった経験を使えるようにしながら、AIが勝手にルールを増やさない。
DevLoreはこの両方を成立させるための仕組みとして作られている。

## 既存資料の再利用から、仕事から知識を作る循環へ広げた

当初のDevLoreは、既存の設計書や障害票などをAI開発で使いやすくすることが中心だった。
しかしそれだけでは、過去に残された情報を読みやすくしているだけで、今の仕事から次の仕事へ経験を渡す仕組みにはならない。

経験蓄積の記事では、案件終了時などに次を抽出する循環へ役割を広げている。

- 何を試したか。
- 何がうまくいったか。
- 何が失敗したか。
- なぜ判断を変更したか。
- 次回なら何を変えるか。
- 別案件でも使えそうなものは何か。

```text
仕事をする
↓
成功、失敗、レビュー、判断変更が生まれる
↓
再利用できる経験をKnowledge候補として整理する（AIが候補を作る）
↓
出所、根拠、適用条件を保持する
↓
人間が確認する
↓
次の仕事で利用する
↓
利用結果から新しい経験が生まれる
```

人間の確認を経ないものを、再利用可能な知識として扱わない。
プロジェクト紹介記事の図では、AI-DE側にも「実プロジェクトで得られた知見を再利用できるKnowledge候補として保存する」知識循環の機能があり、DevLoreと接続する経路として読める。
ただし、AI-DEとDevLoreの間で候補をどう受け渡すかの具体的な仕様は、資料には書かれていない。

## 現在の仕事の文脈は既存製品に任せる

会社中の情報をDevLoreへ集める必要はない。
Microsoft 365を使う会社なら、メール、会議、チャット、資料はOutlook、Teams、SharePoint、OneDriveにある。
Microsoft Copilot側が検索、現在の仕事の文脈（Context）、Microsoft 365の権限管理を担えるなら、DevLoreで同じ機能を作り直さない。

| 領域 | 主な役割 |
|---|---|
| Microsoft 365 / Copilot | 現在進行中の仕事の文脈を使って仕事を支援する |
| DevLore | 案件を越えて残したい経験を、出所・根拠・適用条件付きで整理し、次の仕事から再利用できる状態にする |

DevLoreが集中するのは、Microsoft側ではそのまま残りにくい「仕事から何を学ぶか」「その知識をどの条件で使えるか」「どの根拠から生まれたか」である。
DevLoreはCopilotの代替でも、Copilot専用の機能でもない。
Microsoftを使わない環境でも、別の文書基盤やAIと接続して使える前提にしている。

![[Assets/Images/From Using AI to Accumulating Experience/07-DevLoreと業務の連携.webp]]

```text
入力
├─ Microsoft 365 / Work IQ / Copilot：現在の仕事のContext、検索、権限管理
└─ その他の情報基盤 / AI：社内文書、業務システム、AI Agent / ローカルLLM
↓
DevLore：経験を抽出 → Evidence・出所を保持 → 適用条件を整理 → 人間が確認 → 次の仕事へ再利用
↓
出力先：Copilot、AI Agent、AI-DE、人間
```

## プロジェクト群の中では交換可能なDocument Assetの一つである

日本ハーネス（Japan-Harness）の構想では、各機能を特定のリポジトリに固定せず、「この役割を満たすProvider」として接続する。
DevLoreは「過去の開発知識（過去資料からKnowledge候補）」の枠に置かれている。
ただしDocument AssetもDevLoreに固定せず、必要な能力を満たす別の仕組みを選べるようにする、とされている。

隣接するプロジェクトとの分担は次のとおりである。

| プロジェクト | DevLoreとの関係 |
|---|---|
| Arthur | 現在有効な要求と判断を保持する。DevLoreの知識候補を採用するかの判断は、DevLoreではなく利用側の権限に属する |
| AI-DE | 開発プロセスでDevLoreを参照する。実プロジェクトで得た知見をKnowledge候補として保存する機能を持つ |
| Software-Test-Knowledge | テストに関する一般的な知識を別に提供する。資料から読む限り、過去の開発資料やレビュー経験はDevLore、プロジェクトをまたぐ汎用的なテスト観点はSoftware-Test-Knowledgeという分け方になる |

## 未確定のこと

- 記事時点で検索とRankingの実験を継続中であり、方式は確定していない。
- 実際に組織へ導入する場合、どこまで社内情報へアクセスさせるか、権限やセキュリティをどう設計するかは未定である。
- 筆者自身、DevLoreのような仕組みを実際にどこまで作れるかについて、完成した答えを持っていないとしている。
