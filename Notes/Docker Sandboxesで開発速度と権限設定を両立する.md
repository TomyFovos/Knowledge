# Docker Sandboxesで開発速度と権限設定を両立する

AIエージェントへ開発を任せる範囲が広がるほど、権限確認が開発速度の制約になる。
そこで強い権限を与えたくなるが、会社PCそのものへ与えると影響が開発対象の外まで届く。
元資料は、Docker Sandboxesを使い、壊れても作り直せる隔離環境の中だけへ強い権限を与える考え方を整理している。
中心となる考え方は、元資料の言葉で次の一文である。

> AIエージェントを毎回止めるのではなく、止めなくてもよい範囲を先に作る。

## 並列開発では人間の承認がボトルネックになる

AIエージェントは、ファイル編集やコマンド実行の前に人間の承認を求めることがある。
この確認を **権限確認（Permission）**と呼ぶ。

一体のAIエージェントを人間が横で見ながら使うなら、操作のたびに承認しても大きな問題にはならない。
しかし、複数のAIエージェントへ仕事を分けて並列で動かすと、それぞれが数分おきに承認を求める。
その結果、人間がボトルネックになる。

そこで、確認なしで何でも実行できる **全権限（Full Access）**を使いたくなる。
ただし、会社PCそのものへ全権限を与えると、開発対象以外のファイル、設定、認証情報、別プロジェクトにも影響が届く可能性がある。

元資料の方針は、会社PC全体への全権限ではなく、隔離環境の中だけへ全権限を与えることで、開発速度と安全性の両立を目指すことである。

## 問題は全権限そのものではなく、権限が届く範囲である

**サンドボックス（Sandbox）**は、あるプログラムが自由に動いてよい範囲を先に区切り、その外側へ影響が広がりにくくする考え方である。
AIエージェントの場合は、会社PCの中に「AIが自由に使ってよい別の作業場所」を作ると考えると分かりやすい。
AIはその中でファイルを編集し、開発ツールを追加し、テスト環境を構築し、必要な処理を実行できる。

ここで見るべきなのは、全権限という設定が危険かどうかではない。
その権限がどこまで届くかである。
会社PCそのものへ全権限を与えた場合と、サンドボックス内部だけへ全権限を与えた場合では、同じ「全権限」でも影響範囲が違う。

| 与え方 | 権限が届く範囲 |
|---|---|
| 会社PCそのものへ全権限 | 社内ファイル、別プロジェクト、認証情報、開発者の設定まで届き得る |
| サンドボックス内部だけへ全権限 | サンドボックス内の開発対象、開発ツール、テスト環境に閉じる |

## Docker Sandboxesは「AI用の小さな別PC」と考える

隔離の仕組みには段階がある。

- **コンテナ（Container）**：ホスト側のOSの中核部分である **カーネル（Kernel）**を共有しながら、プロセスやファイルシステムを分離する。
- **仮想マシン（VM）**：仮想的なコンピューターを一台作り、その中に独立したカーネルを持つ。
- **マイクロVM（microVM）**：VMに近い隔離を、AIエージェント用途で扱いやすい形にしたものとして理解する。

Docker Sandboxesは、サンドボックスごとに独立したmicroVMを使う。
通常のDockerコンテナへAIを入れているだけではない、という点がDockerを知っている人向けの補足になる。

IT初学者へ説明するときは、内部技術を先に出さない。
「会社PCの中にAI専用の小さな別PCを作る」と説明する方が伝わりやすい。

## 目的はAIを弱くすることではない

Docker Sandboxesを使う目的は、AIエージェントの能力を制限することではない。
むしろ、サンドボックス内部ではファイル編集、開発ツールの追加、テスト環境の構築、Dockerの利用などを広く許す。
その自由が会社PC全体へ広がらないようにする。

```text
会社PC
  ├─ 社内ファイル
  ├─ 別プロジェクト
  ├─ 認証情報
  └─ 開発者の設定

        境界

  Docker Sandbox
  ├─ AI Agent
  ├─ 開発対象
  ├─ 開発ツール
  ├─ テスト環境
  └─ Sandbox専用の実行環境
```

AIがサンドボックス内部の環境を壊しても、削除して作り直せるなら、人間が操作を一つずつ承認する必要を減らせる。
承認を減らせる根拠は「壊れても作り直せる」ことにある。

## サンドボックスは完全密閉ではなく、出入口が安全性を左右する

サンドボックスは、導入しただけで安全を保証する仕組みではない。
AIエージェントが実際に開発するには、ソースコード、外部ネットワーク、認証情報、MCPなど、サンドボックスの外側とつながる経路が必要になる。

そのため、安全性は「サンドボックスがあるか」ではなく、「サンドボックスの外へ何を接続しているか」で確認する。
元資料が整理した主な出入口は次の四つである。

| 出入口 | 確認すること |
|---|---|
| ソースコード | 会社PC側の開発対象を、どのようにAIへ渡すか |
| ネットワーク | どの外部サービスへ接続できるか |
| 認証情報 | APIキーやパスワードを、AIへどのように使わせるか |
| MCP | サンドボックス外のツールやシステムへ、どこまで操作を許すか |

サンドボックスの境界そのものより、これらの出入口の設定が実際の安全性を左右する場合がある。

元資料は、隔離環境の中のAIが、許可されたサービスや設定上の隙間を経由して外部へ到達した事故の紹介を記事の導入にしている。
参考資料に挙がっているOpenAIのHugging Face事案の記事が、この事故紹介に対応すると考えられる（記事との対応は元資料に明記されていない）。
伝えたいことは、箱だけでなく、外へつながる経路全体を見る必要があるという点である。

## ソースコードの渡し方にはDirect modeとClone modeがある

ソースコードをAIへ渡す方法として、二つの方式がある。

**Direct mode**は、会社PC側の開発フォルダをサンドボックスから直接操作する方式である。
AIの変更が会社PC側へすぐ反映されるので、対話的な開発に便利である。
一方、AIが誤ってファイルを削除した場合も、その変更が会社PC側へ届く。

**Clone mode**は、サンドボックス内部へ作業用のコピーを作り、AIにはそのコピーを編集させる方式である。
会社PC側の元ファイルをその場で書き換えないため、AIの変更を確認してから取り込める。
複数AIの並列開発や、AIの変更を人間がレビューしてから統合したい場合に扱いやすい。

| 比較軸 | Direct mode | Clone mode |
|---|---|---|
| AIが編集する対象 | 会社PC側の開発フォルダ | サンドボックス内の作業用コピー |
| 変更の反映 | すぐ会社PC側へ届く | 確認してから取り込む |
| 向く場面 | 対話的な開発 | 複数AIの並列開発、レビュー前提の統合 |
| 誤操作の影響 | 会社PC側へ届く | コピー内にとどまる |

ただし、Clone modeは元ファイルを「書き換えられない」ための仕組みであり、「読めない」ための仕組みではない。
Git管理外のファイルや `.gitignore` 対象のファイルでも、会社PC側のリポジトリ配下に置かれていれば、AIから読める可能性がある。
そのため、秘密情報の扱いはClone modeとは別に設計する。

## Credential Proxyは秘密を隠すが、権限は消さない

APIキーやパスワードをサンドボックスへそのまま渡すと、AIやサンドボックス内で動くプログラムがその値自体を読める。

Docker Sandboxesでは、**認証情報の代理（Credential Proxy）**を使える。
秘密の値そのものはAIへ渡さず、外部サービスへアクセスするときだけ、代理役が認証情報を付ける考え方である。

```text
AI Agent
   │
   │ 「GitHubでこの操作をしたい」
   ▼
Credential Proxy
   │
   │ 保存している認証情報を利用
   ▼
外部サービス
```

AIから見ると「サービスは使えるが、APIキーやパスワードそのものは知らない」状態になる。

ただし、その認証情報が持つ権限まで消えるわけではない。
たとえばGitHubへのpush権限を持つ認証情報を使わせれば、AIはトークンそのものを知らなくてもpushできる。
「秘密を見せないこと」と「その権限で何をしてよいか」は別の問題として扱う。

## ネットワークは必要な接続先だけに絞る

サンドボックスからインターネットへ自由に接続できれば、GitHubや外部AIサービスを使いやすい。
一方で、それはサンドボックス内部の情報を外へ送る経路にもなる。
そのため、開発に必要なサービスだけへ接続できるようにネットワークを制御する。

```text
許可
  ├─ GitHub
  ├─ 利用中のAIサービス
  ├─ 必要なPackage Registry
  └─ 必要なAPI

遮断
  ├─ 不要なWebサイト
  ├─ 個人用クラウド
  ├─ 不要な社内システム
  └─ その他の未許可接続
```

サンドボックス内部で強いファイル権限を与えることと、インターネットを無制限に使わせることは同じではない。
内部では自由に開発させながら、外部との通信先だけを狭くできる。

## MCPはネットワークとは別の出口になる

**MCP（Model Context Protocol）**を使うと、AIエージェントから外部のツールやシステムを操作できる。
便利な一方で、MCPはサンドボックスの外へ能力を追加する別の出口になる。

たとえば、会社PC上で動くMCPサーバーにホストのファイルシステムを操作する機能があるとする。
サンドボックス内のAIがそのMCPを呼び出せば、サンドボックス外のファイルへ操作が届く場合がある。

このとき、AIはサンドボックスを破ったわけではない。
人間が用意したMCPという正規の通路を使って外側へ操作している。

したがって、ネットワークの制御方針だけを見ても不十分である。
MCPについても次を別に確認する。

- どのサーバーを使えるか。
- どのツールを呼べるか。
- どこまで操作できるか。

「サンドボックスに入っているからMCPも自動的にサンドボックス内へ閉じる」という理解は誤りである。

## 三つの隔離は別々に考える

元資料の理解度テストでは、次の三つを混同しやすいことが分かった。
それぞれが守るものは違う。

| 隔離 | 扱うこと | 守れないこと |
|---|---|---|
| **作業領域の隔離（Workspace isolation）** | ホストのコードへ書けるか、読めるか | Clone modeは元ファイルを書き換えにくくするが、元リポジトリを読めなくはしない |
| **認証情報の隔離（Credential isolation）** | APIキーやパスワードの実値をAIへ見せない | 認証情報に許された操作そのものは禁止されない |
| **MCPの隔離（MCP isolation）** | MCPサーバーとツールの権限 | ネットワークを制限してもMCPは安全にならない。別に管理する |

修正した誤解は次の三つである。

- Clone modeなら元リポジトリの秘密も読まれない、という誤解。
- Credential Proxyを使えば危険な操作もできなくなる、という誤解。
- ネットワークを絞ればMCP経由の操作も防げる、という誤解。

## 複数エージェントは「何を分離したいか」で分ける

Docker Sandboxesは、AIエージェント同士の環境を分ける用途にも使える。
エージェントA、B、Cを別々のサンドボックスへ置けば、それぞれが独立した開発環境を持てる。

```text
Windows会社PC
   │
   ├─ Sandbox A
   │    └─ Agent A
   │
   ├─ Sandbox B
   │    └─ Agent B
   │
   └─ Sandbox C
        └─ Agent C
```

エージェントAが開発ツールや設定を変更しても、その変更がBやCの環境へそのまま広がらない。

ただし、すべてのAIを必ず別サンドボックスへ分ける必要はない。
同じ環境を共有しながら協力させたいエージェントは同じサンドボックスへ置く。
互いの環境に影響してほしくないエージェントは別サンドボックスへ分ける。
判断基準はAIの数ではなく、何を分離したいかである。

## 統括役には限定された制御口だけを渡す

学習中には、統括役のエージェントAがワーカーB、C、Dを管理し、各ワーカーをさらに別のmicroVMへ入れる構成を検討した。
統括役だけが全体を把握し、ワーカー同士を独立させるという狙いは正しい。

ただし、Docker Sandboxesの標準的な使い方として、サンドボックスの内部へさらにDocker SandboxのmicroVMを入れ子にする形を前提にする必要はない。

独立性を重視するなら、ホスト側に複数のサンドボックスを並べる。
その上で、**統括役（Orchestrator）**には、ワーカーの作成、指示、状態確認、成果の回収など、必要な操作だけを許す専用の制御口を用意する。
元資料は、この構成の方が安全だとしている。

```text
Orchestrator
     │
     │ 限定された制御
     ▼
Orchestration Interface
   ├─ Sandbox B
   ├─ Sandbox C
   └─ Sandbox D
```

この部分はDocker Sandboxes単体の知識から一歩進み、AIエージェントの **ハーネス（Harness）**や実行ハーネスの設計領域になる。

## サンドボックスはA/Bテストの実験単位にもなる

サンドボックスを複数作れることは、AIエージェントのA/Bテストにも使える。
エージェントAとBを比較するとき、エージェント以外の条件を揃えなければ、結果の差がAIによるものか環境によるものか分からない。

揃える条件の例は次のとおりである。

- CPU
- メモリ
- 元になるGitのコミット
- 開発ツール
- ネットワーク条件
- テスト方法
- 評価条件

元資料の図では、同じ環境、同じデータ、同じタスク、同じ設定を用意することとしている。
そのうえで、比較したいものだけを変える。

```text
同じ条件
   │
   ├─ Sandbox A → Agent A
   │
   └─ Sandbox B → Agent B
```

- エージェントを比較するなら、エージェントだけを変える。
- プロンプトを比較するなら、プロンプトだけを変える。
- ハーネスを比較するなら、ハーネスだけを変える。

比較対象以外を揃えることで、エージェントごとの得意不得意を比較できる。
サンドボックスは安全のための隔離環境であるだけでなく、同じ実験環境を複製する単位としても使える。

## 会社PCで想定する構成

元資料が想定している環境は、Windowsの会社PC上で複数のAIエージェントを並列に動かし、強い権限を与えながらホストへの影響を抑える構成である。

```text
Windows会社PC
│
├─ Main Repository
├─ Credential管理
├─ Network Policy
├─ MCP Policy
│
├─ Sandbox A
│   ├─ Agent A
│   ├─ Private Clone
│   └─ 独立した開発環境
│
├─ Sandbox B
│   ├─ Agent B
│   ├─ Private Clone
│   └─ 独立した開発環境
│
└─ Sandbox C
    ├─ Agent C
    ├─ Private Clone
    └─ 独立した開発環境
```

基本方針は、AIに強い権限を与える代わりに、その権限が届く範囲をサンドボックス内部へ閉じ込めることである。
ホスト側への接続は、ソースコード、ネットワーク、認証情報、MCPなど、必要な経路だけを明示的に開ける。

学習を再開するときの前提は次のとおりである。

- 目的は、Windows会社PC上でAIエージェントへ強い権限を与えながら、ホストへの影響を制限すること。
- 複数エージェントの並行・並列開発を想定する。
- A/Bテスト用に同条件の環境を複製したい。
- 全権限そのものより、権限が届く範囲を問題として捉える。
- サンドボックスが存在するだけでは安全を保証できず、境界を越える経路まで確認する。

公開仕様は更新される。
実際に会社PCへ導入するときは、その時点のDocker公式ドキュメントで要件と挙動を再確認する。
