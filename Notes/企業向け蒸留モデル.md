# 企業向け蒸留モデル

巨大な大規模言語モデル（LLM）へ毎回判断を任せると、費用、速度、データの持ち出しが問題になる。
そこで、巨大モデルの判断を小型モデルへ学習させ、企業の業務判断だけを手元の計算機で高速に返す方法が注目されている。

このノートは、2026-09-19〜20のChatGPTとの会話を整理したものである。
きっかけは、企業のAI担当として「他社から自社専用のローカルLLMを作れるかと聞かれたとき、できますと答えられるようになりたい」という動機だった。
会話時点の利用者の経験は、量子化済みのQwenをBonsaiで動かした程度である。

## 出発点となった投稿

会話の起点は、Taro L. Saito氏（@taroleo）のX投稿である。
投稿の主張は次の通りである。

- 重み157GBのDeepSeek V4 Flashの判断を、DGX Sparkで26時間かけて蒸留・学習し、4Bモデルへ移した。
- 約20分の1のサイズで、教師モデルの即答モードを超えた。
- 1判断あたり約22msで動く。
- DeepSeek V4 Flashでできる程度の判断なら、何でも学習して小型分類器にできそうで、小さなGPUインスタンスやMacでも動かせる。
- Jevも合成データと大規模モデルのラベルで学習しているらしい。

これを受けた別の投稿は、「専用Jevの蒸留モデルを企業向けにカスタマイズ販売する」ことが大きな事業になり得ると述べていた。
Jevの弱点はAPIであることと判断の正確性に疑義があることで、企業が求める正しい教師データを揃え、少ないパラメータで正しい判断を返す企業別・ケース別のローカルLLMには大きな価値がある、という主張である。

## 量子化と蒸留は別の工程である

利用者が触ってきた量子化は、既存モデルを小さくして動かす工程である。
投稿が扱っているのは、企業専用の判断能力そのものをモデルへ焼き込む工程であり、一段先の話になる。

| 手法 | 何をしているか | モデルの判断能力 |
|---|---|---|
| **量子化（Quantization）**、例：Qwen→GGUF | 重みの数値精度を落として軽量化する | 基本的には同じ |
| **LoRA / QLoRA** | 一部の重みだけを追加学習する | 特定業務に寄せられる |
| **微調整（Fine-tuning）** | モデル自体を再学習する | 特定業務をかなり覚えさせられる |
| **蒸留（Distillation）** | 大モデルの判断を小モデルへ移す | 大モデルに近い判断を安価に再現する |
| **専用分類器（Classifier）** | 分類・判定だけに特化する | 狭い用途ならLLMより速く正確になり得る |

**GGUF**は、llama.cppなどで使われる量子化済みモデルのファイル形式である。
**LoRA（Low-Rank Adaptation）**は、元の重みを固定し、小さな追加の重みだけを学習する方法である。
**QLoRA**は、元モデルを4bitに量子化した状態でLoRAを学習する方法である。

Bonsaiでやっていたのは、この流れの最後にある配布・実行の部分に当たる。
新しく覚える必要があるのは、その手前のデータ作成、教師モデル、学習、評価、量子化、配布である。

## 蒸留の基本形は「先生に解かせて生徒に覚えさせる」

会話では、問い合わせ分類を例に仕組みを説明している。

企業から「顧客の問い合わせを読み、緊急、通常、営業、クレーム、セキュリティ事故のどれかに分類したい」と頼まれたとする。
普通はDeepSeekやClaudeのような巨大LLMへ毎回分類を頼む。
しかし、毎回巨大モデルを使う必要はない。

まず巨大モデルに大量の例題を解かせ、ラベルと確信度を付けさせる。

```text
問い合わせA → セキュリティ事故 0.98
問い合わせB → 通常 0.87
問い合わせC → クレーム 0.91
...
```

この教師データを数万〜数十万件作り、Qwen 4Bのような小型モデルへ「入力文」と「正解（例：security_incident = 0.98）」の組として学習させる。

```text
DeepSeek 300B級
        ↓
   教師データ作成
        ↓
   Qwen 4Bなど
        ↓
  企業専用判断モデル
        ↓
   4bit量子化
        ↓
  RTX / Mac / CPU
```

大モデルを **教師モデル（Teacher）**、学習させる小型モデルを **生徒モデル（Student）** と呼ぶ。
これが「巨大モデルの判断能力を小型モデルへ移す」という発想である。

## 投稿の数値は「圧縮」ではなく「先生として別モデルを育てた」と読む

会話時点でのChatGPTの説明では、投稿の「重み157GB」はパラメータ数ではなく、量子化形式などを含むファイルサイズ側の数字と考えた方がよい。
DeepSeek V4 Flashは公式発表で約284B total / 13B activeの **専門家混合モデル（Mixture of Experts, MoE）** とされていた。
MoEは、多数の専門部分のうち入力ごとに一部だけを動かす構造である。

さらに会話時点（2026年9月）では、V4 FlashはDeepSeek V4.1 Flashへ更新されており、552BパラメータのMoEで、入力時8B、出力時16Bがactiveになる構造だと説明されている。
これらの数値はChatGPTが会話時点で参照した公式ページに基づく説明であり、このノートでは検証していない。

したがって「157GBモデルを4Bに圧縮した」というより、**巨大なMoEモデルを教師として使い、その判断パターンを独立した4Bの生徒モデルへ学習させた**と理解する方が正確である。

## Jevそのものを作っているわけではない

会話時点でTypeSafeが公開していた説明では、Jevは単なる小型LLMではない。
文字列を順に生成する普通のLLMとは異なる構造、並列サンプリング、**RLCD（Reinforcement Learning for Calibrated Decisions）** という学習方式を使う専用モデルだとされている。
出力も文章ではなく、型付きの判断と確率である。

そのため、企業向けに表現するなら「専用Jevを作ります」ではない。
「Jev的な用途を狙った企業専用ローカル判断モデルを構築します」と言う方が技術的に正確である。

## 「蒸留」という言葉は幅が広い

世の中では、大モデルに答えを作らせて小モデルに学習させることを広く「蒸留」と呼ぶ。
しかし機械学習としては、少なくとも次の種類を区別できる。

| 方式 | 教師から渡すもの | 呼び方 |
|---|---|---|
| 確率分布を渡す | `A = 0.72, B = 0.18, C = 0.10` のような分布そのもの | **知識蒸留（Knowledge Distillation）** |
| 正解ラベルだけを渡す | `正解 = A` を大量生成する | 厳密には **合成データによる教師あり微調整（synthetic dataを使ったSFT）** や **疑似ラベル付け（pseudo-labeling）** に近い |
| 推論例まで渡す | 「理由：○○だからA／最終回答：A」 | 推論過程の移植 |

**SFT（Supervised Fine-Tuning）** は、入力と模範出力の組で行う教師あり微調整である。

投稿だけからは、DeepSeekの内部の **ロジット（logits）**、つまり各候補への生のスコアを使った本格的な知識蒸留をしたとまでは判断できない。
実際に何をしたかは、学習コードやデータ形式を見ないと分からない。
会話では、まずは後者の「教師の回答を正解例として使う蒸留風SFT」を中心に理解するのが安全だとしている。

## 何でも4B LLMにするのが正解ではない

企業案件では、蒸留した4Bモデルが常に最適とは限らない。
たとえば「メールに機密情報が含まれるか判定したい」と頼まれた場合も、次の順で検討する。

```text
プログラム
   ↓ 無理なら
正規表現・ルール
   ↓ 無理なら
Embedding / 小型Classifier
   ↓ 無理なら
100M～1B級モデル
   ↓ 無理なら
3B～8B LLM
   ↓ 無理なら
大型LLM
```

判断の難しさごとの目安は次の通りである。

| 判断内容 | 候補 |
|---|---|
| 電話番号が含まれているか | Pythonの正規表現 |
| これはクレームか | BERT系分類器で十分な可能性がある |
| 顧客の文章全体を読み、規程上のセキュリティインシデントに該当するか | LLMを蒸留した1B〜4Bモデルが有力 |
| 法律、契約書、社内規程を横断して理由付きで判断する | 大型LLMや検索拡張生成（RAG）が必要な場合がある |

**埋め込み（Embedding）** は、文章を意味を反映した数値ベクトルへ変換する仕組みである。
**BERT** は、文章理解に使われる比較的小さな言語モデルの系統である。

企業向けの価値は「何でも4Bモデルを作る能力」ではない。
「この業務ならルールで十分、この業務なら分類器、この業務だけ蒸留LLM」と設計できる能力である。

これは、利用者が以前からJevについて考えていた「プログラムで解けるものはプログラムに寄せ、曖昧な判断だけAIに渡す」という考え方と相性がよい。

## 教師データが正しくても「完璧」にはならない

投稿には「完璧に蒸留された」という表現がある。
会話では、企業向けの説明でこの言葉を使わない方がよいとしている。

教師が99%正しくても、次の誤差源が残るためである。

```text
教師の誤り
+
教師データの偏り
+
実データとの分布差
+
Studentの能力不足
+
未知入力
```

そのため実運用では、モデルの確信度で処理を分ける。

```text
入力 → 専用モデル → confidence 0.97 → 自動処理
入力 → 専用モデル → confidence 0.58 → 人間確認
```

会話時点のTypeSafeも、確率と確信度を出し、高確信度なら自動処理、そうでなければ人間へ回す設計を前面に出していると説明されている。

企業システムとして重要なのは「常に正解するAI」ではない。
**どこまでなら機械に任せてよいかを測定できるAI**である。

## 企業専用モデルを作る実際の工程

「御社専用のローカルAIを作れますか」と聞かれたとき、実際の工程は次の八段階になる。

1. **業務を決める。** 「何でも答える社内LLM」ではなく、何を入力して何を判断させるかを定義する。出力も `YES/NO`、5分類、0〜1のスコアなどに固定する。
2. **正解データを作る。** 実データに専門家が正解を付けた **正解データセット（Gold Dataset）** を作る。境界事例や失敗例も重要である。
3. **巨大な教師モデルを使う。** DeepSeek、Claude、GPT系、あるいは複数モデルで大量の教師ラベルを生成する。機密データを外へ出せない企業では、教師モデル自体をオンプレミスに置くこともある。
4. **生徒モデルを学習する。** Qwen 1.5B/3B/4BなどへLoRAやQLoRAで学習させる。利用者がまだ触っていない領域である。
5. **未知データで評価する。** 正解率（Accuracy）だけでなく、適合率（Precision）、再現率（Recall）、F1、誤検出、見逃し、Brier Score、Calibration Errorなどを測る。学習データをテストに混ぜないことが非常に重要である。
6. **確信度の境界を決める。** 例：`0.95以上=自動処理`、`0.70〜0.95=確認`、`0.70未満=拒否または大型モデルへ送る`。
7. **量子化する。** GGUF、AWQ、GPTQなどで軽量化する。ここで利用者がBonsaiで触っていた世界へ戻る。
8. **ローカルに配備する。** llama.cpp、vLLM、SGLang、Ollamaなどで社内API化し、既存システムへつなぐ。

評価指標の詳しい意味は [[企業専用モデルの学習ロードマップ|企業専用モデルの学習ロードマップ]] のPhase 2とPhase 7で整理している。
**Brier Score** と **較正誤差（Calibration Error）** は、モデルが出す確率が実際の正解率とどれだけ合っているかを測る指標である。

この一連をできれば、「企業専用ローカルAIの設計・学習・評価・配備ができます」とかなり正当に言えるようになる。

## 価値の中心はモデル学習より設計と評価にある

会話では、この分野の企業案件で重要なのは、学習そのものより教師データ設計、評価、閾値設計だとしている。
学習コード自体は、すでにかなり既製品化されているためである。

最初の実習題材としては、チャットボットではなく「文章を入力すると、3〜5個の業務判断と確率をJSONで返すモデル」が勧められた。
これを一度自分で作れば、投稿の内容がほぼ理解できるという位置づけである。

最初の提案は、手元のRTX 4070 12GBでQwen 1.5B〜4B程度をQLoRAし、「自分専用Jevっぽい判断モデル」を一本作る実習だった。
データの作り方、学習の仕方、教師を本当に再現できたかの測り方までを一周する狙いである。

その後の会話で、題材は社内用語を扱えるローカルChatへ変更された。
変更の経緯は [[企業向け完全ローカルAIアシスタント|企業向け完全ローカルAIアシスタント]] にまとめている。
