# Azure SRE AgentとAWS DevOps Agent

2026年3月、MicrosoftとAWSがクラウド運用向けのAIエージェントを相次いで一般提供した。
Microsoftは **Azure SRE Agent**、AWSは **AWS DevOps Agent** である。
どちらも単にログを要約するAIではない。
障害が起きた後に、システムの状態、エラーログ、ソースコードの変更履歴、過去の障害情報などを確認し、原因候補を整理して対応案を人間へ提示するところまでを担う。

元資料は社内向けニュース記事のためにまとめたナレッジであり、書き手が実際に使った感想ではない。
以下の機能、数値、料金は記録時点（2026年）の公式情報に基づく整理である。

## 自動化の対象が「調べる仕事」まで広がった

保守では、毎回同じ障害が起きるとは限らない。
そのため、従来の「決められた条件で決められた処理を実行する自動化」だけでは対応しにくかった。
これまでの自動化は、異常を検知して人間へ知らせるところが中心だった。

今回の2サービスが興味深いのは、異常検知の後にある「何が起きたのかを調べる」仕事までAIの対象になった点である。

```text
従来
異常発生 → 人間が調査 → 原因特定 → 対応

AIエージェント導入後
異常発生 → AIが調査 → 原因候補・対応案 → 人間が判断 → 対応
```

## AIは監視情報だけを見ているわけではない

原因を調べるために、AIエージェントは次のような情報を集約して参照する。

- システムの状態。
- エラーログ。
- ソースコードの変更履歴。
- 過去の障害情報。

たとえばエラーが増えた場合、現在のシステム状態だけでなく、「直前にソースコードが変更されていないか」も合わせて原因を探す。
単一のエラーログだけで判断するのではなく、変更履歴と突き合わせる点が、ログ要約AIとの違いである。

## Azure SRE AgentはAzure上のシステムを中心に調べる

Azure SRE Agentは、Azure上で動くシステムについて、状態、ログ、ソースコードなどを確認しながら障害原因を調査するAIエージェントである。
直前にどのような変更があったかも合わせて確認し、原因候補や対応方法を提示する。
設定した権限の範囲では、復旧操作まで実行させる構成も可能である。

```text
Azure上のシステム → Azure SRE Agent → 原因候補 → 対応案 → 必要に応じて復旧
```

Microsoftは自社サービスでもAzure SRE Agentを利用している。
2026年3月の一般提供時点で、1,300以上のエージェントを展開し、35,000件以上のインシデントを軽減したと公表している。
これは提供元による公表値である。

初学者向けには、次のように説明できる。

> Azure上で問題が起きたときに、ログだけでなくシステムの状態や最近のソースコード変更などを確認し、原因候補と対応方法を整理してくれるAIエージェント。

## AWS DevOps Agentは複数環境をまたいで調べられる

AWS DevOps Agentも、システムの状態やソースコードの変更履歴などを確認しながら、障害原因を調査するAIエージェントである。

特徴は、AWS環境だけでなく、Azureやオンプレミス環境も調査対象にできる点である。
複数環境を利用するシステムにも対応できる。
障害発生時の原因調査だけでなく、システム運用上の改善点を調べる用途にも使える。

```text
AWS / Azure / オンプレミス
↓
AWS DevOps Agent
├─ システム状態の確認
├─ 変更履歴の調査
└─ 原因候補の提示
```

初学者向けには、次のように説明できる。

> AWSやAzure、社内サーバーなどで問題が起きたときに、システムの状態や変更履歴を調べ、原因候補と対応方法を整理してくれるAIエージェント。

## 二つの違いは対応環境と変更操作の扱いにある

| 項目 | Azure SRE Agent | AWS DevOps Agent |
| --- | --- | --- |
| 主な用途 | Azure環境を中心としたSRE・運用支援 | 複数環境をまたいだDevOps・運用支援 |
| 原因調査 | 可能 | 可能 |
| ソースコード変更履歴を含めた調査 | 可能 | 可能 |
| 対応案の提示 | 可能 | 可能 |
| 復旧操作 | 権限設定に応じて可能 | 承認を含む変更操作を実行可能 |
| 対応環境 | Azure中心 | AWS、Azure、オンプレミス |

細かな機能差より重要なのは、「どちらも障害調査までAIが入る」という共通点である。

## 調査と提案はAIへ、本番変更の判断は人間へ残せる

すべての処理をAIへ任せる必要はない。
AIは異常検知後の情報収集、原因候補の整理、対応案の作成を担当する。
人間は提案内容を確認したうえで、本番環境へ変更を加えるかを判断する。

```text
異常検知 → 原因調査 → 対応案作成   （AI）
↓
人間が承認 → 復旧対応              （人間。導入初期は復旧操作も人間が行う）
```

導入初期は、調査と提案だけをAIに任せ、復旧操作は人間が行う構成が現実的である。

## 外販した自社製品の一次保守に組み込める可能性がある

自社で開発したツールを外部へ販売すると、販売先が増えるほど保守負担も増えやすい。
ソフトウェア自体は複数社へ展開できても、障害を調査するエンジニアの時間は同じようには増やせない。

そこで、販売したシステムの状態、ログ、ソースコード変更履歴などをAIエージェントが確認できるようにしておけば、**一次保守（first-line maintenance）**、つまり最初の調査と切り分けをAIに任せる構成が考えられる。
これは元資料が示す活用案であり、検証済みの構成ではない。

```text
お客様環境（複数）
    ↓
障害発生
    ↓
AIエージェントが一次調査
    ↓
原因候補 + 対応案
    ↓
自社の保守担当者
    ↓
人間が判断・対応
```

この構成なら、保守担当者が毎回ゼロから情報収集を始める負担を減らせる。
「製品へAI機能を追加する」というより、「販売後の保守サービスにAIエージェントを組み込む」という捉え方が近い。

## 提供元への信頼と、原因判断の正しさは別問題である

MicrosoftやAWSが提供元であることは、企業導入を検討する材料になる。
しかし、提供元への信頼と、AIが個別障害の原因を正しく判断できることは別の問題である。

お客様環境へすぐに導入するのではなく、まず検証環境や社内システムで次を確認する。

- 原因候補の精度。
- 必要な情報を取得できるか。
- 誤った提案に気付きやすいか。
- 権限範囲。
- 費用。

最初は読み取りと原因調査を中心に使い、実績を見ながら任せる範囲を広げる方針が適している。

## 料金方式が違うため障害件数だけでは比較できない

**AWS DevOps Agent** は、AIエージェントが実際に処理した時間に応じた秒単位の従量課金である。
2026年時点のAWS公式例では、月10件のインシデントを1件あたり平均8分調査した場合、月額39.84ドルとなる。
周辺のAWSサービス利用料は別途発生する。

**Azure SRE Agent** は **Azure Agent Units（AAU）** という単位を使う。
料金は、エージェントを利用できる状態にしておく分と、実際にAIが処理した分の組み合わせで構成される。

```text
AWS   ：AIが実際に動いた時間に応じて課金
Azure ：利用できる状態の料金 + AIが処理した量
```

課金方式が異なるため、障害件数だけで単純比較せず、実際の利用方法を想定して評価する必要がある。

## 実際に試すときに記録する項目

元資料は、検証時に次の結果を記録しておくと、後の記事更新や「使ってみた」記事に使いやすいとしている。

1. どの環境へ導入したか。
2. AIに与えた権限。
3. どのような障害を発生させたか。
4. AIがどの情報を調査したか。
5. 原因候補は正しかったか。
6. 対応案は実用的だったか。
7. 人間が追加で調べる必要があったこと。
8. 1件の調査にかかった時間。
9. 人間だけで調査した場合との差。
10. 実際に発生した料金。
