# TokenEconomizerによるセッション学習と費用削減

TokenEconomizerは、コーディングエージェントの過去セッションから、再調査、未使用ツール、行き詰まりの繰り返しを減らすプラグインとして提供資料で紹介されている。モデルの重みを学習するものでも、モデル通信を中継するプロキシでもなく、フック・設定・ログを利用する。

根拠は2026-11-02の提供資料。README由来の確認事項と会話中の推測を含み、今回の取り込みでは外部確認・インストールを行っていない。原資料も論文本体は未読で、実験値はREADMEの報告である。

## 三つの仕組み

| 機能 | 何を減らすか | 資料時点の動作 |
|---|---|---|
| Micro-skills | 毎回同じ環境・手順を調べ直す無駄 | 複数セッションで確認した事実を開始Contextへ入れる。既定オフ |
| Tool pruning | 使わないツール定義の入力 | 複数セッションで未使用のツール等を、次のセッション向け設定から外す。既定オン |
| Loop guard | 同じ失敗を繰り返すターン | 蓄積した通常の長さやモデル判定を使い、注意書き・停止方法を示す。既定オン |

Micro-skillsは3セッションでの確認を経て採用し、後で食い違えば撤回する。`envfacts`設定では繰り返し失敗だけを使い、モデルによる見直しを増やさないとされる。

Tool pruningの判定は、2セッション以上にまたがる10プロンプト未使用、または5セッション未使用等。書き込み単位はClaude Codeでは個別ツール、Codexでは機能パッケージ、Copilot CLIではMCPサーバーで異なる。Piは対象ツールが少なくpruningしないとの説明である。

## 元に戻せることと実行上限を区別する

設定書き込みはリポジトリの非活動60分後に行うとされ、キャッシュ再構築の負担を避ける意図がある。この60分を、すべてのモデルサービスのキャッシュ寿命として一般化しない。

`propose`で提案だけにする、`restore`でプラグイン自身の変更だけを戻す経路がある。利用者の拒否ルールとは区別する設計である。

Loop guardは正常終了とみなしたターンを5回蓄積してから介入し、注意書きは1ターン1回まで。通常長の2.5倍超かつ同じ失敗を反復する場合の直接警告もある。ただし**自動停止機構ではなく、無人実行の上限管理を代替しない**。正常終了の判定も、タスクの正しさを外部評価した結果とは分ける。

## 効果と適用条件

README報告ではSWE-Benchの277タスク・6リポジトリ・5構成で平均費用18.4〜30.9%減。Pass@1は4構成で改善したが、1構成では低下した。プラグイン自身のモデル呼び出し費用も含める方針とされる。自環境での節約率の保証ではない。

対象はClaude Code、Codex、Copilot CLI、Piで、Python 3.10以上や対応するフックが必要。資料時点の対応範囲より新しい版、論文測定時のMicro-skills設定、自作ハーネスへのAdapter再利用範囲は未確認である。
