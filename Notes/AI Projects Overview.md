# AIに仕事を任せるために作っているプロジェクト

AIエージェント（AI Agent）に実際の仕事を任せようとすると、コードを書く能力だけでは埋まらない役割が次々と見えてくる。
このノートは、筆者が個人で作り続けているAI開発関連プロジェクトを紹介した記事「AIに仕事を任せるために、足りないものを一つずつ作っている」を整理したものである。
記事は内部実装には踏み込まず、「なぜその役割を分けたのか」と「何が便利になるのか」に絞っている。

最初から大きな仕組みを作ろうとしていたわけではない。
CodexやClaude CodeのようなAIエージェントで開発するうちに「ここもAIに任せたい」部分が増え、そのたびに足りない仕組みを作った結果、複数のプロジェクトに分かれた。

## AIに任せる範囲を広げるほど、人間の暗黙の仕事が見えてくる

AIはすでにかなりコードを書ける。
リポジトリ（Repository）を調べ、修正し、テストを実行し、プルリクエスト（Pull Request）を作るところまで任せられる場面も増えた。

しかし、実際の開発で人間がやっていることはコードを書くことだけではない。

- 何を作るのかを決める。
- 途中で出てきた判断を覚えておく。
- 過去の経験を参照する。
- 必要なテストを考える。
- 会社の情報を外部へ出してよいか判断する。
- 複数の道具を使うなら、それらをどう組み合わせるかを決める。

AIへ任せる範囲を広げるほど、これまで人間が暗黙に担当していた仕事が見えるようになった。
各プロジェクトの多くは、その不足を一つずつ埋めるためのものである。

## 九つのプロジェクトはそれぞれ独立した責任を持つ

記事の順番と、記事時点の現在地は次のとおりである。

| 順番 | プロジェクト | 役割 | 現在地 |
|---|---|---|---|
| 1 | Arthur | プロジェクトの目的、要求、判断を保持する | 構築中 |
| 2 | AI-DE | 決まった仕事を計画し、実行し、検証する | 既存実装を発展中 |
| 3 | MeetingAssistant | 会議で生まれる判断とArthurを近づける | 会議アプリ実装済み、Arthur接続はMock |
| 4 | DevLore | 過去の設計資料やレビュー経験をEvidence付きで再利用する | 検索・Ranking実験を継続中 |
| 5 | Software-Test-Knowledge | 再利用できるテストの視点を提供する | Knowledge Providerとして整備 |
| 6 | InputGuardian | 人間がWeb AIへ送る入力を送信前に守る | 構築中 |
| 7 | LLM-Security-Proxy | AgentやCLIからLLMへ出る通信を守る | 主要Runtimeを実装済み、継続開発中 |
| 8 | AI-Security-Policy（ASP） | 会社のAI利用ルールを機械可読なPolicyとして管理する | v1中核を実装済み |
| 9 | 日本ハーネス（Japan-Harness） | 独立したProviderを組み合わせ、一つのAI開発環境として成立させる | Architecture・Contract設計と実装を進行中 |

紹介の順序は、一つの不足を埋めると次の不足が見える、という連鎖になっている。

```text
Arthur：何を作るかを保持する
↓ 何を作るかが決まっても、それだけでは開発は進まない
AI-DE：決まった仕事を継続して進める
↓ 判断は開発画面の外、会議でも生まれる
MeetingAssistant：会議の判断を開発から切り離さない
↓ 現在の要求を保持しても、仕様書に残らない経験が足りない
DevLore：熟練者の経験を根拠と一緒に残す
↓ 同じ問題はテストにもある
Software-Test-Knowledge：テストの考え方を毎回ゼロから作らない
↓ 会社の仕事へ広げるとセキュリティが問題になる
InputGuardian：人間がWeb AIへ送る入力を守る
↓ Web画面を通らないAI通信が残る
LLM-Security-Proxy：Agent／CLIからLLMへの通信を守る
↓ 二つを別々に作ると会社のルールが二重化する
AI-Security-Policy：会社としてのルールを一つのPolicyで持つ
↓ 独立した仕組みを組み合わせる必要がある
日本ハーネス：Providerを選び、接続し、一つの環境として成立させる
```

## Arthurは「何を作るのか」を持ち続ける

最初に必要になったのは、「何を作るのか」を持ち続ける仕組みだった。

AIエージェントへの最初の指示ならチャットに書ける。
しかし開発が長く続き、途中で仕様を話し合い、方針を変え、「これは採用する」「これはやめる」と判断していくと、プロジェクトの正解は最初のプロンプト（Prompt）だけでは表せなくなる。
会話をまたいで別のエージェントが参加するなら、なおさらである。

**Arthur** は、プロジェクトの目的、要求、制約、受け入れ条件、その時点で有効な判断を扱う。
コードを書く担当ではなく、「このプロジェクトは何を目指していて、何を満たせばよいのか」を保持する側である。
この役割を実装担当から分ければ、エージェントが入れ替わっても、そのたびに背景を一から説明する必要が減る。

![[Assets/Images/AI Projects Overview/01-arthur.webp]]

図に描かれたArthurの入出力は次のとおりである。

```text
入力：人との会話、会議・議論、要求・相談、仕様変更
↓
Arthurが管理するもの
  目的・ゴール、要求、制約・原則、受け入れ条件、
  設計・仕様の判断の記録、現在有効な判断の判別、
  確認が必要な事項、実装結果の確認
↓
Arthurからの出力：現在の要求、現在有効な判断、受け入れ条件
↓
実装するAI（AI-DEなど）→ 実装結果
↓
結果の確認としてArthurへ戻る
```

名前の由来は、複数のAIモデルから意見を集めて意思決定していく構想を、円卓の騎士をまとめるアーサー王になぞらえたことである。

## AI-DEは決まった仕事を継続して進める

Arthurが持つ要求を受け取った後、実際の開発を進める役が必要になる。
人間が毎回タスクを分け、エージェントへ渡し、失敗したら再実行し、テスト結果を確認して次を指示するなら、AIがコードを書いていても人間は進行管理に張り付くことになる。

**AI-DE** は、開発作業を計画し、実行単位へ分け、Workerへ割り当て、実行結果や **証跡（Evidence）**を集めながら次の処理へ進める **実行ハーネス（Execution Harness）**である。

Arthurとの境界は意識して分けている。

| | 担当 |
|---|---|
| Arthur | 何を満たす必要があるか |
| AI-DE | それをどう実行するか |

AI-DE自身がプロジェクトの目的や要求を勝手に変える設計にはしていない。
この分離により、実装に使うエージェントやモデルを変えても、プロジェクトそのものの意味まで一緒に入れ替わらない構成を目指している。

![[Assets/Images/AI Projects Overview/02-ai-de.webp]]

機能図から読み取れるAI-DEの構成は次のとおりである。

- **入力**：要求（仕様・やりたいこと）、既存コード（既存プロジェクト）、人間の指示（追加の要望・修正指示）。
- **工程**：要件（理解・整理）→ 設計（アーキテクチャ・詳細設計）→ 人間の承認（承認Gate）→ 実装（自律実装）→ レビュー（マルチAgentレビュー）→ 検証結果（テスト・動作確認）。既存プロジェクトの改修時のみ、設計の前に既存コード解析（構造・影響範囲の把握）が入る。
- **複数AI CLI対応**：Codex、Claude Code、OpenCode、GitHub Copilot。
- **Agent／Modelの振り分け**：複雑なタスクは高性能モデル（Claude、GPT-4系）、定型・軽量タスクは軽量モデル（GPT-4o miniなど）へ、作業内容や難易度に応じて使い分ける。
- **自律実装**：タスクをAgentへ渡し、継続して実装を進め、途中で状況を確認し、完了まで自律的に実行する。
- **コンテキスト圧縮**：長いログや大量のテスト結果を、AIが扱いやすいコンテキストに変換する。
- **知識循環**：実プロジェクトで得られた知見を、再利用できるKnowledge候補として保存する。
- **承認Gate**：人間の判断が必要な箇所では自動的に先へ進まず、承認を待ってから次の工程へ進む。
- **マルチAgentレビュー**：要件整合（仕様との一致）、機能ロジック（正しさ・網羅性）、可読性（保守性・構造）、セキュリティ（脆弱性・安全性）を複数の観点から並列でレビューする。
- **Evidence収集**：テスト結果、実行結果（コマンド実行ログ）、レビュー結果、Artifact（生成物・成果物）を開発結果の根拠として残す。
- **出力**：変更されたコード、テスト結果、レビュー結果、Evidence。

名前は、AIと統合開発環境（IDE）を組み合わせたもので、AIによる開発環境そのものを表す。
設計境界の詳細は [[AI-DE Harness Design|AI-DEにおけるハーネスの位置づけと設計境界]] にある。

## MeetingAssistantは会議で生まれた判断を開発から切り離さない

プロジェクトについての判断は、開発画面の中だけで行われるわけではない。
実際の仕事では、会議の中で仕様が決まり、方針が変わり、それまでなかった要求が生まれる。

**MeetingAssistant** は、日本語の会議をPC内で文字起こしするWindows向けアプリケーションである。
会議を記録するだけでなく、将来は会議中からArthurへ相談し、プロジェクトについての判断と会議をつなげることを考えている。

記事時点の状態は次のとおりである。

- ローカルでの文字起こし、会議履歴、相談画面はすでに動いている。
- Arthurの応答はMockで、Arthur Coreとの本接続はまだ行っていない（図にも「Arthur連携は開発中」とある）。

会議の内容をすべて自動的に正式決定へ変えたいわけではない。
人間の判断が大量に発生する会議という場所と、Arthurとの距離を縮めたい、というのが出発点である。

![[Assets/Images/AI Projects Overview/03-meetingassistant.webp]]

利用イメージの図は次の流れを示している。

```text
会議（社内会議、打ち合わせ、オンライン会議）
↓
マイクから音声を取得（マイク選択、一時停止・再開、入力レベルの確認）
↓
PC内でリアルタイム文字起こし（日本語、クラウドへ音声は送信しない）
↓
会議内容をその場で画面で確認
↓
気になった内容をArthurへ相談（例：「この案の問題点は？ 今の議論を踏まえるとどう考える？」）
↓
Arthurから提案・助言を受ける（検討すべきポイント、潜在的なリスク、次のアクション案など）
```

過去の会議の文字起こしを後から見返す会議履歴機能もある。
名前は、文字起こしだけでなく、アイデアや助言を加えて会議を支援する存在を目指していることに由来する。

## DevLoreは熟練者の経験を根拠と一緒に残す

現在の要求を保持できても、まだ足りないものがあった。
ソフトウェア開発には、仕様書にきれいに残っていない知識が大量にある。

- この顧客では以前この表現を指摘された。
- この種類の変更では、いつもここを確認している。
- 設計上は問題なさそうでも、この会社ではこの作り方を避けている。

長く担当している人は覚えていても、新しく参加した人やAIエージェントは知らない。

**DevLore** は、過去の設計資料やレビュー記録を、根拠となった情報を失わない形でAIが再利用できる知識へ変えることを目指している。
ただし「昔そう言われた」というだけで、現在の絶対的なルールにはしない。
過去に何度も同じ指摘があっても、それが今も有効な会社ルールなのか、特定案件だけの判断だったのかは別の話だからである。
そのため、知識を見つけることと、それを現在のプロジェクトで採用することを分けている。
熟練者の頭の中だけにあった経験を使えるようにしながら、AIが勝手にルールを増やさない。
その両方を成立させる仕組みである。

![[Assets/Images/AI Projects Overview/04-devlore.webp]]

機能図の内容は [[DevLore|DevLore]] に詳しく書いた。
名前はDevelopment（開発）とLore（蓄積された知識・伝承）の組み合わせである。

## Software-Test-Knowledgeはテストの考え方を毎回ゼロから作らない

似た問題はテストにもある。
AIへ実装を任せるたびに、「どんなテストを考えるべきか」までゼロから考えさせる必要はない。
境界値、異常系、状態遷移といったテストの知識には、プロジェクトをまたいで再利用できる部分がある。

そこで、テストに関する一般的な知識を **Software-Test-Knowledge** として分離している。
ここでも、実際のプロジェクトでどのテストを必須にするかまでは決めない。
再利用可能なテストの視点を提供し、現在の要求や実装へどう適用するかは利用側が判断する。
狙いは、エージェントが変わるたびにテストの考え方までリセットされる状態を避けることである。

![[Assets/Images/AI Projects Overview/05-software-test-knowledge.webp]]

機能図の内容は次のとおりである。

- **入力**：要求（機能要求・非機能要求）、仕様（機能仕様・画面仕様・インターフェース仕様）、実装内容（実装コード・実装方針）、変更差分（差分内容・変更の影響範囲）、対象機能（対象の機能・利用シナリオ）、既存テスト（既存のテストケース・テスト結果）。
- **蓄積されたテスト知識（汎用的なテスト観点）**：正常系、異常系、境界値（最小値、最大値、空、上限付近）、入力検証、状態遷移（正しい順序や禁止された遷移）、エラー処理（失敗時の処理や復旧）、セキュリティ（権限、入力、機密情報）、回帰テスト（既存機能を壊していないか）、テスト漏れ確認（変更内容に対して不足している観点がないか）。
- **処理の流れ**：入力内容を理解 → 関連するテスト知識を探す → 今回に関係する観点を選ぶ → テスト候補として返す。
- **返すもの**：テスト観点候補、テストケース候補、確認すべき条件、見落としやすい観点（過去の事例などからの注意点）、関連するテスト知識。
- **利用する側**：AI-DE、AIエージェント、開発者、テスト設計。
- **プロジェクト固有のテスト設計は利用側で行う**：テスト候補から採用・調整 → プロジェクト固有のテストケースを作成（詳細な手順や期待結果を定義）→ 実際のテスト（実施・結果確認）。

名前は、ソフトウェアテストの知識をその場限りのノウハウではなく、再利用可能な知識として扱うことをそのまま表している。

## InputGuardianは人間の注意力だけに頼らず送信前に守る

AIを開発だけでなく会社の仕事へ広げると、セキュリティの問題が大きくなる。
ChatGPTなどのWeb AIへ入力する文章には、個人情報、社内情報、認証情報などが混ざる可能性がある。

利用者自身が確認してから送信するのが基本である。
しかし「送ってよい情報かを毎回人間が完全に判断する」運用だけに頼ると、利用者が増えるほど確認漏れが起きやすくなる。

**InputGuardian** は、人間がWeb AIへ入力しようとしている内容を送信前に確認し、必要に応じて変換したり、送信を止めたりする仕組みである。
AIを禁止するのではなく、安全に使える範囲を増やすために、人間の注意力だけに依存しない境界を置く。

![[Assets/Images/AI Projects Overview/06-inputguardian.webp]]

図に示された判定と処理は次のとおりである。

```text
Web AIに送る文章を入力
↓
InputGuardian（会社のAI利用ルールを参照し、送信前に入力内容を確認）
  機密情報を検出：個人情報（氏名・メールアドレス）、認証情報（APIキー・パスワード）、
                  社内情報（社内の顧客情報・機密資料）、その他（社外に出すべきでない情報）
↓
├─ 問題なし：そのまま送信
├─ 保護が必要：一部をマスク・置換して送信（例：APIキーを [MASKED] に置き換える）
├─ 判断が必要：送信前に利用者へ確認（送信する／キャンセル）
└─ 送信不可：ポリシーにより送信を止める
↓
Web AIサービス（ChatGPT、Claude、Geminiなど）
```

名前は、Web AIへ送るInputを送信前に確認し、機密情報などから守るGuardianの役割を表す。

## LLM-Security-ProxyはWeb画面を通らないAI通信にも境界を置く

InputGuardianを考えると、別の入口が残っていることに気付く。
CodexやClaude CodeのようなAgent、CLI、APIからLLMへ送られる情報は、Web画面への入力を監視するだけでは守れない。

**LLM-Security-Proxy** は、AgentやCLIから外部LLMへ出ていく通信側に置き、送信内容を検査し、必要に応じてマスクや除去を行う **セキュリティ境界（Security Boundary）**である。

| | 守る場所 |
|---|---|
| InputGuardian | 人間がWeb AIへ入力する場所 |
| LLM-Security-Proxy | AgentなどからLLMへ出ていく通信 |

二つは似た目的を持つが同じものではない。

![[Assets/Images/AI Projects Overview/07-llm-security-proxy.webp]]

図の内容は次のとおりである。

- **送信元**：Codex、Claude Code、OpenCode、AI-DE、API Clientなど。
- **検査対象**：User Prompt（ユーザーの指示）、System Prompt（システム指示）、Context（参照するファイル・履歴など）、Tool Call（実行するツールの情報）、添付データ（ファイル・テキストなど）。
- **処理**：機密情報の検出（API Key、Access Token、Password、個人情報、社内情報、接続情報など）→ ポリシーによる判断（そのまま送信／変換して送信（Masking / Redaction）／送信拒否）→ マスキング・変換（例：APIキーを `sk-****`、メールアドレスを `t***@example.com`、社内プロジェクト名を `【社内情報】` へ）→ 検査・ポリシーに適合した安全な内容だけを外部LLMへ送信。
- **安全に処理できない場合**：**フェイルクローズ（Fail Closed）**、つまり外部LLMへは送信せず通信を停止する。
- **送信先**：Cloud LLM（OpenAI、Anthropic、Google、Azure OpenAIなど）、Local LLM（社内LLM、オンプレミス、プライベート環境など）。
- **ポリシー**：会社のAI利用ルール（セキュリティポリシー）を適用する。

名前は、Coding AgentからLLMへ向かう通信経路にSecurity Proxyを置き、送るべきでない情報を検出・保護する役割を表す。

## 二つの防御を別々に作ると会社のルールが二重化する

InputGuardianとLLM-Security-Proxyは、どちらも「何を送ってよいか」を判断する。
その判断基準まで別々に管理すると、会社のルールが二重化する。

**AI-Security-Policy（ASP）** は、会社の生成AI利用ルールを機械が扱えるPolicyとして管理するプロジェクトである。
「この種類の情報は送信禁止」「この情報はマスクすれば利用可能」といった会社としての要求を、各防御の設定へ直接書かず、一つのPolicyとして持つ。

ASP自身は通信を止めない。

| | 担当 |
|---|---|
| ASP | 会社として何を要求するか |
| InputGuardian / LLM-Security-Proxy | その要求に従って実際の入力や通信を扱う |

この構造なら、新しいAI利用経路が増えても、会社のルールを一から別管理する必要がない。
ASPは構想だけでなく、Policy Schema、分類体系、各Security Component向けのCompilerなど、v1の中核部分まで実装が進んでいる。

![[Assets/Images/AI Projects Overview/08-ai-security-policy.webp]]

図に示されたPolicyの構成要素は次のとおりである。

- **会社の生成AI利用ルールの例**：個人情報はそのまま送らない。認証情報は送信禁止。一部の社内情報はマスクして利用可能。
- **情報の種類**：個人情報、認証情報、社内情報など。
- **送信可否**：送信OK、送信NG、加工すればOK。
- **保護方法**：マスク、削除、置換。
- **適用範囲**：会社全体、特定のTeam、特定のユーザー。
- 同じ会社ルール（共通Policy）が、InputGuardian（人間 → Web AIの入力を保護）とLLM-Security-Proxy（Agent / CLI → LLMの通信を保護）の両方へ渡る。

```text
会社のAI利用ルール
↓
AI-Security-Policy（機械可読なPolicy、Compilerで各Componentへ）
├─ InputGuardian：人間 → Web AI
└─ LLM-Security-Proxy：Agent / CLI → LLM
```

## 日本ハーネスは独立した仕組みを一つの開発環境として組み合わせる

ここまでのプロジェクトは、それぞれ別の問題を解く。

- Arthurは要求と判断を扱う。
- AI-DEは実行を扱う。
- DevLoreは過去の開発知識を提供する。
- Software-Test-Knowledgeはテストの知識を提供する。
- InputGuardianとLLM-Security-Proxyは異なるAI利用経路を守る。
- その判断基準をASPが管理する。

それぞれを独立させた理由は二つある。
全部を一つの巨大なシステムへ入れると、一部分だけ別製品へ交換したいときに他の機能まで作り直すことになる。
また、会社やチームによって使いたいAgent、Sandbox、Issue管理、Document管理の仕組みが異なる。

**日本ハーネス（Japan-Harness）** は、それらを組み合わせるためのものである。
特定のリポジトリを必須部品として固定せず、「この役割を満たすProvider」という単位で接続する。

- AI-DEをExecution Harnessとして使っていても、同じ **契約（Contract）**を満たす別のExecution Harnessがあれば置き換えられる。
- Document AssetもDevLoreに固定せず、必要な能力を満たす別の仕組みを選べる。

日本ハーネス自体は、要求を決めたり、コードを書いたり、会社のSecurity Policyを決めたりしない。
役割を持つ仕組みを選択し、接続し、互換性を確認しながら一つの構成として成立させる部分を担当する。

筆者が最終的に作りたいのは、すべてを自作した巨大なAI開発ツールではない。
既存の開発方法や道具をできるだけ残したまま、足りない部分だけをAI向けの仕組みで補い、一つの開発環境として使える状態である。

![[Assets/Images/AI Projects Overview/09-japan-harness.webp]]

図では、中央のJapan-Harnessが「Providerを選ぶ」「接続する」「必要な機能を確認」「組み合わせを確認」「導入する」「更新する」「問題時に戻す」「構成を把握」「状態を確認」を担い、周囲に次の役割枠を置いている。

| 役割 | Provider（⇄は交換可能を表す） | 説明 |
|---|---|---|
| プロジェクトの目的・判断 | Arthur | 何を作るか、有効な判断を管理 |
| 開発の実行 | AI-DE ⇄ Execution Harness | 設計／実装／レビュー／テスト |
| AI Agent | Codex ⇄ Claude Code ⇄ OpenCode ⇄ GitHub Copilot | 考える／書く／提案する |
| Development Sandbox | Docker Sandboxes ⇄ 別のSandbox | 隔離環境で実行 |
| 過去の開発知識 | DevLore | 過去資料からKnowledge候補 |
| テスト知識 | Software-Test-Knowledge | 再利用可能なテスト観点 |
| Security | AI-Security-Policy、InputGuardian、LLM-Security-Proxy | AI利用ルール、入力保護、LLM通信保護 |
| GitHub | Issue、Repository、Pull Request | 既存の開発資産を利用 |
| CI | GitHub Actions ⇄ ほかのCI | テスト・検証を自動実行 |

名前は、日本のソフトウェア開発で使われてきた仕様書、過去資料、テストなどの開発文化を活かしながらAIを組み込みやすくするハーネスを目指していることに由来する。
ハーネスの階層については [[AI Development Terms and Harness Layers|AI開発の用語とハーネスの階層]]、ハーネスという考え方は [[Harness Engineering|ハーネスエンジニアリング]] にある。
隔離環境のProvider例は [[Docker Sandboxes|Docker Sandboxesで開発速度と権限設定を両立する]]、Issueを作業単位にする考え方は [[Issue-Driven Development|Issue駆動開発]] にある。

## 作っているのはAIそのものではない

並べてみると、筆者が作っているものの多くはLLMそのものではない。

使っているモデルが少し賢くなれば不要になるものもあるだろう。
一方で、モデルがどれだけ賢くなっても次の問題は残る。

- 誰が何を決めるのか。
- どの情報を信頼するのか。
- 会社として何を許可するのか。

むしろAIへ任せられる仕事が増えたことで、それまで人間が無意識に引き受けていた役割を、システムとして定義する必要が出てきた。
Arthurも、AI-DEも、DevLoreも、Security系の仕組みも、その過程で生まれている。

まだ完成していないものが多く、設計を変えながら作っている途中である。
作ってみたからこそ責任の置き場所がおかしいと分かり、リポジトリを分けたり役割を移したりしたものもある。

AIに仕事を任せるために必要なのは、さらに大きなAIを一つ置くことだけではない。
これまで人間が担っていた判断、実行、経験、テスト、セキュリティを分け、それぞれをAIと人間のどちらからも扱える形にしていく必要がある。
一連のプロジェクトはそのための部品であり、各プロジェクトは設計、実装、使ってみて分かったことまで含めて個別記事で書く予定とされている。
