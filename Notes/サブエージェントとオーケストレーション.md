# サブエージェントとオーケストレーション

AIエージェントを使った開発では、一つのAIにすべての仕事を任せるだけでなく、複数のAIに役割を分けて進める方法がある。
調査を担当するAI、実装を担当するAI、レビューを担当するAIのように仕事を分け、その間の受け渡しまで設計する考え方である。

このノートは、入門向け資料をもとに、サブエージェントの役割、オーケストレーションとワークフローの違い、役割ごとのモデル選択とエスカレーション、「AIの中に組織を作る」という見方を整理する。
管理役方式と引き継ぎ方式の違い、委譲時に渡す情報、並列化、評価、本番運用の難しさは [[複数AIエージェントのオーケストレーション|複数AIエージェントのオーケストレーション]] で扱っている。

## サブエージェントは特定の役割を担当する

中心となるAIエージェントから仕事を受け取り、特定の役割を担当するAIエージェントを **サブエージェント（Sub-agent）** と呼ぶ。
仕事を分解して指示する中心側は **メインエージェント（Main agent）** である。

サブエージェントは担当作業に集中し、必要な情報や結果をメインエージェントへ返す。
一つのAIがすべてを抱えるのではなく、役割を分けることで、仕事の境界をはっきりさせやすくなる。

```text
メインエージェント（仕事を分解・指示）
├─ 調査サブエージェント
├─ 実装サブエージェント
└─ レビューサブエージェント
```

資料が例に挙げる典型的な役割は三つである。

| 役割 | 担当すること | 主な作業 |
| --- | --- | --- |
| 調査サブエージェント | コード、ドキュメント、ログなどを調べ、問題の原因や必要な情報を集める | 情報収集、検索、要点整理 |
| 実装サブエージェント | 調査結果や指示を受け取り、コードの修正や新しい実装を行う | コード作成、修正、テスト |
| レビューサブエージェント | 変更内容を確認し、問題がないか、追加修正が必要かを判断する | 設計レビュー、品質確認 |

サブエージェントは、それぞれ違う役割を持つ担当者として考えられる。

## オーケストレーションは担当者たちの仕事の回し方である

サブエージェントを用意しただけでは、仕事全体はうまく進まない。
調査が終われば結果を実装担当へ渡す必要がある。
レビューで問題が見つかれば実装へ戻し、原因の見立てが違っていれば調査からやり直すこともある。

そこで必要になるのが **オーケストレーション（Orchestration）** である。
複数のエージェントやツールを組み合わせ、次を決めて仕事全体の流れを制御する仕組みを指す。

- 誰に何を任せるか。
- 次に何を実行するか。
- 結果をどこへ渡すか。

この制御を担う役を **オーケストレーター（Orchestrator）** と呼ぶ。
資料の図では、メインエージェントがこの役を担っている。

```text
Orchestrator（メインエージェント）
↓
調査 → 実装 → レビュー
         ↑        │
         └────────┘ 問題があれば戻す
```

サブエージェントが「担当者」なら、オーケストレーションは「担当者たちの仕事をどう回すか」である。

## ワークフローは一本道、オーケストレーションは途中で分岐する

単純な処理なら、調査、実装、テストの順に流せば終わる。
しかしAIエージェントが扱う仕事では、途中の結果によって次の行動が変わる。
原因が分からなければ追加調査が必要になり、レビューで問題が見つかれば修正へ戻る。

資料は、この違いを **ワークフロー（Workflow）** とオーケストレーションの対比として説明している。

```text
Workflow（流れそのもの）
調査 → 実装 → テスト

Orchestration（途中の状態に応じて流れを制御する）
結果を判定 → 次を選ぶ
             ├─ 追加調査へ
             └─ 実装へ
```

オーケストレーションは、サブエージェントを順番に呼び出すだけではない。
途中の状態を見ながら、次に進む先を変えるところに特徴がある。

## サブエージェントごとに違うモデルを割り当てられる

サブエージェントを使う利点は、仕事を分担できることだけではない。
役割ごとに異なるモデルを割り当てられるため、仕事の難しさに応じて、速度、コスト、能力のバランスを変えられる。

ファイルを探す、集めた情報を分類する、決められた形式に整理する、といった比較的単純な仕事なら、最高性能のモデルは必ずしも必要ない。
高速で安価なモデルへ任せれば、システム全体のコストを抑えながら素早く処理できる。

一方、次のような判断には、より高い推論能力が求められる。

- 複数の修正案からどれを選ぶべきか。
- 原因がはっきりしない問題をどう調査するか。
- この設計変更がシステム全体にどんな影響を与えるか。

こうした仕事だけを、能力の高いモデルへ任せることができる。

| 仕事 | 向くモデル | 作業例 |
| --- | --- | --- |
| 情報整理 | 高速・低コストのモデル | 分類、整形、要約 |
| コード調査 | 高速モデル | 検索、候補抽出 |
| 設計判断 | 高性能モデル | 複雑な推論 |

すべてを高性能モデルへ任せず、役割に応じて能力とコストを使い分ける。
どのモデルが何に向くかを測る見方は [[LLMの「賢さ」と品質グラフの読み方|LLMの「賢さ」と品質グラフの読み方]] でも扱っている。

## 難しい仕事だけを上位のモデルへエスカレーションする

この仕組みは、会社の仕事の進め方に似ている。
会社でも、すべての案件を最初から最も経験のある専門家が担当するわけではない。
まず担当者が内容を確認し、自分で処理できるものはそのまま進め、判断が難しい場合にだけ上司や専門部署へ相談する。

AIエージェントでも、これに近い流れを作れる。
最初は高速で安価なモデルに仕事を任せ、そのモデルでは判断が難しい場合だけ、より能力の高いモデルへ引き継ぐ。

```text
高速・安価なモデル（まずここで処理）
↓
判断できるか
├─ できる：そのまま完了
└─ 難しい：高性能モデルへ引き継ぐ（必要なときだけ使う）
```

この「自分では処理できないので、より高い能力を持つ相手へ仕事を渡す」動きは、組織でいう **エスカレーション（Escalation）** に近い。
簡単な仕事まで高性能モデルで処理する必要がなくなり、本当に難しい場面にだけ計算資源を使える。

```text
会社
担当者（まず自分で対応）→ 判断が難しい（相談）→ 専門家・上司（高い能力で対応）

AIエージェント
軽量モデル → 判断が難しい → 高性能モデル
```

## AIの中に組織を作れる

ここまで考えると、サブエージェントを使ったAIシステムは会社の組織図に似てくる。
AIエージェントが本当に会社員になるわけではない。
しかし、人によって担当や権限を分けるのと同じように、AIにも役割と責任範囲を持たせられる。

```text
Manager Agent（全体を管理）
├─ 調査チーム ── 検索 / 整理
├─ 開発チーム ── 実装 / テスト
└─ レビューチーム ── レビュー
```

各役割に適したモデルを割り当てれば、情報収集には高速で安価なモデル、複雑な設計判断には高性能モデル、という構成も可能になる。
現実の会社にある「担当者」「専門部署」「マネージャー」「上位者へのエスカレーション」という構造を、AIシステムの設計にも持ち込めるわけである。

AIシステム全体を「一つの巨大で賢いAI」として作る必要はない。
能力、速度、コストが異なるモデルを複数配置し、それぞれが得意な仕事を担当する組織として設計できる。

## モデルの選択もオーケストレーションの一部になる

オーケストレーションは「どのサブエージェントを呼び出すか」を決める仕組みだと思われがちである。
しかし実際には、その先にあるモデルの使い分けまで含めて考えられる。

オーケストレーターが一体として決めることは三つある。

| 問い | 決める対象 |
| --- | --- |
| 誰に頼むか | どのエージェントか |
| どのモデルを使うか | 能力とコスト |
| 次に何をするか | 仕事の流れ |

同じサブエージェントでも、状況に応じて使うモデルを変えられる。
普段は高速で安価なモデルを使い、難しい問題に遭遇したときだけ高性能モデルへ切り替える、という構成も考えられる。

## モデルの使い分けには三つのパターンがある

```text
① 常に同じモデル
Model A → Model A

② 状況に応じて切り替え
軽量モデル ⇄ 高性能モデル

③ 段階的にエスカレーション
Level 1 → Level 2 → Level 3
```

資料は、固定、状況に応じた切り替え、段階的エスカレーションなど、複数の設計が考えられるとしている。
資料はどれが最適かまでは示していない。

## 設計では四つを判断する

オーケストレーションを設計するときは、役割分担だけでなく、モデル選択、切り替え条件、情報の受け渡しまで決める必要がある。

| 判断 | 決めること |
| --- | --- |
| どの仕事を分けるか | 役割の境界 |
| どのモデルに任せるか | 能力、速度、コスト |
| いつエスカレーションするか | 切り替え条件 |
| 結果をどうつなぐか | 情報の受け渡し |

## サブエージェントを増やせば速く安くなるわけではない

エージェント同士で情報を受け渡す処理にも、時間とコストがかかる。
振り分けを間違えれば、同じ仕事を何度もやり直すことにもなる。

分割の判断基準や、委譲時に目的、担当範囲、返却形式、完了条件を渡す必要性は [[複数AIエージェントのオーケストレーション|複数AIエージェントのオーケストレーション]] を参照する。

## 一言で覚えるなら

サブエージェントは、仕事を分担するための「担当者」である。
オーケストレーションは、その担当者たちへ仕事を配り、結果を受け取り、次の仕事へつなぐ「仕事の回し方」である。

さらに、サブエージェントごとに異なるモデルを割り当てれば、簡単な仕事は高速で安価なモデルへ、難しい仕事は高性能モデルへ、という使い分けもできる。

```text
Orchestrator（仕事を配る）
├─ 高速・安価なモデル ── 軽い仕事
├─ 専門担当 ── 役割に集中
└─ 高性能モデル ── 難しい判断

役割分担 + モデル選択 + エスカレーション
```

能力の違うAIに役割を持たせ、会社のように仕事を分担しながら、一つの目的に向かって動かす。
資料は、これをAI開発にオーケストレーションを持ち込む面白さの一つとしている。
