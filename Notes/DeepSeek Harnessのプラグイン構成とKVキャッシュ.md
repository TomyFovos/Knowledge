# DeepSeek Harnessのプラグイン構成とKVキャッシュ

DeepSeek Harness（DSH）はモデルそのものではなく、モデル接続、ツール、Agent loop、履歴、承認・実行制御を組み合わせるコーディングエージェントの実行環境である。提供資料は、プラグインでの構成変更と、追記専用ログからの履歴生成、サーバー側KVキャッシュとの関係を中心に整理している。

このノートは2026-10-22作成の提供資料を整理したもの。原資料の【事実】【推測】【検討】は調査時点の区分であり、今回の取り込みで外部サイトやコードを再検証したという意味ではない。公式説明、報道、個人の発言、会話中の見立てを同じ確度にしない。

## 構成を変える三つの単位

| 単位 | 提供資料の説明 |
|---|---|
| profile | 起動形態。web、headless、sdk、sdk-minimal、acpの5種類 |
| bundle | 設定とコードを配布する単位。IDによる置換や追加を行う |
| agent preset | モデルへ見せるツール・プロンプト・skillの組み合わせ |

モデルアダプター、ツールレジストリ、Agent loopまで差し替え可能とされる。`dsh-base`はモデル接続、ツール、永続化、サンドボックス・承認、設定、認証情報、テレメトリを含む。`sdk-minimal`は`dsh-base`へ重ねる構成ではなく、独立したプラグイン木と説明されている。

| preset | 主な用途・構成 |
|---|---|
| Standard | ファイル・シェル・Web検索・sub-agent・プランモード |
| Minimal | bashとstr_replace_editor |
| Code | 生成されたTypeScript SDKを通じてプログラムで複数操作をまとめる |
| Creator | 実行時検査、プラグイン実験、preset作成支援 |

Code presetの往復削減例は、すべての処理が常に1回で済むという保証ではない。

## 接続・実行・配布

資料にはWeb UI、SDK、headless、ACPによるエディタ接続と、macOS / Windowsデスクトップ版が記載されている。Web起動例は`npx @deepseek-ai/dsh web`、既定URLは`http://127.0.0.1:3080`。ソース起動にはNode.js 20または22とpnpmを挙げている。今回の追加ではインストールや起動を行っていない。

Claude Code / Codexのsub-agent利用は、各製品のバイナリ・ログインを利用者が用意し、既定では無効と説明される。ACPの公式実装と、人間向け機能を補うコミュニティ実装も分けて読む。

ローカル実行の制御としてLinuxのLandlock、macOSのSeatbelt、Windowsの制限付きトークン・ACLランナーが挙げられている。対応OSの一覧だけで、必要な操作がすべて隔離・許可制御されるとは判断せず、利用する実行経路で確認する。

社内配布の検討案は、共通bundleを含むprofileを配り、個人の調整を`cordis.patch.yml`へ分けるもの。これは会話中の構成案であり、企業の権限管理が一式完成するという説明ではない。

## 履歴は追記専用ログから導く

資料によると、セッションの追記専用ログから`deriveMessages()`でモデル入力の履歴を作り、履歴そのものを別の正本として保存しない。入力種別の追加はイベントとして記録し、再生時も同じログから導出する。コンパクションは過去項目を削除するのではなく、見せる範囲を変える設計とされる。

```text
追記専用セッションログ
        ↓ deriveMessages()
モデルへ渡すメッセージ列
        ↓ 推論リクエスト
プロバイダー側のKVキャッシュ利用
```

ログはハーネスが持つ記録、KVキャッシュは推論側の中間計算の再利用である。同じものではない。

## キャッシュとセッションを分ける

ここで扱う履歴送信方式では、ハーネスが前のやり取りとツール結果をモデル入力へ組み込む。キャッシュが残っているから、後の指示だけを送ってもモデルが前提を知っている、と扱わない。

KVキャッシュが保存するのは、入力をモデルで処理して得るKey / Valueの中間データであり、コマンド結果を独立した業務記録として保存する機能ではない。

| ハーネス側 | 推論プロバイダー側 |
|---|---|
| 会話・ツール結果をログへ記録 | 入力プレフィックスの中間計算を保存 |
| ログから毎回入力を再構成 | 仕様上の一致条件を満たす部分を再利用 |
| 再開と追跡の根拠 | 入力処理の料金・速度に影響 |

資料は一致条件を「前半が同じ文字列」と説明している。実際の一致単位・保持条件は提供者の仕様で確認し、意味が似ているだけでヒットすると判断しない。

キャッシュの失効とログ消失は別である。入力がログから復元できれば、キャッシュが失効していても同じ情報を送り直せるが、処理費用や応答時間は変わりうる。

## 追記方式が有利になる条件

前回の入力を変えずに後ろへ結果・指示を追加する方式は、再利用可能な前半を保ちやすいというのが資料の設計上の説明である。保存・再開できることだけではヒット率の保証にはならず、実際に同じ入力を再構成できるかが問題になる。

DeepSeekのキャッシュは既定有効・ベストエフォートと説明され、usageの`prompt_cache_hit_tokens`と`prompt_cache_miss_tokens`で利用状況を観測する。保持期間、作成までの遅延、失効に左右されるため、再開後も必ずヒットするとは扱わない。

95〜100%のヒット率、入力の約98%がキャッシュ料金だったという資料中の報告は、独立検証済みの一般保証ではない。

## コンパクションのトレードオフ

| 方針 | 得られるもの | 確認する負担 |
|---|---|---|
| 履歴を追記し続ける | 再利用する前半を保ちやすい | キャッシュ読込費、長い入力、古い情報の混入 |
| 要約して短くする | 入力トークンを減らす | 変更された前半の再処理、要約による情報欠落 |

資料では「圧縮直後はミスが増え、その後は圧縮後の入力を基準に追記する」という単純化で損得を検討している。直後に必ず全ミス、次回に必ずヒット、と保証するものではない。

キャッシュ読込は無料ではなく、履歴を長く保つことの費用・速度・精度と、圧縮で失う情報を分けて測る。

## モデル最適化・料金・OpenAI比較の扱い

提供資料はDeepSeek-V4.1-Flash-1017のDSH向け最適化と、DSH v0.2.1-rc.1以降の推奨を紹介している。ツール構成に合わせた学習や往復削減、キャッシュとの相性などの具体的な内訳は、資料でも推測を含む。

料金やDeepSWE / Terminal-Benchの数値は原本に残した。公式発表・報道由来の値であり、今回の実測や独立比較ではない。APIのモデル名・対応バージョン・料金は導入時に再確認する。

OpenAIとの保持期間比較には、APIの公式説明に加え、担当者の発言や報道が混在している。「Codex等は無期限保持・ヒット保証」という資料中の説明を、すべての利用形態に適用される正式なサービス保証として採用しない。適用範囲と第三者検証は原資料にも未解決事項として残っている。

## 自前ハーネスで確認すること

- 再開前後で、同じログから同じモデル入力を作れるか。
- 先頭プロンプトに時刻など変動する値が入っていないか。
- ツール一覧の順序とスキーマが変わっていないか。
- 圧縮の前後で、入力長、ヒット・ミストークン、速度、タスク成績がどう変わるか。
- DSHと自前ハーネスを同じタスク・モデルで比較し、Trajectory、ツール往復、出力、課金内訳を分けて評価できるか。

上記は検証案であり、比較実験を実施した結果ではない。
