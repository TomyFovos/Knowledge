# LLMを理解するためのニューラルネットワーク基礎

LLMには「数十億個の重みがあり、それをVRAMへ載せて計算する」と説明されることが多い。
しかし、重みが何を表し、何のために計算するのかが分からないと、微調整や蒸留で何が変わるのかも理解できない。

このノートは、2026-09-20に [[Custom Model Learning Roadmap|企業専用モデルの学習ロードマップ]] のPhase 0として、PyTorchの小さなモデルを実際に動かしながら確認した内容を整理したものである。
機械学習の知識がない状態から、テンソル、重み、学習、LLMの学習方式、埋め込みまでを順につなげている。
実行環境は [[LLM Training Environment on WSL2|WSL2でのLLM学習環境構築]] で作ったものである。

## テンソルは計算に使う数値の器である

**テンソル（Tensor）** は、AIが計算に使う多次元の数値データである。

```python
import torch

a = torch.tensor([1, 2, 3])
print(a)         # tensor([1, 2, 3])
print(a.device)  # cpu
```

`torch.tensor([1, 2, 3])` は、`torch` モジュールにある `tensor()` 関数を呼び、3個の数値を持つテンソルを作る処理である。
何も指定しなければ、PyTorchはテンソルをCPU側のメモリに作る。

`print(a)` に `device='cpu'` が表示されないのは、CPUが既定値なので表示を省略しているだけである。
デバイス情報が存在しないわけではない。
`a.device` は省略なしで「実際にどこにあるか」を問い合わせるため、`cpu` が返る。

## `cuda()` はテンソルのGPU版を作って返す

```python
a = a.cuda()
print(a)         # tensor([1, 2, 3], device='cuda:0')
print(a.device)  # cuda:0
```

`Tensor.cuda()` は、同じ値を持つテンソルをCUDAデバイス上に用意して返すメソッドである。
元のテンソルそのものを書き換えるのではなく、GPU上にコピーを作る。

```text
CPU側（RAM）
[1, 2, 3]
     │
     │ a.cuda()（コピー）
     ▼
GPU 0側（VRAM）
[1, 2, 3]
     ▲
     │
     a
```

そのため `a.cuda()` だけを実行しても、`a.device` はCPUのままである。
`a = a.cuda()` として初めて、変数 `a` がGPU側のテンソルを指すようになる。
CPU側の古いテンソルを誰も参照しなくなれば、後でPython/PyTorchが解放する。

引数を省略した `cuda()` は、現在選択されているCUDAデバイスを使う。
GPUが1枚だけなら `cuda:0` であり、実質 `a.cuda(0)` と同じである。
GPUが2枚あれば `a.cuda(1)` で `cuda:1` へ置ける。
GPUが1枚の環境で `a.cuda(1)` を実行すると、存在しないGPUを指定したというエラー（`invalid device ordinal` のようなもの）になる。

移動先を明示しやすい `a = a.to("cuda:0")` という書き方もよく使われる。
したがって `cuda()` は「CPUからGPUへ移動する専用命令」と覚えるより、**テンソルを指定したCUDAデバイス上にコピーして返す操作**と理解する方が正確である。

## 要素ごとの演算と行列積は違う

```python
b = a * 10
print(b)  # tensor([10, 20, 30], device='cuda:0')
```

この掛け算はRTX 4070側で処理されている。
これは各要素に10を掛ける **要素ごとの演算（Element-wise multiplication）** であり、行列計算ではない。

本当の **行列積** は `a @ b` や `torch.matmul(a, b)` で書く。
LLMは、この行列積を膨大な回数実行している。

## 重みはテンソルに入った数値であり、入力が出力へ効く強さと向きを表す

**重み（Weight）** は特殊な物体ではなく、テンソルに入った大量の数値である。
ただし単に「モデルが持っている数字」ではなく、**入力された数値を出力へどの程度反映させるかを決める係数**である。

PyTorchの最小の部品で確認できる。

```python
model = torch.nn.Linear(3, 2)
print(model.weight)
print(model.weight.shape)   # torch.Size([2, 3])
print(model.weight.device)  # cpu
```

`Linear(3, 2)` は、3個の数値を受け取って2個の数値を返す、ごく小さなニューラルネットワークの部品である。
会話時点の実行では、次の重みが表示された。

```text
Parameter containing:
tensor([[-0.0570, -0.5442,  0.3951],
        [-0.1819, -0.0693, -0.4873]], requires_grad=True)
```

形が `[2, 3]` なのは、2個の出力それぞれについて、3個の入力に対応する重みが必要だからである。
1個目の出力には1行目、2個目の出力には2行目を使う。
入力と出力の間の接続が6本あり、それぞれに1個の重みが付いていると考えられる。

```text
x1 ─┬────→ y1
x2 ─┼────→ y1
x3 ─┘

x1 ─┬────→ y2
x2 ─┼────→ y2
x3 ─┘
```

## `Linear` は入力に重みを掛けて足し、最後にバイアスを足す

`model = model.cuda()` で重みをGPUへ移し、入力を与えた。

```python
x = torch.tensor([1.0, 2.0, 3.0], device="cuda")
y = model(x)
print(y)  # tensor([ 0.3904, -1.6738], device='cuda:0', grad_fn=<ViewBackward0>)
```

1個目の出力を重みだけで計算すると、次のようになる。

```text
1 × -0.0570 + 2 × -0.5442 + 3 × 0.3951
= -0.0570 - 1.0884 + 1.1853
= 0.0399
```

実際の出力は0.3904で、差がある。
差の理由は、`Linear` が重みとは別に **バイアス（Bias）** を持つためである。
バイアスは、重みによる計算結果へ最後に足される値である。
今回の1個目のバイアスはおよそ0.3505、2個目はおよそ0.1086と推定できる（`print(model.bias)` で確認できる）。

```text
y1 = 1 × -0.0570 + 2 × -0.5442 + 3 × 0.3951 + 0.3505 ≈ 0.3904
y2 = 1 × -0.1819 + 2 × -0.0693 + 3 × -0.4873 + 0.1086 ≈ -1.6738
```

一般には `y = Wx + b` と書く。
式を覚える必要はなく、「入力それぞれに重みを掛け、結果を足し合わせ、最後にバイアスを加えて出力を作る」と理解できれば十分である。

## 学習前の重みにはまだ意味がない

`Linear(3, 2)` を作った直後の重みは、PyTorchが適当な範囲でランダムに初期化した値である。
そのため `[1, 2, 3]` から `[0.3904, -1.6738]` が出ても、その結果には意味がない。
この実習の目的は、有用な答えを出すことではなく、モデルが入力値と重みを使って出力値を作る仕組みを実物で確認することだった。

重みが意味を持つのは、学習によって値が決まったときである。
たとえば設備の状態を判定するモデルを考える。

```text
入力：x1 = 温度、x2 = 振動、x3 = 圧力
出力：y1 = 正常らしさ、y2 = 異常らしさ
```

これも形だけ見れば `Linear(3, 2)` で表せる。
学習後に「異常らしさ」を計算する重みが「温度 × 0.2、振動 × 3.0、圧力 × 0.4」になったとする。
このモデルでは、振動が1増えると異常側の計算結果が3増えるため、温度や圧力より振動の影響を強く受ける。
反対に重みが負なら、その入力が大きくなるほど出力を下げる方向へ働く。

したがって重みは、**各入力が出力へ与える影響の強さと向きを表す係数**である。

## 学習とは正解とのずれを見ながら重みを調整することである

機械学習では、最初はランダムな重みを、正解データに合うよう少しずつ変更する。

たとえば「温度80、振動9、圧力5 → 正解：異常」という学習データに対して、モデルが「正常」と答えたとする。
PyTorchは、どの重みをどの方向へ動かせば「異常」という正解に近づくかを計算し、重みを少し修正する。

```text
初期状態の重み
↓
入力を与える
↓
モデルが回答する
↓
正解と比較する
↓
どれくらい間違っていたか計算する
↓
重みを少し修正する
↓
もう一度やる
```

これを大量のデータで何度も繰り返すと、「この入力が増えたときには、この出力をどの程度動かすべきか」という関係が重みへ保存される。
**学習とは、出力が望ましい結果へ近づくようパラメータを調整する処理**である。

## パラメータ数は全テンソルの数値の合計である

**パラメータ（Parameter）** は、学習によって変更される値の総称である。
`Linear(3, 2)` には重みが6個、バイアスが2個あり、合計8個のパラメータがある。

```python
print(sum(p.numel() for p in model.parameters()))  # 8
print(model.weight[0])  # 1個目の出力を計算するための3つの重み
```

LLMの「3B」「7B」「70B」も同じ種類の数値の個数である。
ただし、70億個のPython変数が並んでいるわけではない。
たとえば4096×4096のテンソル一つに16,777,216個（約1,678万個）の数値が入っており、そうした巨大なテンソルがモデル内部に何百、何千個もある。
その中身の総数が数十億になる。

`a = a.cuda()` と同じ発想で、モデルなら `model = model.cuda()` とする。
するとモデル内部の大量のテンソルがGPUのVRAMへコピーされる。
これが「LLMの重みをVRAMへ載せる」の正体である。

## VRAMの容量はパラメータ数と数値精度で決まる

重み1個を **BF16**（16bitの浮動小数点形式）で保存すると約2byteである。

| モデル | 精度 | 重みだけの容量 |
|---|---|---|
| 3B | BF16（2byte/重み） | 約6GB |
| 7B | BF16（2byte/重み） | 約14GB |
| 7B | 4bit（0.5byte/重み） | 約3.5GB |

RTX 4070は約12GBなので、7BのBF16は重みだけでも入らない。
4bit程度まで小さくすると載せやすくなる。
これが **量子化（Quantization）** である。

## LLMも入力と重みの計算を何層も繰り返している

LLMは文字そのものに重みを掛けるわけではない。
まず文章を **トークン（Token）** という単位へ分け、それぞれを数値のベクトルへ変換する。

```text
「猫」→ [0.14, -0.37, 0.81, 0.22, ...]
「は」→ [-0.08, 0.41, 0.13, -0.52, ...]
```

その数値に対して、重みを使った計算を何十層も繰り返す。

```text
入力されたTokenの数値
        ↓
Parameterを使った計算
        ↓
別の数値表現
        ↓
Parameterを使った計算
        ↓
……
        ↓
次に来そうなTokenのスコア
```

最後に「かわいい 4.8、動物 3.2、犬 1.4、飛行機 -2.7」のようなスコアができる。
これを確率へ変換すると「かわいい 55%、動物 25%、犬 8%……」のようになり、その結果を使って次のトークンを一つ選ぶ。
LLMの内部でも、大量の `Linear` が使われている。

GPUが強いのは、大量の数値同士の計算を並列に行うのが得意だからである。

## LLMは回答全文ではなく次のトークンを一つずつ計算する

LLMは通常、回答全文を一度に計算しているわけではない。

「日本の首都はどこですか？」と入力されると、まず「東京」のような次のトークンを予測する。
入力を「日本の首都はどこですか？ 東京」にしてもう一度計算し、「です」を予測する。
この繰り返しで回答を作る。

```text
入力
 ↓
大量のParameterを使って計算
 ↓
次のTokenを予測
 ↓
そのTokenを入力へ追加
 ↓
もう一度計算
 ↓
……
```

これを **自己回帰生成（autoregressive generation）** と呼ぶ。

## LLMのパラメータは知識を一つずつ保存しているわけではない

LLMのパラメータ一個一個が「Pythonについて答える重み」「猫について答える重み」のように対応しているわけではない。
知識や言語能力は、**大量のパラメータの組み合わせとして分散して保存されている**。
一個だけ取り出して「このパラメータは何を覚えているか」と見ても、通常は人間が意味を読み取れない。

`振動 × 3.0` のような単純な例なら解釈できたが、LLMでは何十億個のパラメータが何層もの計算に関与するため、対応関係はそこまで単純ではない。

それでも役割は、先ほどの重みとつながっている。
LLMのパラメータは、**入力された数値を次の計算結果へどう変換するか**を決めている。

LLMは「質問Aなら回答B」という巨大な回答表を持っているわけではない。
**大量の文章を予測するために調整されたパラメータを使い、現在の文脈に続くトークンをその場で計算している**と考える方が近い。

利用者の「入力されたチャットから、どういう掛け算をしたら答えになりそうかを大量の計算で導いている」というイメージは大筋で合っている。
修正点は、回答全文ではなく次のトークンを一つずつ計算している点である。

## 教師あり学習と自己教師あり学習

人間が正解ラベルを用意して学習させるのは **教師あり学習（supervised learning）** である。
「入力：温度・振動・圧力、正解：異常」のようなデータで、モデルは自分の回答と正解を比較できる。

LLMの最初の学習は「教師なし学習」と説明されることがあるが、**自己教師あり学習（self-supervised learning）** と呼ぶ方が正確である。
文章そのものから正解を自動的に作れるからである。

```text
元の文章：今日は天気が良いので散歩に行った

入力                  正解
今日は                天気
今日は天気が          良い
今日は天気が良い      ので
...
```

人間が一件ずつラベル付けしなくても、次のトークンという正解を作れる。
この仕組みで大量の文章を学習するのが、LLMの **事前学習（Pre-training）** の基本である。

事前学習では、何兆回という規模で「ここまでの文章から次に何が来るか」を繰り返す。
最初は「今日は天気が → 冷蔵庫」のような間違った予測をし、正解「良い」との差からパラメータを修正する。
学習データにはプログラム、歴史、数学、会話、説明文などが大量に含まれるため、調整が積み重なると、文法、単語の意味、概念同士の関係、文章構造、プログラムのパターン、事実関係、推論パターンなどがパラメータ全体の配置として形成される。

## 会話データは役割記号を含む一つのトークン列として学習する

ChatGPTのような会話モデルへ仕上げる段階では、ユーザーの質問と望ましい回答の組を使った **教師あり微調整（Supervised Fine-Tuning, SFT）** を行う。

利用者は、質問と回答を別々に学習していると思っていたために混乱していた、と気付いた。
実際には、質問と回答は役割を表す特殊なトークンを含めて、一続きのトークン列としてモデルへ渡される。

```text
<User>
日本の首都はどこですか？
<Assistant>
東京です。
```

モデルから見ると、これ全体が「<User> → 日本 → の → 首都 → は → どこ → です → か → ？ → <Assistant> → 東京 → です → 。」というトークン列である。

「日本の首都」までの段階では、次のトークンとして「は」「の」「が」「を」などに確率を出し、「は」が高くなる。
「日本の首都はどこですか？ <Assistant>」まで来れば、「東京」「京都」「大阪」「千葉」などにスコアを付け、学習が進んでいれば「東京」が高くなる。

つまり、質問を理解する処理と回答を学習する処理が別にあるのではない。
質問から回答までを含むトークン列の中で、**ここまでのトークンが与えられたとき、次は何が来るか**を繰り返し学習している。

ただし、質問と回答の両方をモデルへ見せることと、質問部分にも学習上の点数を付けることは別である。
現在の会話モデルの微調整では、質問部分を文脈として読ませつつ誤差を計算せず、回答部分だけで正しく出せたかを評価する方法がよく使われる。
質問は回答を作るための条件として使われ、回答側が学習対象になる。
ただし学習実装によっては質問側も含めて誤差を計算する場合があり、「必ず回答部分だけ」とまでは言えない。

推論時には、回答部分はまだ存在しない。
「<User> 日本の首都はどこですか？ <Assistant>」までを入力し、「東京 0.82、京都 0.03、大阪 0.02……」から一つ選び、続いて「です 0.76、は 0.05……」と順に決めていく。

## 事前学習は主に知識、事後学習は主に答え方を担う

```text
Pre-training
    ↓
「何を知っているか」
「言葉をどう扱うか」

Post-training
    ↓
「質問されたらどう答えるか」
「どんな回答を望ましいとするか」
```

事前学習だけのモデルは知識をかなり持つが、質問に親切に答えるとは限らない。
文章の続きを生成する能力を学んだのであって、ユーザーの指示に従う振る舞いを十分には学んでいないからである。

そこで **事後学習（Post-training）** で、質問と望ましい回答の組を学習させる。
教師あり微調整のほか、モデルや世代によってRLHF、RLAIF、DPOなどの方法も使われる。
**RLHF** は人間の評価を使った強化学習、**RLAIF** はAIの評価を使った強化学習、**DPO（Direct Preference Optimization）** は望ましい回答と望ましくない回答の組から直接学習する方法である。

ただし完全に分離しているわけではない。
事後学習でも新しい知識を多少覚え、事前学習の文章から回答らしい書き方も学ぶ。
それでも、知識を持たせる処理と望ましい振る舞いを教える処理を分けて考えると、企業向けAIの設計で役に立つ。
この考え方が、会社固有の知識はRAG、会社固有の振る舞いは微調整という分担につながる（[[Enterprise Local AI Assistant|企業向け完全ローカルAIアシスタント]]）。

## 実習：正解の規則が分かっているモデルを学習させる

「学習すると重みが本当に変わる」ことを確認するため、`Linear(3, 1)` を学習させた。
正解となる重みをあらかじめ知っている状態を作れるので、学習後に正解へ近づいたかを数字で確認できる。

正解は次の規則で作る。

```text
正解 = 2 × x1 - 3 × x2 + 0.5 × x3 + 1
```

この規則はモデルに教えない。
モデルに渡すのは「入力 [1, 2, 3] → 正解 -1.5」のような組だけである。
モデル自身に、重み `[2, -3, 0.5]` とバイアス `1` へ近づいてもらう。

`train_linear.py` の内容は次の通りである。

```python
import torch

# 毎回ほぼ同じ結果になるよう乱数を固定
torch.manual_seed(42)
device = "cuda"

# 1. 教師データを作る：1000件、各3個の数値
x = torch.randn(1000, 3, device=device)
true_weight = torch.tensor([2.0, -3.0, 0.5], device=device)
true_bias = 1.0
y_true = x @ true_weight + true_bias

# 2. 学習対象のモデルを作る
model = torch.nn.Linear(3, 1).to(device)
print("=== 学習前 ===")
print("Weight:", model.weight.detach())
print("Bias:", model.bias.detach())

# 3. 誤差の測り方を決める
loss_function = torch.nn.MSELoss()

# 4. Weightの変更方法を決める
optimizer = torch.optim.SGD(model.parameters(), lr=0.05)

# 5. 学習する
for epoch in range(201):
    y_pred = model(x).squeeze()          # 現在のWeightで答えを出す
    loss = loss_function(y_pred, y_true) # 正解との差を計算する
    optimizer.zero_grad()                # 前回の勾配を消す
    loss.backward()                      # どのParameterをどちらへ動かすか計算する
    optimizer.step()                     # WeightとBiasを実際に変更する
    if epoch % 50 == 0:
        print(f"epoch={epoch:3d} loss={loss.item():.6f}")

# 6. 学習結果を見る
print("\n=== 学習後 ===")
print("Weight:", model.weight.detach())
print("Bias:", model.bias.detach())
print("\n=== 本当の値 ===")
print("Weight:", true_weight)
print("Bias:", true_bias)
```

`uv run python train_linear.py` で実行した結果は次の通りである。

```text

Weight: tensor([[ 0.4414,  0.4792, -0.1353]], device='cuda:0')
Bias: tensor([0.5304], device='cuda:0')
epoch=  0 loss=13.950964
epoch= 50 loss=0.000983
epoch=100 loss=0.000000
epoch=150 loss=0.000000
epoch=200 loss=0.000000

=== 学習後 ===
Weight: tensor([[ 2.0000, -3.0000,  0.5000]], device='cuda:0')
Bias: tensor([1.0000], device='cuda:0')
```

モデルには一度も重みの値を教えていない。
教えたのは「入力→正解」の1000組だけである。
それでも、ランダムだった `[0.4414, 0.4792, -0.1353]` が `[2.0000, -3.0000, 0.5000]` へ変わった。
初めて実機で「学習によってパラメータが書き換わる」ことを確認できた。

表示上 `0.000000` になっている損失は、数学的に完全な0とは限らず、小数点以下6桁では0に見えているだけの可能性がある。
今回の目的では、ほぼ完全に規則を学習したと考えてよい。

## 学習ループの各行が何をしているか

- `x = torch.randn(1000, 3, ...)`：1000行×3列の入力を作る。
- `y_true = x @ true_weight + true_bias`：決めた規則から正解を作る。`@` は行列積である。
- `y_pred = model(x)`：現在の重みで回答する。
- `loss = loss_function(y_pred, y_true)`：正解とどれだけずれたかを測る。
- `loss.backward()`：各重みをどちらへ動かせば損失が減るかを計算する。
- `optimizer.step()`：実際に重みを変更する。

**損失（Loss）** は、どれくらい間違ったかを表す数値である。
今回使った **平均二乗誤差（MSE, Mean Squared Error）** は、正解との差を二乗して平均する方法である。
正解10に対して回答8なら、差2、二乗4になる。
大きく間違えるほど損失が大きくなり、学習は損失を小さくする方向へ重みを動かす。

**勾配（Gradient）** は、各パラメータを「どちらへ、どれくらい」動かせば損失が減るかを表す値である。
`backward()` は方向を計算するだけで、重みそのものはまだ変えない。

実際に変更するのが **最適化手法（Optimizer）** である。
今回の **SGD（確率的勾配降下法）** は単純な更新方法で、たとえば現在0.40の重みに「もう少し大きくした方が損失が下がる」という勾配が得られれば、0.46のように少し変える。
一発で2.0にするのではなく、0.40 → 0.46 → 0.55 → 0.67 → … → 1.99 → 2.00 と徐々に近づく。
`lr=0.05` は学習率である。

`for epoch in range(201)` は学習処理を繰り返す回数である。
今回はデータ全体を一度使うたびに1エポック進んでいる。

この実験は、入力と正解が存在するため教師あり学習そのものである。

## Pythonの構造としての `torch.nn.Linear`

利用者は「torchライブラリのnnクラスのLinearメソッドか」と確認した。
正確には次の関係である。

| 書き方 | 正体 |
|---|---|
| `torch` | PyTorchのパッケージ |
| `torch.nn` | ニューラルネットワーク関連をまとめたサブモジュール |
| `torch.nn.Linear` | Linear層を表すクラス（メソッドではない） |
| `torch.nn.Linear(3, 1)` | Linearクラスからオブジェクトを1個作る処理 |
| `model` | 作られたLinearオブジェクト |

`class Car: ...` に対して `car = Car()` と書くのと同じ関係である。

`Linear` は、PyTorchの `nn.Module` という基底クラスを継承したクラスである。
今後出てくる `torch.nn.Embedding` や `torch.nn.LayerNorm` なども、`nn.Module` を基礎にしたニューラルネットワークの部品だと考えればつながる。

`model` は関数ではないのに `model(x)` と呼べる。
`nn.Module` がオブジェクトを関数のように呼び出せる仕組みを持ち、内部で `forward(x)` を呼ぶからである。
Linearの `forward` では「入力 × 重み + バイアス」が計算される。

`model.weight` は、`model` オブジェクトが持つ属性である。
表示される `Parameter containing:` の **`Parameter`** は特別なテンソルで、「学習によって変更する対象である」という意味を持つ。

## きれいに学習できたのは問題とモデルの形が一致していたからである

正解の規則 `y = 2x1 - 3x2 + 0.5x3 + 1` は線形であり、モデル `Linear(3, 1)` も `y = w1x1 + w2x2 + w3x3 + b` という形しか扱わない。
**正解の構造とモデルの構造が完全に一致していた**ため、きれいに学習できた。

本当の規則が `y = x1² + sin(x2) + x3` なら、単純な `Linear(3, 1)` だけでは完全には表現できない。
この違いが、ニューラルネットワークに複数の層や **活性化関数（Activation Function）** が必要になる理由へつながる。

LLMの微調整でも、最終的には `loss.backward()` で勾配を求め、最適化手法が学習対象のパラメータを変更する。
次の候補として、`backward()` で作られた勾配を表示し、PyTorchがどうやって重みを2や-3の方向へ動かすと判断したかを見る実習が挙がっていた。

## LLMの学習では唯一の正解に一致させるのではない

LLMの学習は、この実験ほど単純ではない。
「この文章を分かりやすく説明してください」に対する望ましい回答は一つに決まらない。
初心者向けに具体例で説明する、短く要点だけ説明する、技術用語を残して丁寧に説明する、など複数の妥当な回答があり得る。

そのためLLMでは、**学習データで望ましいとされるトークン列へ高い確率を割り当てる方向にパラメータを調整する**と考える方が正確である。

```text
学習前：東京 0.20、京都 0.45、大阪 0.15、その他 0.20
学習後：東京 0.85、京都 0.04、大阪 0.02、その他 0.09
```

ここでの損失は単純な数値差ではなく、**モデルが望ましいトークンへどれだけ低い確率しか与えていないか**を表す。
損失が下がるほど、望ましいトークン列により高い確率を与えられるようになる。

ただし、損失が下がってもすべての質問に完璧に答えられるわけではない。
学習データにない表現や、似ているが少し違う質問にも適切に答えられる **汎化（generalization）** が必要になる。

利用者は、実際に学習させたいデータは答えが一意に定まらないため誤差がゼロになるかは分からないが、ランダムな値から誤差が減っていけば欲しい回答に近づく、と理解した。
ChatGPTはこの理解を正しいとしている。

まとめると、**機械学習は、望ましい出力とのずれを損失として測り、その損失が小さくなる方向へパラメータを繰り返し調整する処理**である。
LLMでは、それが「望ましい回答を構成するトークンへ高い確率を割り当てられるようになる」という形で現れる。

## トークンIDと埋め込みは別物である

LLMへ入るのは文章なので、そのままでは重みと計算できない。
そこで、まず文章を **トークンID（Token ID）** に変え、そのIDを計算に使える数値のまとまりへ変換する。
後半を担当するのが **埋め込み（Embedding）** である。

説明用に次の対応表があるとする。

```text
ID 0 = <pad>
ID 1 = 猫
ID 2 = 犬
ID 3 = りんご
ID 4 = みかん
```

「猫 犬 猫」は、トークナイザーによって `[1, 2, 1]` へ変換される。
ただしこの `1` や `2` は単なる識別番号である。
「犬は猫の2倍」や「りんごは猫より3倍何かが強い」という意味はない。
そのため、トークンIDそのものをニューラルネットワークの数値として扱うのは都合が悪い。

## 埋め込みはIDごとの学習可能な数値表である

埋め込みは、各トークンIDに複数の数値を割り当てる表を持つ。
4次元なら、概念的には次のようになる。

```text
ID 0 <pad>   → [ 0.12, -0.31,  0.05,  0.82]
ID 1 猫      → [ 0.73,  0.21, -0.42,  0.15]
ID 2 犬      → [ 0.68,  0.18, -0.37,  0.24]
ID 3 りんご  → [-0.13,  0.92,  0.61, -0.20]
ID 4 みかん  → [-0.08,  0.87,  0.55, -0.15]
```

「猫 犬 猫」は `[1, 2, 1]` を経由して、3行×4列の数値に変わる。
この数値なら重みとの行列計算に使える。

埋め込みも、最初はランダムなパラメータである。
学習を繰り返すうちに、「猫と犬は似た文脈に出やすい」「りんごとみかんも似た文脈に出やすい」「猫とりんごでは使われ方がかなり違う」という情報が損失を通して反映され、値が少しずつ変わる。
その結果、似た使われ方をするトークンのベクトルが似た特徴を持つようになる。

ただし、各次元に「1個目＝動物度」「2個目＝果物度」のような人間が読める意味が必ず割り当てられるわけではない。
意味は多数の次元に分散して表現される。

## 実習：PyTorchで埋め込みを作る

`embedding_demo.py` として、次のコードが提示された。
トークナイザーはまだ使わず、トークンIDを手で用意する。

```python
import torch

torch.manual_seed(42)
device = "cuda"

# Token数は5個、各Tokenを4個の数値で表現する
embedding = torch.nn.Embedding(num_embeddings=5, embedding_dim=4).to(device)

print("=== Embedding全体 ===")
print(embedding.weight)
print("\nShape:")
print(embedding.weight.shape)

# 「猫 犬 猫」に相当するToken ID
token_ids = torch.tensor([1, 2, 1], device=device)
print("\n=== Token IDs ===")
print(token_ids)

vectors = embedding(token_ids)
print("\n=== Embedding後 ===")
print(vectors)
print("\nShape:")
print(vectors.shape)

print("\n=== 1個目と3個目は同じTokenか ===")
print(torch.equal(vectors[0], vectors[2]))
```

`Embedding(num_embeddings=5, embedding_dim=4)` は、5種類のトークンそれぞれに4個の数値を持たせる。
内部には5行×4列、つまり20個の学習可能なパラメータがあり、`embedding.weight.shape` は `torch.Size([5, 4])` になる。

`embedding(token_ids)` は、最初の段階では計算というより **検索表から該当する行を取ってくる** 処理である。
`[1, 2, 1]` なら1行目、2行目、1行目を取り出す。
1個目と3個目は同じトークンID `1` なので、`torch.equal(vectors[0], vectors[2])` は `True` になる。

LLMではこれが巨大になる。
概念的に、語彙が100,000トークン、埋め込みの次元が4,096なら、100,000 × 4,096 = 409,600,000個のパラメータになる。
埋め込みだけで数億パラメータになることもある。

```text
文章
 ↓ Tokenizer
Token → Token ID
 ↓ Embedding
大量の数値を持つベクトル
 ↓
Transformerがベクトル同士の関係を計算する
```

現時点では、**トークナイザーは文字列をIDへ変え、埋め込みはIDを学習可能な数値ベクトルへ変える**という区別がつけば十分である。

会話はこのコードを受け取った段階で終わっており、実行結果はまだ確認していない。
次は実行結果を見ながら埋め込みのどこがパラメータか、学習すると何が変わるかを確認し、その後 **注意機構（Attention）** と **Transformer** へ進む予定とされていた。
