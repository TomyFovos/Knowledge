# AWS Nitro Sandboxesによるワークロードの隔離

AWS Nitro Sandboxesは、同じEC2インスタンス上のEKSポッド、ECSタスク、仮想マシンなどを、ワークロードごとに隔離して動かす仕組みとして紹介される。AIエージェントが生成したコードのように、実行内容を事前に完全には決められない処理が利用例である。

以下は2026-11-10に調査した提供資料の整理。AWSの2026-11-09の発表に基づく記述と会話中の比較を含む。今回の取り込みでは現行の仕様・料金の再確認や環境構築・実測を行っていない。

## コンテナの実行単位と隔離の境界

資料は、通常のコンテナではホストのカーネルを共有し、Nitro Sandboxesでは個々のポッドやタスクを別の軽量VMとして隔てる、と説明する。

```text
EC2インスタンス
  └─ Nitroの隔離機構
      ├─ VM A → ポッド／タスク A
      └─ VM B → ポッド／タスク B
```

隔離するのは実行単位であり、必ずしも利用者や各実行が自動的に別VMへ割り当てられるわけではない。利用者ごと・実行ごとに分けたい場合は、ポッドやタスクの切り方と権限を設計する必要がある。

資料はEKS・ECSで設定を1行変えて使え、Pod Identity、VPC CNI、ストレージ、CloudWatch等も使えるという発表を紹介する。ただし、元資料では各ユーザーガイドを未読としており、具体的な設定項目、対応条件、既存アプリの互換性をこのノートで確認したものではない。

EC2上で直接使う場合は、自分のAMIやオーケストレーション、VMMを組み合わせ、Amazon LinuxとFirecrackerに対応すると資料は記録する。詳細な構成・制約は未確認である。

## 暗号による証明と秘密情報

資料は、環境に関する暗号学的な証明を使い、期待した条件を満たす環境にだけ秘密情報を渡す用途を挙げている。実際に秘密を渡すには、何を証明対象とし、証明結果をどこで検証し、どの条件で鍵を出すかの方針が別途必要になる。

証明が示す対象と、実行コードが安全であることは別の問題である。資料ではアテステーションや鍵の受け渡しの具体的な設定を確認していない。

## ほかの隔離方式との位置づけ

| 方式 | 主な境界・実行場所 | 比較するときの問い |
|---|---|---|
| ローカルのOS権限制御 | 開発者のPC上で、ファイルやコマンド等へのアクセスを制御 | 制御されるツール・ファイル・ネットワークの範囲は何か |
| 通常のコンテナ | ホストカーネルを共有し、プロセス等を分離 | ホストと他のワークロードへのアクセスがどこまで許されるか |
| gVisor等 | アプリとホストの間に別のシステムコール処理を置く方式 | 利用する構成・攻撃面・互換性は何か |
| Docker Sandboxes | 開発者の環境でmicroVMを使う方式として資料が紹介 | 共有する作業フォルダや認証情報は何か |
| Nitro Sandboxes | 自分のAWS環境のEC2上でワークロード単位のVM隔離 | ポッド・タスクの分割とAWS側の権限・通信をどう設定するか |
| 外部のサンドボックスサービス | サービスが提供する隔離環境を利用 | 実行基盤、データの置き場所、運用責任を誰が持つか |

元資料の「壁の厚さ」は概念をつかむための比喩で、製品や構成ごとの安全性を一列に格付けした実測ではない。gVisor・E2Bに関する比較は提供資料でも一次情報未確認と記される。

VMによる分離があっても、共有ストレージ、許可したネットワーク、IAM権限、認証情報、外部ツールへの出口は別に管理する。隔離機構だけで攻撃や情報流出を完全に防げるとは扱わない。
