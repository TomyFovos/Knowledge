# Claude Codeの組織向けセキュリティ設定配布

Claude Codeを組織へ広げるとき、課題は「使わせるか、禁止するか」の二択ではない。
Claude Codeは、ファイルの読み書き、Web検索、コマンド実行まで行える。
便利さの源泉になっている権限が、そのまま情報漏えいや誤操作の原因にもなり得る。

メルカリの事例は、全員へ同じ設定を配るのではなく、利用者の役割に合わせて設定の厳しさを変える方法を紹介している。
組織として越えてはいけない境界は共通化し、その内側で許す自由度を変える考え方である。

## AIエージェントでは端末上の権限が問題になる

チャット型の生成AIは、回答を返しても、最終的な操作は人間が行うことが多い。
一方、Claude CodeのようなAIエージェントは、利用者の代わりにファイルを編集し、コマンドを実行し、ネットワークへアクセスできる。

そのため、モデルの回答内容だけでなく、端末上で何を実行できるかを制御する必要がある。

資料では、主な能力として次を挙げている。

- ファイルの検索、読み取り、書き込み、編集。
- Web検索とページ取得。
- コマンド実行。

コマンド実行を許せば、削除、外部送信、システム設定の変更も技術的には可能になる。
端末上に業務ファイルや認証情報がある以上、利用者の注意だけへ安全性を任せるわけにはいかない。

## 危険な操作の手前に人間確認を残す

資料は、確認を省略する設定を組織側で禁止し、影響の大きい操作では人間の承認を残す方針を示している。

すべての操作を毎回確認させれば安全になるとは限らない。
確認が多すぎると、利用者が内容を読まず承認するようになり、確認そのものが形骸化する可能性がある。

そこで、危険度の高い操作へ確認を集中させる。
例として、任意のシェルコマンドや外部通信を伴う操作が挙げられている。

## 禁止する操作は明示する

人間確認だけでは扱いたくない操作もある。
資料では、認証情報が含まれやすい設定ファイルの読み取りや、`sudo`を使ったシステム変更などを、明示的な禁止対象にする案を示している。

「危険かもしれないので毎回考える」のではなく、組織として許可しない操作は最初から使えないようにする。

## サンドボックスで被害範囲を狭める

**サンドボックス（sandbox）**は、プログラムが操作できる範囲を隔離する仕組みである。
作業対象のディレクトリ外へ触れないようにしたり、ネットワーク接続先を制限したりすることで、AIエージェントが誤った判断をした場合の影響範囲を小さくできる。

これは、モデルへ「この場所へ触れないでください」と指示することとは違う。
指示を守らなかった場合でも越えられない実行境界を作る。

## 組織の方針もエージェントへ渡す

権限設定だけでは表現しにくい行動規範は、システムプロンプトや `CLAUDE.md` のような指示文書で渡せる。

たとえば、機密情報の扱い、外部サービスへの送信、レビューが必要な作業など、組織固有の判断基準を記述する。

ただし、指示文書は強制機構ではない。
禁止事項、承認、サンドボックスと組み合わせて使う。

## 個人設定ではなく端末管理から配布する

利用者へ「この設定を入れてください」と依頼するだけでは、設定漏れや差異が生まれる。
そこで資料では、**端末管理（Mobile Device Management, MDM）**を使い、Claude Codeの設定と組織向け指示を配布している。

端末管理から配ることで、利用者が設定を忘れても、組織が決めた最低限の安全設定を維持できる。

## エンジニアと非エンジニアでは必要な自由度が違う

一律配布には別の問題がある。
組織から強制された設定は利用者が変更できない場合があり、全員へ同じ厳しい設定を配ると、詳しい利用者の作業効率を落とす。

資料では、利用者を少なくとも二種類に分けている。

**エンジニア**は、コマンドや権限の意味を理解し、必要に応じて自分で設定を調整したい。

**非エンジニア**は、細かな安全設定を自分で設計することを前提にせず、最初から安全な状態で使いたい。

両者へ同じ設定を配ると、厳しすぎるか、緩すぎるかのどちらかになりやすい。

## 共通の禁止境界と、役割別の設定を分ける

メルカリの事例では、端末管理にある利用者情報を使い、配布する設定を分けている。

組織として禁止する操作は共通にする。
その上で、エンジニアには安全性を保ちながら調整できる余地を残し、非エンジニアには利用者側の設定作業を求めない厳しめの初期値を配る。

この構成は、次の層へ分けて考えられる。

1. 組織として越えてはいけない禁止事項。
2. 危険な操作の前に置く人間承認。
3. サンドボックスとネットワーク制限による実行境界。
4. 指示文書で伝える組織方針。
5. 利用者の役割に応じた設定プロファイル。
6. 端末管理による強制配布。

安全性と生産性を一つの設定値で調整しようとすると、どちらかへ無理が出る。
責任の種類を分けて設計することで、共通の安全境界を保ちながら役割ごとの自由度を変えられる。
