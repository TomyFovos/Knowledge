# AI開発をコーディングから工程管理へ広げる

提供された原稿は、AIにコードを書かせるところから、仕様、レビュー、差し戻し、権限、完了条件までを管理するAI-DEへ進んだ経験を記録している。

原稿の著者の経験・設計動機として読む。特定モデルの性能や、製品機能の現在仕様を今回検証したものではない。

## 試したことと残った問題

| 試み | 得られたもの | 次に残った問題 |
|---|---|---|
| 詳しいプロンプト | 背景・制約・過去の問題を伝える | 毎回すべての必要情報を人間が把握・入力するのは難しい |
| コーディングエージェント | ファイル探索、実行、テストをAI自身が行う | 情報取得だけでは開発全体の抜けはなくならない |
| セッション引継ぎ用の説明資料 | 背景の再説明を減らす | 後付け資料より、仕様を先に決める形へ進んだ |
| 仕様書中心の開発 | 何を作るかを残す | 仕様があっても実装漏れや不正確な完了報告があった |
| 別セッションでのレビュー | 実装担当が見落とした問題の発見 | 人間が実装・レビュー・修正の伝言係になった |
| 工程・Gateの管理 | 条件を満たした場合だけ次へ進める | 証拠、権限、通信、Model選択等も統合する必要が生じた |

## 完了報告と完了の証拠は別

原稿では、実装完了・テスト成功と報告された成果物に、仕様の未実装と「V1はテンプレート、実装はV2」といった記述が残っていた経験がある。

この経験は、仕様書を渡すことやテストが通ることだけで、そのテストに含まれない要求まで満たしたと判断しない、という教訓につながっている。自己申告の確認、要求と成果物の対応、別視点のレビューが必要になる。

## 人間が仲介していた工程も対象にする

```text
仕様 → 実装 → 別の視点でレビュー
             ↑       ↓ 問題あり
             └─ 修正・再確認
                      ↓ 条件を満たす
                    次工程
```

役割を増やすだけでなく、必要資料の参照、指摘の受け渡し、差し戻し、再評価、完了条件を仕組みにする。原稿は、コードを書く能力と、一連の開発を安定して任せられることを別の問題としている。

原稿には別レビューで品質が改善した経験があるが、実装・レビューの役割を分けたことだけで検証の独立性が保証されるわけではない。これは既存の[[AI開発における理解負債]]とも合わせて読む。

## 目指している状態

人間は目的・要求・採用判断・受け入れを担い、その間の製造・検証・調整をAIと実行基盤へ委譲する。モデル性能だけを待つのではなく、情報へアクセスできる環境、誤りを検出する工程、自己申告に依存しない完了条件を整えることが中心になる。
