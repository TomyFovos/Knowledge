# Perplexity SPACEによる自社ホスト型AI開発環境

Perplexity SPACEは、AIエージェントなどが実行するコードをFirecracker microVM内に隔離し、環境の作成、コマンド実行、状態保存・復元、削除をAPIで管理する基盤である。OSやLLM、完成済みのクラウドIDEではない。

このノートは2026-10-19更新の提供資料を整理したもの。以下の「資料で確認」は元資料の調査区分であり、今回の取り込みで公式サイトを再検証したという意味ではない。構成案・試算・未確認事項は、製品の標準機能や動作保証と区別する。詳細と全出典は末尾の原本に残している。

## 検討の目的と現時点の判断

目的は、自社管理サーバーを使い、社員ごとのAI開発環境を配布して、どのPCからでも作業を続けられるようにすることである。

**提供資料の判断は、少人数の遠隔利用ならDocker LocalのPoCを先行し、社員別の自動払い出しや複数ホストの中央管理が必要になった段階でSPACEを比較する、というもの。** 遠隔アクセスができること、同じ環境設定を配れること、利用者ごとの権限とライフサイクルを安全に管理できることは、それぞれ別の課題である。

## SPACEが担当する範囲

資料で確認されている中心機能は、テンプレートからのmicroVM生成、コマンド実行と出力取得、Pause、Suspend、復元、削除、非同期Operationの追跡である。

| 概念 | 役割 |
|---|---|
| Template | 再利用する初期ファイルシステム・ランタイム構成 |
| Sandbox | 個別microVMと書き込み可能なファイルシステム |
| Process / Command session | ゲスト内プログラム、実行開始・出力接続のセッション |
| Operation | 作成・復元・削除などの非同期処理の進行管理 |

公式Kind構成は、HTTP API、PostgreSQL、コントローラー、ワーカー、Firecracker、出力用データプレーン、テンプレート・スナップショット用ストレージからなる。Kubernetesは公式Kind手順で使うが、SPACEそのものの必須要素ではない。非Kubernetes構成が同じ手順で導入できるという意味でもない。

社内SSO、ポータル、社員IDとVM所有者の対応、IDE・ターミナルへの中継、Git連携、クォータ、監査は利用側で設計する。

```text
社員PC → 社内SSO・開発ポータル → 自社の払い出しサービス → SPACE API
                           ↓                            ↓
                   IDE・端末への接続中継          社員別microVM
                                                       ↓
                                               Git / 外部LLM API
```

この図は構成案であり、SPACEに一式同梱される製品構成ではない。

## Docker Local・Docker Cloud・SPACEの比較

以下は提供資料の2026-10-19時点の比較である。

| 項目 | Docker Local | Docker Cloud | SPACE |
|---|---|---|---|
| 実行場所 | 自社の対応Linuxホストも候補 | Docker管理クラウド | 自社管理Linux / KVMホスト |
| 遠隔利用 | ホストSSHなどの入口を追加検証 | Cloud専用SSHあり | API実行に加え、IDE・SSHゲートウェイを自社設計 |
| 共通設定の配布 | Kits、`sbxenv.yaml` | Kits、Cloud対応環境設定 | テンプレートのビルド・公開 |
| 社員別の自動払い出し | ホストCLIの外側に処理を設計 | REST API / SDK | Native API、コントローラー、ワーカー |
| 利用者分離 | OSユーザー、デーモン、ログイン、作業領域を検証 | Dockerアカウント・権限を確認 | SSOとVM所有者・接続権限の結合を設計 |
| 複数ホスト管理 | 外側の配置管理を設計 | Dockerが運用 | 中央APIとワーカー管理を評価できる |
| 実装改変 | 実行基盤の内部改変を前提にしない | 管理側は変更不可 | Apache 2.0のソースを改変・運用できる |

SPACEだけがmicroVM、API、状態保存、ネットワーク制御を持つわけではない。主に比較するのは、配置場所、ソース改変の自由度、中央管理と運用の責任範囲である。

### SSHは三つの方式を区別する

- **Docker Localの`ssh 名前.sbx`**：`ProxyCommand`が実行ホストの`sbx`デーモンへローカルソケットで中継する。別PCからVMのIPへ通常のTCP SSHをすれば届く、という仕様ではない。社員PCからUbuntuホストへSSHし、ホスト上で各自の`sbx`を使う構成は検証案になる。
- **Docker CloudのSSH**：Docker管理クラウドへの専用接続。Localの`.sbx`とは接続先・認証が異なる。別社員が同じ稼働VMへ接続できる権限条件は未確認。
- **SPACEの`space-ssh`**：ホスト側でネットワーク名前空間を取得し、`sudo nsenter`等を使う管理ツール。社員PC向けの汎用リモートSSHサービスと同一視しない。

Kitsや`sbxenv.yaml`で初期設定を共有することは、同じ稼働VMや所有権を共有することではない。Docker Governanceも組織ポリシーの配布・強制であり、社員別VMの払い出しとは別で、資料では別途有料契約が必要とされる。

## ライフサイクルと資源の扱い

| 状態 | メモリ・状態 | 運用上の意味 |
|---|---|---|
| Running | 実行中VMのメモリとFS | CPU・RAM等を使用する |
| Paused | メモリをワーカー内に保持 | 実行は止まるがRAM解放策にはならない |
| Suspended | メモリ・実行状態・ルートFS等をスナップショット化 | アクティブVM資源を解放し、後で復元する |
| Deleted | APIから利用不能 | 環境を終了・削除する |

資料によるとNative API作成環境は標準で6時間の非活動後に自動Suspendする。最大存続期間が6時間という意味ではない。Pauseは耐障害性のある保存と区別し、ファイルの永続化保証もライフサイクル境界で確認する。

Warm Poolは起動済み環境を待機させ、作成待ち時間を短くする代わりに資源を使う。Native APIのKubernetes上のPool利用には環境変数とフィーチャーフラグ双方の条件があり、カスタムディスクやファイル変更追跡などには対象外条件がある。

E2B Compatibility Wrapperは限定的な互換層である。資料で検証対象とされるのは`e2b==2.21.1`、`e2b-code-interpreter==2.6.2`。ECWのpauseはSPACEのSuspendに対応し、resident-memory Pauseと同じではない。

## Proxmoxに置く構成案

```text
物理サーバー
└─ Proxmox VE（L0）
   └─ Ubuntu Server VM（L1、SPACEホスト）
      ├─ API / Controllers / PostgreSQL等
      └─ Firecracker microVM（L2、社員別環境）
```

Nested Virtualizationが必要になる。資料にある公式Kind手順の前提は、apt系Linux x86_64、KVM、`/dev/kvm`、`/dev/net/tun`、loopデバイス、btrfs、特権コンテナを扱えるDockerである。

CPUタイプ`host`や仮想化拡張の露出は検討候補だが、異なるCPU間のライブマイグレーションへの影響も確認する。**SPACEのProxmox公式サポート、実機起動、復元、性能、可用性は未確認。** LXCへの直接配置を前提にせず、まずUbuntu VMで公式手順の要件を満たせるか検証する案である。

## GPU・RAM・CPU・SSDの見積もり

外部LLM APIだけで推論するなら、LLM推論用GPUは通常不要という構成上の判断になる。CUDA処理やGPUテスト等は別であり、SPACEのGPU対応は未検証である。コード実行基盤を社内に置いても、外部モデルへ送るデータまで社内完結するわけではない。

**以下は1環境4GiBと置いた設定容量の単純合計で、実測値や公式推奨値ではない。**

| 同時稼働・待機環境 | 設定メモリ合計 |
|---|---:|
| 5環境 | 20GiB |
| 10環境 | 40GiB |
| 20環境 | 80GiB |
| 稼働10＋Warm Pool 5 | 60GiB |

実際にはVM実消費、待機VM、ホスト・DB・サービス、キャッシュ、余裕を合算して測る。ビルド・テスト・言語サーバーのCPUピーク、SSD I/O、テンプレート・スナップショット容量、バックアップも必要になる。

SPACE内でSuspendしても、外側のUbuntu VMに割り当てた物理RAMがProxmoxへ直ちに返るとは限らない。ゲスト内再利用と外側のバルーニングを分けて考える。

資料の60msという作成レイテンシ中央値はPerplexity本番条件の実測であり、自社Proxmox環境の保証値ではない。

## 公開段階・セキュリティ・運用責任

資料では2026-07-15の設計発表と、2026-10-15のApache 2.0によるソース公開を区別している。資料時点の互換性基準は0.8.0で、0.9.0には破壊的変更予定、安定API契約の目標は1.0.0とされる。

管理APIのBearerトークンとコマンド接続のattachment tokenは別の権限であり、共通トークンを全社員へ配る設計にしない。SSO、所有者権限、通信制御、秘密情報の保管・失効、暗号化、バックアップ、監査、退職者の削除を利用側で設計する。

元資料のレッドチーム報告要約ではVM脱出0/108件に対し、修正前の一部ネットワーク許可条件で通信ポリシー回避11/54件が記録されている。VM隔離とネットワーク制御は別の境界であり、この結果は安全性全般の保証ではない。

Perplexity Computerの法人向けSSOや管理・保証がSPACE OSSに付属するとは確認されていない。ライセンスによる商用利用と、自社の運用・セキュリティ責任も分けて評価する。

## 検証の順序（提供資料のPoC案）

1. Proxmox上のUbuntu VMでNested VirtualizationとKVM要件を確認する。
2. Docker Localを検証し、2人分の別LinuxユーザーでDockerログイン、デーモン、VM、ファイル、秘密情報を分離できるか試す。
3. 社員PC→ホストSSH→各自のSandboxという接続と、切断・再接続、VS Code接続を検証する。
4. Kits・`sbxenv.yaml`で共通環境を再作成し、2・5・10環境など実機容量に応じた同時利用を測る。
5. 中央管理が必要ならSPACE公式Kind構成を試し、作成・実行・Pause・Suspend・復元・削除をAPIで再現する。
6. 社員IDとVM所有者を結ぶゲートウェイ、IDE接続、クォータ、複数ワーカー、Warm Poolの費用と運用負担を比較する。

この取り込みでは環境構築やPoCは実行していない。上記は資料にある今後の検証案である。
