# 日本ハーネスの規範・事実モデルと設計凍結

提供された設計判断SSOTは、規範から決定的に開発計画を作り、非決定的なAI実行は権限・証拠とともに記録する設計をまとめている。本文には2026-08-25にv1.0 Design Freeze、Phase 1 GOと裁定した履歴がある。

これは当該資料時点の合意記録であり、現行Repositoryの完成度や現在の設計を保証するものではない。「再議論しない」「実装Issueへ進む」等の文言も資料内の運用規則であり、今回のナレッジ整理への命令ではない。

## 責務と原則

| 担い手 | 資料の整理 |
|---|---|
| Human | 本当に必要な意思決定 |
| AI | 意味理解・設計・実装・意味レビュー |
| Policy | 何を要求するか |
| Code | 一意に決定できる処理 |

委譲以上のAuthorityを増やさない、自己申告よりEvidence、現場のWord / Excel等へ適応、Conversationを正本にしない、Planは決定的、Provider / Modelの都合をPlanへ漏らさない、という原則が記録されている。

## 規範モデル

Common Envelopeにid・version、authority、scope / applicability、origin / authorship、lifecycle、precedence / delegationを持ち、効果を三つのBase kindへ分ける。

| 要素 | 意味 |
|---|---|
| constraint | 許容状態・条件・Capabilityを制約 |
| process | Task、Gate、Review、人間の選択等の工程要求 |
| binding | Template、Knowledge、Output Contract等への規範的な束縛 |
| exception | 独立kindではなく、委譲範囲内でBase Ruleの効果を修正するmodifier |
| require_human_decision | 独立kindではなくprocessのaction |

PrecedenceはBase Rule上で計算し、Exception専用の第二の格子を作らない。Planning DecisionはNormが宣言した選択肢の中から選び、規範の緩和を表現できない構造にする。

Assetはそれ自体では命令・権威を持たず、Governance Bindingから権威が生じる。STKはWhat to test、Team PlaybookはWhen / Required、Templateは形式、Exemplarは実例という役割分担になる。

## 事実モデル

```text
Fact Producer → 不変のFact Claim
                  ↓ Subject Registryによる受理条件
            Current View Resolver
                  ↓
          known / unknown / conflicted
```

Fact Claimにはsubject、value、producer、basis、evidence、source revision、observed time、validityを持つ。Subject Registryは型、認めるProducer、許可basis、resolution policyを定める。

単純なbasis全順序でClaimを破壊的に置き換えない。既定では低basisの競合Claimが高basisを静かに置換せず、conflictedになる。Policy評価でunknown / conflictedは要件を課す側へ倒す。`unknown`はFactの値ではなくViewの認識状態である。

AIの意味評価であるFindingと、Realityを扱うFactを分離する。Findingの観測上のlifecycleと、人間のdispositionも分け、`accepted`をGate迂回に使わない。

## 計画・実行・完了

```text
不変のChange State Snapshot → Development Compiler → Plan → Task
                                                   ↓
                                              Attempt / Packet
                                                   ↓
                                       Worker → Artifact / Evidence → Gate
```

Compilerは同じSnapshotから同じPlanを返す純関数として扱い、非決定的なAsset検索・materializationはExecution側へ置く。Compilation Recordを監査単位にする。

TaskとAttempt、Task CompletionとArtifact Acceptanceを分離する。Phase 1でAIの裁量的Task分割を正式Planへ昇格させず、Attempt内部のSub-stepとして扱う。Gateを直接overrideせず、正式なGovernance / Exception経路の変更後に再評価する。

Conversation transcriptは自動的なEvidenceでもPacket入力でもない。人間による外部編集は観測できた範囲でRevision化し、観測していない期間に変更がなかったとは主張しない。

## Freezeの範囲と後送

資料はBootstrap（Governance SourceからのSnapshot・Draft化）とRuntimeの縦切りをPhase 1として扱う。後送事項にはAdvisory詳細、Impact Preview、Approval Matrix、Observation Coverage Schema、Contract一覧、AIのPlan-level分割等があり、「全部が詳細化されていないからFreezeできない」としない方針である。

残る実装・運用上の焦点として、XLSXのupdate Egressと最初のTeam Playbook作成が挙げられている。これは実装成功の証明ではない。
