# AnthropicのAIコードレビューと人間の説明責任

AIが大量のコードを生成する環境では、コードの検査だけでなく、変更の目的、リスク、設計、検証範囲、採用の責任を分けて扱う必要がある。提供資料はAnthropicの公開運用を調べ、人間が全行を再検査する以外の役割と、その限界を整理している。

このノートは2026-10-21作成の提供資料を、2026-10-22に取り込んだもの。原資料の「公式情報」は調査時点の引用・要約区分であり、今回の追加で記事や製品の現行仕様を再確認したという意味ではない。Anthropicの公表内容と、会話で一般化した業務開発への考え方を区別する。

## 公開運用：複数の検査層と復旧を組み合わせる

提供資料が紹介する2026-10-15の記事は、6つの層と、検知・ロールバックによる補完を説明している。

| 層 | 資料で紹介された内容 |
|---|---|
| PR作成前 | テスト、ビルド、スクリーンショット、E2E、別文脈のsub-agentレビュー等 |
| PRでのAIレビュー | 目的・コードベースを踏まえた複数Agentの検査 |
| セキュリティレビュー | 独立した自動検査と指摘に応じたマージ制限 |
| CI | Lint、型、環境別テスト、ビルド |
| リスク別の人間承認 | 変更のリスク・対象パス等に応じた承認 |
| マージ・段階的リリース | マージキュー再検証、Feature Flag、社内先行利用、段階展開 |
| 補完 | テレメトリー、オンコール、Flag無効化、差し戻し |

PR前にも検証するが、CI等をすべて終えてから初めてPRになるわけではない。マージ前に全不具合を発見できるとは想定せず、出荷後の検知と復旧も含める。

プロジェクト文脈を`CLAUDE.md`、領域固有の障害パターン・確認事項等を`REVIEW.md`へ置き、繰り返す問題をLint、スキル、指示へ反映する運用が記載されている。これらは当該運用の説明であり、このRepositoryへ同じファイルや規則を導入する指示ではない。

## 公開運用：リスク別の承認

| リスク | 資料に挙げられる例 | 人間の承認 |
|---|---|---|
| 低 | 文書、文言、社内向け機能、Flag保護された追加 | 条件により0人 |
| 中 | 通常の製品変更、キャッシュ、アップデーター、システムプロンプト等 | 1人 |
| 高 | 特に重大なコード、指定された高リスクのパス | 2人 |

人数だけで一般化しない。分類器、重要パス、CI変更、信頼された作成者、承認対象コミット等の追加条件がある。指示した人間が承認者の1人と数えられる場合はあるが、AIの承認で必要な人間の枠は埋めない。

社内で低リスクの自動マージがあることと、外部向けCode Review製品が承認権限を代行することは別である。提供資料は製品のGA、対象プラン、深度・所要時間も扱うが、提供条件は原本と導入時の最新情報で確認する。

記事時点では、障害率等の悪化に応じて承認を自動厳格化する仕組みは未実装とされる。低リスク分類そのものも誤りうる。

## AIレビューの品質と収束

資料では、探索役と指摘の妥当性を確認するAgent群を分け、スタイルだけの指摘を減らす工夫が紹介されている。一方、50回超の修正・レビューが続いた例もあり、回数を重ねるだけで良いとはしない。

3ラウンドを超えたら実装方針を再検討する、新しい差分へ再レビューを絞る、既出指摘を繰り返さない等の対応が記載される。実障害と修正・差し戻しを評価セットへ追加し、既知の正常PRへの誤検出も観察する。

資料にある差し戻し減少や指摘率の上昇は、公表された運用指標である。単独の検査による因果効果、検出精度・再現率そのものとは区別する。

## 公開記事が人間へ残す五つの判断

1. そもそも作るべきか。目的、品質感、スコープ、既存方針に合うか。
2. 高リスク変更を許容できるか。
3. 今後模倣されるアーキテクチャ・設計パターンとして適切か。
4. 検証の内容と、見逃しうる範囲を理解して結果を信用できるか。
5. 誰が結果の責任を引き受けるか。

人間が必ずAI以上のバグ検出能力を持つ、という前提とは異なる。AIに渡っていない顧客合意や運用制約も判断材料になる。ただし高リスクな技術判断には相応の専門性が必要であり、形式的に人数を満たすだけでは品質保証にならない。

## 検討結果：検証の実行・十分性・受容を分ける

| 段階 | 判断すること |
|---|---|
| 実行 | Lint、テスト、AIレビュー等を実際に動かしたか |
| 十分性 | 必要な仕様・リスクを検査したか、未検査領域は何か |
| 受容 | 残る不確実性と復旧手段を踏まえて採用してよいか |

テストの成功は、その条件を満たした証拠にはなるが、存在しないテスト、誤った期待値、仕様の妥当性まで保証しない。AIの説明も、対象コミット、実行ログ、実物に照らして確認できる必要がある。

## 検討結果：説明責任の三層

以下は提供資料の会話で整理された枠組みであり、Anthropicの正式な社内標準の名称ではない。

| 層 | 説明する内容 | 根拠の例 |
|---|---|---|
| 追跡・監査 | 何を変え、何を検証し、誰が承認したか | コミット、要求ID、CI・レビュー・承認履歴 |
| 採用判断 | なぜ選び、何を残余リスクとして受容したか | 要件、設計、代替案、検査範囲、未確認事項 |
| 是正・結果責任 | 障害時に誰が調査・修正・顧客説明するか | 担当・権限、運用体制、復旧策、インシデント記録 |

監査ログがあることは、担当者が顧客仕様を理解し、妥当性を判断できることとは別である。技術的な担当範囲と組織・契約上の責任も同じとは限らない。

提供資料は、Anthropicの別の公開記事にあるShadow Mode、リスク別の抜き取り監査、自動承認理由やツール・Agent間通信の記録、SIEM、再評価も紹介する。これらを、判断能力や説明責任全体の自動保証とは扱わない。

## 検討結果：小さな変更と意図・証拠の関連付け

| 記録先 | 残す情報の例 |
|---|---|
| 要求・チケット | 必要性、利用者、制約、期待結果 |
| 設計・計画 | 対象、代替案、検証方針 |
| コミット | この単位の変更内容・理由、要求ID |
| PR | 影響、テスト、リスク、未確認点、復旧方法 |
| 検査ログ | 実行条件、結果、指摘と処理 |
| 承認履歴 | 対象コミット、承認者、判断根拠 |

AIが下書きを作り、人間がリスクに応じて照合・修正する役割分担は検討できる。すべての説明を手書きすることも、すべてをAIの自己申告へ委ねることも必須ではない。

教材で紹介される`intent.md`、`spec.md`、`plan.md`等は推奨パターンであり、全社必須のファイル名として一般化しない。

## 検討結果：ハーネスへの理解と信頼

Agent harnessは実行を調整する環境、evaluation harnessは定義済み課題を実行・記録・採点・集約する評価基盤として区別する。

同じ課題で通常実行とハーネス適用を比べることは、利用者が差や限界を学ぶ助けになる。一方、数回よい出力を見た納得と、正解付き課題での客観的性能評価は別である。モデル・ハーネスの版、入力、変える条件、誤検出・見逃し、時間・費用、複数試行の変動を分けて記録するというのが会話の整理である。

## 検討結果：試作後に採否を決める

試作が安くなれば、実物を比較してから採用・変更・中止を決められる場面が増える。ただし、予算・期間、利用データ、評価基準、採用権限、顧客や契約の制約まで不要にはならない。上流工程の廃止ではなく、実装・比較を意思決定に使える範囲の変化として捉える。

## 未解決の問い

- 人間の承認者に必要な専門能力をどう確かめるか。
- 高度なAIレビューを人間が独立に評価できない場合、何を採用根拠にするか。
- 逐行レビューを減らした後、チームのシステム理解・教育・保守能力をどう維持するか。
- AIが作る説明・証拠・リスク分類をどの程度独立に照合できるか。
- リスク誤分類や未知の課題・環境変更に対し、評価と復旧がどこまで通用するか。

これらは提供資料に残る論点であり、今回の取り込みで実装計画や作業優先順位を決めたものではない。
