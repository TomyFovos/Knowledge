# Issue駆動開発

Issueを単なるタスク管理項目ではなく、開発作業の入口、実行単位、履歴の起点として扱う考え方がある。
これを **Issue駆動開発（Issue-Driven Development）**と呼ぶ。
AIコーディングエージェントを使う開発では、Issueは「人間のToDo」から「AIへ渡せる作業契約」へ役割を広げられる。
元資料は、これを完全に新しい方法論ではなく、既存の考え方をAIエージェントによる実行へ合わせて再構成したものとして整理している。

## チケット駆動開発をGitHub IssueとAIエージェントへ持ち込んだもの

似た考え方として、日本では以前から **チケット駆動開発（Ticket Driven Development, TiDD）**が知られている。
TiDDでは「No Ticket, No Commit」という考え方が代表的である。
コードを変更する前にチケットを作り、その変更をチケットと対応付ける。

Issue駆動開発は、この考え方をGitHub Issueなどへ持ち込み、AIコーディングエージェントによる開発と組み合わせやすい形へ発展させたものとして捉えられる。

ただし、「Issue-Driven Development」という名称に業界共通の厳密な標準定義があるわけではない。
実際の運用では、チケット駆動開発、**GitHub Flow**（ブランチを切ってPull Requestでレビューし、mainへmergeする軽量な流れ）、Issue中心のエージェント作業フローなど、複数の考え方が重なっている。

## Issueは理由から完了までを追跡する基点になる

典型的なIssue駆動開発では、次のように進める。

```text
要求 / バグ / 改善案
        ↓
Issueを作成
        ↓
背景・要求・受け入れ条件を記述
        ↓
Issueを作業単位として着手
        ↓
branch / worktree
        ↓
調査
        ↓
設計・計画
        ↓
実装
        ↓
テスト
        ↓
Pull Request
        ↓
レビュー / CI
        ↓
merge
        ↓
Issue close
```

この構造では、Issueは「何をするか」を示すだけではない。
その変更が必要になった理由、完了条件、実装結果までを追跡する基点になる。

## AIエージェント向けのIssueは作業契約に近い

人間向けのタスク管理なら、Issueに「ログイン画面を修正する」とだけ書かれていても、担当者が周辺状況を確認し、不足している情報を補いながら作業できる。

一方、AIエージェントへまとまった作業を任せる場合、Issueには少なくとも次の情報が必要になる。

- なぜ変更するのか。
- 何を変更するのか。
- どこまでを対象とするのか。
- 何を変更してはいけないのか。
- どの状態になれば完了なのか。
- どのように検証するのか。

このため、AIエージェントを前提としたIssueは、単なるToDoよりも **作業契約** に近い。

```text
Issue
├─ Background           背景：なぜ変更するのか
├─ Goal                 目的：何を変更するのか
├─ Scope                範囲：どこまでを対象とするのか
├─ Constraints          制約：何を変更してはいけないのか
├─ Acceptance Criteria  受け入れ条件：どの状態なら完了か
└─ Verification         検証方法：どう確かめるか
```

エージェントは、このIssueを入力としてコードベースを調査し、実装し、テストし、Pull Requestを作る。

Issueが十分に書かれていれば、AIエージェントはIssue単位で比較的独立して作業できる。
反対に、Issueが単なるメモのままなら、エージェントは不足している前提を推測する必要があり、作業品質が不安定になる。

## IssueとPull Requestの対応を追跡できる状態を保つ

Issue駆動開発は、変更単位をできるだけ小さく保ち、IssueとPull Requestの対応を明確にする運用と相性がよい。

```text
Issue #101
    ↓
調査・実装
    ↓
PR #201
    ↓
レビュー・CI
    ↓
merge
    ↓
Issue #101 close
```

必ずしも「1 Issue = 1 PR」でなければならないわけではない。
大きなIssueを複数のPRへ分割する場合もある。
重要なのは、Issueの目的とコード変更の対応を追跡できる状態を維持することである。

## 仕様駆動開発とは競合せず、階層が違う

Issue駆動開発と [[仕様駆動開発|仕様駆動開発]] は競合する考え方ではない。

仕様駆動開発は、「システムや機能として何を実現するのか」を定義することに重点を置く。
Issue駆動開発は、その仕様や要求を「どの変更単位で実行するのか」に重点を置く。

| 比較軸 | 仕様駆動開発 | Issue駆動開発 |
|---|---|---|
| 中心 | 仕様（Spec） | Issue |
| 主な役割 | 作るものを定義する | 実行する変更を定義する |
| 粒度 | システム、機能、要求 | 一つの変更、修正、改善 |
| 寿命 | 比較的長い | Issue closeまで |
| 実装との対応 | 一つの仕様から複数の変更へ展開される | PRや実装タスクへ直接対応しやすい |
| AIへの入力 | 仕様書、設計情報 | 実行可能なIssue |
| 完了判断 | 仕様との一致 | 受け入れ条件（Acceptance Criteria）の充足 |

両者を組み合わせると、次の階層になる。

```text
Goal
  ↓
Spec
  ↓
Issue #101
Issue #102
Issue #103
  ↓
各Issueを実装
  ↓
Pull Request
```

仕様が「何を実現したいか」を保持し、Issueが「そのために次に何を変更するか」を保持する。

## Issueを書いた時点で仕事を渡せる

AIコーディングエージェントでは、Issueを実行単位として扱うと、エージェントへ渡す仕事の境界を明確にしやすい。

```text
Issue取得
   ↓
コードベース調査
   ↓
実装計画
   ↓
実装
   ↓
テスト
   ↓
Pull Request作成
   ↓
レビュー対応
   ↓
CI確認
   ↓
merge
```

この構造なら、人間が毎回チャットで細かく作業指示を与えるのではなく、Issueを書いた時点で仕事を渡せる。
人間とAIの役割分担も整理しやすい。

```text
人間
  ↓
目的・制約・完了条件をIssueへ記述
  ↓
AI Agent
  ↓
調査・実装・検証
  ↓
Pull Request
  ↓
人間 / CI
  ↓
レビュー・承認
```

## チケットの読み手が人間からエージェントへ広がった

従来のチケット駆動開発では、チケットは主に人間の作業を管理し、変更履歴を追跡するために使われていた。
AIエージェントを組み合わせると、Issueの役割が広がる。

```text
従来

Issue
  ↓
人間が読む
  ↓
人間が考える
  ↓
人間が実装する
```

```text
AIエージェントを利用する場合

Issue
  ↓
Agentが読む
  ↓
Agentが調査・計画する
  ↓
Agentが実装・検証する
  ↓
人間がレビューする
```

この変化で、Issueは「人間のタスク管理単位」だけでなく、「AIエージェントへ渡せる実行単位」として扱えるようになる。

## Issueを書くだけではIssue駆動開発にならない

最低限、次の関係を追跡できる必要がある。

| 問い | 記録する場所 |
|---|---|
| なぜ変更したのか | Issue |
| 何を変更したのか | Commit / Pull Request |
| 正しく変更できたか | Test / CI |
| 誰が確認したか | Review |
| 変更は完了したか | Merge / Issue close |

この一連の情報が結び付いていることで、後から変更理由や判断を確認できる。

## 仕様と実装の間に実行可能な単位を置く

元資料の現時点での整理では、AIエージェントを使う開発では次の構造が扱いやすい。

```text
Goal
  ↓
Spec
  ↓
Issue
  ↓
Agent Execution
  ↓
Pull Request
  ↓
CI / Review
  ↓
Merge
```

この構造では、仕様と実装の間にIssueという実行可能な単位が置かれる。
その結果、人間は目的、制約、受け入れ条件を定義し、AIエージェントはIssueを単位として調査、実装、検証を進める、という責務分担を作れる。

今後AIエージェントによる開発方法を整理するときは、「Issueをタスク管理から作業契約へ変える」という視点が一つの軸になる。
これは元資料の整理であり、確立した標準ではない。
