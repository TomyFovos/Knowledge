# Treg Web AccessによるSEOエージェントの情報取得改善

Treg Web Accessは、Web検索、URL本文取得、構造化抽出、サイト内URL探索、ニュース検索、プラットフォーム別データ取得を、複数の外部プロバイダー経由で利用するための取得・ルーティング層である。

このノートは2026-10-19作成の提供資料を整理したもの。以下の製品仕様・料金・規約に関する記述は資料時点の調査結果であり、今回の取り込みで再検証していない。資料の確認事項、設計判断、要確認事項を区別し、詳細と出典は原本へ残している。

## 解きたい問題と検討結果

提供資料の中心課題は、SEO改善を閉ループで行うAIエージェントが、同種のページや一部の検索結果に偏っていることである。今回の検討対象は情報取得・調査品質であり、改善施策の実行環境は利用側で用意する前提になっている。

**検討結果は、Tregを競合・公開Web情報の取得層に使い、Search ConsoleやPageSpeed Insightsの公式APIを自サイトの実測・診断データ層として別に接続する構成である。** Tregの導入だけで偏りが解消するかは未検証であり、調査対象の選び方、本文の取得成功、独立した出典、欠落時の停止条件も設計する。

## Tregが担当する範囲

資料によると、提供主体はSuperdesign。CLIやSkillはローカルのエージェントから利用できるが、取得処理は通常外部サービスで行う。ローカルに置いたスクレイパーだけで完結する構成ではない。

```text
AIエージェント → Treg CLI / API → ルーティング
                                  ├─ TinyFish：無料優先経路
                                  ├─ 別の取得プロバイダー
                                  └─ SNS・EC・SEO等の専用データ
                ← 本文・URL・構造化データ・履歴・費用
```

検索結果の信頼性評価、引用、仮説の判断、SEO施策の妥当性確認は利用側の責務である。ログイン済みブラウザーの操作やPlaywright / CDPの代替として扱わない。

| 機能 | 資料にあるジョブ | SEO調査での用途 |
|---|---|---|
| Web検索 | `treg.web.search` | 競合・関連トピックの発見 |
| 本文取得 | `treg.web.extract` | 記事本文・見出しの確認 |
| 構造化抽出 | `treg.web.extract.structured` | タイトル、見出し、FAQの比較 |
| URL探索 | `treg.web.map` | サイト内の関連ページの発見 |
| ニュース検索 | `treg.web.search.news` | 新しい話題と公開日の確認 |
| 専門データ | 現行カタログから選択 | SNS、EC、レビュー、SEO専門情報など |

通常検索と重複する機能も多い。既存ツールでも本文取得やサイト探索が可能なら、機能の有無だけで優劣を判断しない。Tregでもすべてのサイトを取得できる保証はない。

## 無料経路と費用制御

資料ではTinyFishによる検索・ページ取得が無料優先経路として案内される。一方、有料プロバイダーへのフォールバックや専門ジョブには料金が発生しうる。ローカルCLIを使うことが無料の理由ではない。

| 設定 | 役割 |
|---|---|
| `X-Treg-Route-Prefer` | 優先プロバイダー |
| `X-Treg-Route-Exclude` | 除外プロバイダー |
| `X-Treg-Route-Max-Cost` | ルーティング呼び出しの費用上限 |
| `X-Treg-Route-Waterfall: 0` | 連鎖的な切り替えを抑制 |

提供資料が参照した公式Skillには、上限未指定のフォールバックで最大1米ドルに達しうるという注意がある。常に1ドルかかるという意味ではない。導入時はヘッダーの仕様・上限の単位・最新価格を確認する。

直接プロバイダージョブの`tinyfish.web.fetch`には複数URL取得の例があるが、Tregの自動フォールバックはない。導入・認証・コマンド例の詳細は原本に保存しており、今回の追加ではインストールや呼び出しは実行していない。

## Google系データを別の役割として接続する

| 情報源 | 得られる情報 | 資料の構成案 |
|---|---|---|
| Search Console | 自サイトのクエリ、表示回数、クリック、CTR、平均順位 | 認証付き公式API |
| PageSpeed Insights | Lighthouseの性能診断、Core Web Vitals関連情報 | 公式API |
| Google Trends | 検索関心度の推移 | 正式な取得手段・条件を別途確認 |
| 競合の公開ページ | 本文、見出し、リンク、FAQなど | Treg等の公開Web取得 |
| SEO専門サービス | バックリンク、競合分析など | 各社API、対応があればTreg経由 |

「GoogleInsights」がどのサービスを指すかは元の会話でも未確定。Tregを導入すればGoogle APIがすべて自動利用できる、とは扱わない。現行カタログの対応ジョブ、認証・権限、公式APIを直接使う場合との運用差を確認する。

## 情報源の偏りに対処する調査設計

Tregが役立つ可能性があるのは、スニペットで止まらず本文を読むこと、競合サイト内の関連ページを探すこと、取得失敗時に別経路を試すこと、専用情報源を増やすことである。

一方、同じクエリ・サイトだけを選ぶ行動、情報の新しさ・独立性・品質の評価、自サイトAPIの認証、改善の実装・効果測定・ロールバックは別に扱う。

資料で提案されている調査ルール：

- 調査前にGoogle公式、競合一次ページ、実測値、SEO専門データなどの情報源カテゴリを決める。
- 検索結果URLの収集と、本文取得の成功を区別する。
- 同一ドメインや類似コンテンツへの過度な依存を検出する。
- 根拠ごとにURL、取得日時、取得方法、対象指標、失敗・欠落を記録する。
- Googleの実測・診断データと、競合記事からの推測を分ける。
- 必須データが欠ける場合は断定的な施策判断へ進まない。
- 改善前後の計測期間、対象URL、クエリ、計測条件を揃える。

## 検証案と評価指標

1. 現行ログから検索クエリ、参照ドメイン、実際に読めた本文、取得失敗を集計する。
2. 同じSEOタスクについて、現行検索のみとTregの本文取得・サイト探索を追加した構成を比較する。
3. 公式APIの自サイト指標を別系統で取得し、公開Web情報と照合する。
4. 取得品質と、その後のSEO成果を別々に評価する。

| 評価対象 | 指標例 |
|---|---|
| 情報源の多様性 | ユニークな参照ドメイン数、カテゴリの分散 |
| 取得品質 | 実際に取得できた本文数、取得失敗率 |
| 証拠 | 出典・取得日時・方法を追えるか、根拠の再現性 |
| 費用 | タスクごとのAPIコスト、フォールバック履歴 |
| 最終成果 | 条件を揃えた検索パフォーマンスの変化 |

これは提供資料の検証計画であり、Tregの性能優位やSEO改善効果を実証した結果ではない。

## 規約・データ処理・ライセンスの確認点

資料ではホスト型サービスはEarly Accessとされ、SLA、Enterprise契約、DPA、データ所在地、監査要件は個別確認事項である。

プロキシ側でリクエスト・レスポンス本文を保存しないという説明と、呼び出しメタデータの記録、外部プロバイダーへの処理用情報送信は区別する。公開Web取得を主目的とし、Cookieやログインセッションを渡す運用を当然の前提にしない。

**提供資料によるとLICENSEは追加条項を含み、無条件のApache 2.0として扱えない。** 内部商用セルフホストと、第三者向けのホスト型・マネージド型・組み込みサービス提供を分け、最新の許諾範囲を確認する。

## 未解決事項

- 既存エージェントの偏りの主因が、検索クエリ、検索エンジン、取得失敗、ページ選定、重複排除のどこにあるか。
- 現行カタログのSEO関連ジョブ、価格、品質、レート制限。
- Search Console・PageSpeed InsightsをTreg経由にする価値と、直接接続との差。
- Google Trendsの正式な取得経路、元の会話の「GoogleInsights」の対象。
- Enterprise契約、SLA、データ処理条件、ライセンス。
- 参照先の多様性・本文取得成功率が実際に改善するか。
