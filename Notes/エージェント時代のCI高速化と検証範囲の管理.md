# エージェント時代のCI高速化と検証範囲の管理

エージェントのコード生成が速くなると、CI待ちが開発ループの上限になる。提供資料はCIを待ち・準備・実行へ分解し、最大40分から約2分へ短縮した事例を整理している。

資料の調査日は2026-10-31、取り込み日は2026-11-02。数値は記事やサービス側の報告で、原記事の完全なURLは資料にない。今回の実測やRepositoryのCI変更は行っていない。

## 施策と交換条件

| 施策 | 資料の事例 | 注意する範囲 |
|---|---|---|
| ランナー確保 | 最大11分の待ちを8秒へ | 小さいジョブの待ちも全体を止める |
| 並列・シャード | 最遅ジョブの余分な役割を分離 | CPU・DB・状態分離、並列費用 |
| lint・型検査の置換 | lint 2分→5秒等 | 速さと検査の互換性は別 |
| モジュール再読込抑制 | Vitestの`isolate: false`で100秒→35秒 | テスト間状態を片付ける必要 |
| 準備・キャッシュ | 依存キャッシュ外れ半数→1%等 | キー・参照範囲・復元経路を調べる |
| 変更範囲のみ実行 | `nx affected`、フルテストは夜間 | 変更検出が誤ると未実行で緑になる |
| pre-push検査 | 変更ファイルの検査を9秒未満で実行 | 対象・回避・CIとの役割を確認する |

キャッシュの説明は当該事例の不具合・復元構成として読み、資料中の「mainから自動利用できない」等をGitHub Actions全般の条件へそのまま一般化しない。

## 検証を省く判定そのものを検証する

資料には、サーバー変更をNxから見えなくすると6シャードすべてがテストを省き、緑になった失敗例がある。対象テスト数、依存関係、変更検出の故障を確認し、「未実行」と「成功」を同じ表示にしないことが教訓になる。

lint・型検査を高速実装へ替える場合も、tsc等と同じ指摘・対象を保てるかは別に確認する。`isolate: false`の高速化は、状態分離を捨てても常に安全という意味ではない。

指示だけに頼らずフックで機械的に検査するという考えは有用だが、フックを置いたことだけで回避不能・完全な強制が成立したとは扱わない。

## 費用と次のボトルネック

事例の月額は230ドルから4,300ドルへ増えている。大きなランナーで速度を買う施策と、待ち・重複・不要実行を減らして費用も抑える施策を分ける。各施策の費用内訳は未提示である。

CIが短くなれば次は人間のマージ待ち等が支配する。全体のcritical pathで測り、検査本体だけを最適化しない。自前VMと外部ランナーの差も、I/O・初期化・展開等の原因別に実測するというのが資料の検討である。
